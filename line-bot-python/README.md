# LINE OA Bot (Python) — ระบบแจ้งปัญหา IT

บอท LINE Official Account ที่คุยกับพนักงานเป็นภาษาไทย รับแจ้งเรื่อง สร้าง ticket เข้าระบบ
และตอบคำถามจากข้อมูลจริงในฐานข้อมูลของโปรเจกต์ (สต็อก ทรัพย์สิน สถานะงาน FAQ)

---

## สถาปัตยกรรม

```
  พนักงานใน LINE
        │  webhook (HTTPS + ลายเซ็น HMAC-SHA256)
        ▼
  ┌──────────────────────────────────────┐
  │  Python service (FastAPI)            │
  │   • ตรวจลายเซ็น                       │
  │   • State machine ของบทสนทนา          │
  │   • ชั้น AI: ตัดคำไทย + TF-IDF + fuzzy │
  │   • state เก็บใน memory หรือ Redis     │
  └──────────────┬───────────────────────┘
                 │  HTTP + INTERNAL_API_KEY
                 ▼
  ┌──────────────────────────────────────┐
  │  Next.js admin (/api/internal/*)     │
  │   • สร้าง ticket / ตัดสต็อก            │
  │   • อ่านสาขา ทรัพย์สิน สต็อก FAQ        │
  └──────────────┬───────────────────────┘
                 ▼
           ฐานข้อมูลของระบบ
```

**ทำไมแยกเป็น 2 service แทนที่จะให้ Python เขียนฐานข้อมูลเอง**

ตรรกะสำคัญ (การออกเลข ticket, การตัดสต็อก, การผูกผู้แจ้ง) อยู่ในฝั่ง Next.js อยู่แล้ว
ถ้าให้ Python เขียนตรงจะต้อง maintain ตรรกะเดียวกัน 2 ภาษา และถ้ามี 2 process เขียนไฟล์
ข้อมูลเดียวกันพร้อมกันจะเกิด race condition วันที่ย้ายไป Supabase ก็แก้แค่ฝั่งเดียว บอทไม่ต้องแตะ

## ติดตั้งและรัน

```bash
cd line-bot-python
python -m venv .venv
.venv\Scripts\activate          # Windows
# source .venv/bin/activate     # macOS / Linux

pip install -r requirements.txt
copy .env.example .env          # Windows  (macOS/Linux: cp)
# แก้ค่าใน .env ให้ครบ แล้วรัน
uvicorn app.main:app --reload --port 8000
```

ตรวจว่าขึ้นแล้ว: เปิด `http://localhost:8000/health` ต้องได้ `{"ok": true, ...}`

ฝั่ง Next.js ต้องรันคู่กันด้วย และต้องมี `INTERNAL_API_KEY` ใน `.env` ตรงกันทั้งสองฝั่ง

## ตัวแปรสภาพแวดล้อม

| ตัวแปร | จำเป็น | คำอธิบาย |
|---|---|---|
| `LINE_CHANNEL_SECRET` | ✅ | Basic settings ของ channel — ใช้ตรวจลายเซ็น webhook |
| `LINE_CHANNEL_ACCESS_TOKEN` | ✅ | แท็บ Messaging API — ใช้ส่งข้อความกลับ |
| `INTERNAL_API_KEY` | ✅ | ต้องตรงกับฝั่ง Next.js สร้างด้วย `openssl rand -hex 32` |
| `BACKEND_BASE_URL` | | URL ของแอดมินแพเนล (ค่าตั้งต้น `http://localhost:3000`) |
| `REDIS_URL` | | เว้นว่าง = เก็บ state ในหน่วยความจำ (dev เท่านั้น) |
| `SESSION_TTL_SECONDS` | | อายุบทสนทนาที่ค้างไว้ ค่าตั้งต้น 1800 วินาที |
| `WELCOME_BACK_DAYS` | | หายไปนานกว่ากี่วันถึงทักต้อนรับกลับ ค่าตั้งต้น 7 (0 = ปิด) |
| `AI_PROVIDER` | | `none` (ตั้งต้น) / `openai` / `anthropic` |
| `AI_API_KEY`, `AI_MODEL` | | ใส่เมื่อเปิดชั้น LLM เท่านั้น |
| `KNOWLEDGE_TTL_SECONDS` | | cache ข้อมูลจาก DB กี่วินาที ค่าตั้งต้น 300 |
| `LINE_API_HOST` | | **ใช้ตอนทดสอบเท่านั้น** ชี้ไปเซิร์ฟเวอร์จำลอง ปล่อยว่างเสมอในการใช้งานจริง |

## เชื่อมกับ LINE Official Account

### 1. เปิด public URL ให้ webhook

LINE ต้องยิงเข้ามาได้จากอินเทอร์เน็ตและต้องเป็น HTTPS ตอน dev ใช้ tunnel:

```bash
# ngrok
ngrok http 8000

# หรือ Cloudflare Tunnel (ไม่ต้องสมัคร)
cloudflared tunnel --url http://localhost:8000
```

จะได้ URL เช่น `https://xxxx.ngrok-free.app`

### 2. ตั้งค่าใน LINE Developers Console

ไปที่ <https://developers.line.biz/console/> เลือก channel แล้วตั้งตามนี้:

| หัวข้อ | ค่าที่ต้องตั้ง |
|---|---|
| Messaging API → Webhook URL | `https://xxxx.ngrok-free.app/webhook` |
| Messaging API → Use webhook | **เปิด** |
| Messaging API → Auto-reply messages | **ปิด** (ไม่งั้นจะตอบซ้อนกับบอท) |
| Messaging API → Greeting messages | ปิด ถ้าจะให้บอทจัดการเอง หรือดูข้อ 3 |

กด **Verify** ข้างช่อง Webhook URL — ต้องขึ้น Success (service มี endpoint `GET /webhook` รองรับไว้แล้ว)

### 3. ข้อความต้อนรับ (Greeting message)

ในรูปต้นแบบ บับเบิลแรกมาจาก Greeting message ที่ตั้งใน LINE Official Account Manager
(<https://manager.line.biz/>) → Auto-responses → Greeting messages วางข้อความนี้:

```
สวัสดีครับ 👋 ยินดีต้อนรับสู่ระบบแจ้งปัญหา IT

กดปุ่ม "แจ้งเรื่องใหม่" เพื่อเลือกบริษัทและสาขาได้เลยครับ
หรือพิมพ์ชื่อสาขามาตรงๆ ก็ได้ เช่น: ภูเก็ต, สำนักงานใหญ่, ลาดพร้าว

📋 บริการที่รองรับ:
🖊 แจ้งซ่อมอุปกรณ์
📦 เบิกอุปกรณ์
🔄 คืนอุปกรณ์
```

บับเบิลที่สอง (ที่ทักชื่อผู้ใช้ พร้อมปุ่มเมนู) บอทเป็นคนส่งจาก follow event เอง ไม่ต้องตั้งอะไร

> ถ้าไม่อยากตั้ง Greeting message ก็ข้ามได้ บอทจะทักเองอยู่แล้ว แค่จะไม่มีบับเบิลแรก

## บทสนทนาที่รองรับ

### แจ้งเรื่อง (ได้ ticket จริงเข้าระบบ)

```
เลือกบริษัท → [ถ้าสาขาเยอะ: เลือกกลุ่ม/ทีม] → เลือกสาขา → เลือกประเภท
            → ใส่รหัสทรัพย์สิน → [ถ้าเบิก: เลือกของ + จำนวน]
            → ชื่อผู้แจ้ง → รายละเอียด → ได้เลขที่ ticket
```

ประเภทที่รองรับ: 🖊 แจ้งซ่อม · 📦 เบิกอุปกรณ์ · 🔄 คืนอุปกรณ์ · 🛠 ขอใช้บริการ IT

พิมพ์ `ยกเลิก` ออกจากขั้นตอนได้ทุกเมื่อ และบทสนทนาที่ค้างเกิน 30 นาทีจะหมดอายุเอง

**เลือกบริษัทก่อนสาขาเสมอ** — มี 3 บริษัท: Montipa · Motta · ส่วนกลาง
เพราะชื่อสาขาซ้ำกันข้ามบริษัทได้จริง (ขอนแก่น / ชลบุรี / หาดใหญ่ มีทั้ง 2 บริษัท) ถ้าถามแค่สาขา
ticket จะบอกไม่ได้ว่าต้องส่งช่างของบริษัทไหนไป และรวมกันแล้วมีร้อยสาขาซึ่งใส่ปุ่มชุดเดียวไม่พอ
(LINE จำกัด quick reply ที่ 13 ปุ่ม) บริษัทที่สาขาเกิน 11 สาขาจึงมีชั้น "เลือกกลุ่ม/ทีม" คั่นก่อน
พร้อมปุ่ม "📋 ดูสาขาทั้งหมด" และปุ่มเลื่อนหน้าไว้ให้คนที่จำกลุ่มตัวเองไม่ได้

**ชื่อสาขาถูกตรวจกับข้อมูลจริงในระบบ** ถ้าพิมพ์สาขาที่ไม่มีจะถูกปฏิเสธ (เหมือนต้นแบบ)
แต่ยอมให้พิมพ์ผิดเล็กน้อยได้ เช่น `สำนักงานใหย่` → จับเป็น `สำนักงานใหญ่` ให้อัตโนมัติ
ถ้าเลือกบริษัทไว้แล้ว การค้นจะจำกัดเฉพาะสาขาของบริษัทนั้น ซึ่งแม่นขึ้นด้วยเพราะชุดที่เอามาเทียบเล็กลง

พิมพ์ชื่อสาขามาตรงๆ โดยข้ามขั้นตอนเลือกบริษัทได้ ถ้าชื่อสาขานั้นไม่ซ้ำข้ามบริษัท (บอทเติมบริษัทให้เอง)
แต่ถ้าซ้ำ บอทจะถามบริษัทเสมอ ไม่เดาให้ — ticket ที่ระบุบริษัทผิดแย่กว่า ticket ที่ไม่ระบุบริษัท

### ถามข้อมูลในระบบ (ไม่ต้องเปิดหน้าเว็บ)

| พิมพ์ | บอทตอบ |
|---|---|
| `คีย์บอร์ดเหลือกี่อัน` | ยอดคงเหลือสดจากตารางสต็อก + เตือนถ้าต่ำกว่าขั้นต่ำ |
| `สต็อกเหลือเท่าไหร่บ้าง` | 5 รายการที่ใกล้หมดที่สุด |
| `NB2501001 ใครถืออยู่` | รุ่น สถานะ ผู้ถือครอง ที่ตั้ง จำนวนครั้งที่ซ่อม |
| `ITRQ2026090158 ถึงไหนแล้ว` | สถานะ ประเภท สาขา ผู้แจ้ง วันที่แจ้ง |
| `ขอดูเรื่องที่แจ้งไป` | รายการ ticket ทั้งหมดของผู้ใช้ LINE คนนั้น |
| `ปริ้นเอกสารไม่ได้` | คำตอบจาก FAQ ที่แอดมินสร้างไว้ + ปุ่มแจ้งเรื่องถ้ายังไม่หาย |

ยอดสต็อกอ่านสดทุกครั้งที่ถาม ไม่ใช้แคช เพราะตัวเลขที่ผิดแย่กว่าการไม่ตอบ

### ประโยคเดียวจบ

บอทดึงข้อมูลออกจากประโยคแรกได้ แล้วถามเฉพาะส่วนที่ยังไม่รู้:

```
ผู้ใช้: ขอเบิกเมาส์ 2 อัน ที่สาขาเชียงใหม่
บอท:   รับทราบครับ 👍
       • สาขา: สาขาเชียงใหม่
       • อุปกรณ์: เมาส์ x2
       ระบุหมายเลขทรัพย์สินครับ ...
```

บอทจะสรุปสิ่งที่เข้าใจออกมาให้เห็นเสมอ เพื่อให้ผู้ใช้จับผิดได้ทันทีถ้า AI เดาพลาด

## คำทักทาย — ตอนแอดใหม่ และตอนทักเข้ามาใหม่

| สถานการณ์ | บอททำอะไร |
| --- | --- |
| กดเพิ่มเพื่อน (follow event) | ทักด้วยชื่อ + การ์ดเมนู |
| พิมพ์คำทักทายล้วนๆ ("สวัสดีครับ", "hi") | ทักกลับ + การ์ดเมนู แล้วจบ |
| หายไปเกิน `WELCOME_BACK_DAYS` แล้วพิมพ์เข้ามา | ทักต้อนรับกลับ **แล้วตอบเรื่องที่ถามต่อ** |
| พิมพ์อะไรมาแล้วตีความไม่ออกเลย | "ยังไม่เข้าใจข้อความนี้" + การ์ดเมนู |
| กดปุ่ม/พิมพ์ "ยกเลิก" กลางทาง | ขอบคุณที่ใช้บริการ + ถามชื่อคนนั้นว่าจะแจ้งเรื่องอะไรต่อไหม + เมนู |

**ข้อความต้อนรับสั้น รายละเอียดอยู่ในการ์ด** — บับเบิลข้อความยาวๆ บนมือถือกินเกือบครึ่งจอ
คนจึงปัดผ่านแล้วไปกดเมนูอยู่ดี รายการบริการจึงย้ายไปอยู่ในการ์ด (flex) ที่อ่านง่ายกว่า
เพราะแยกเป็นบรรทัดละบริการพร้อมไอคอนและปุ่มกดต่อได้ทันที

**ยกเลิกแล้วต้องไม่จบห้วนๆ** — คนกดยกเลิกส่วนใหญ่ไม่ได้เลิกอยากแจ้ง แต่กรอกผิดขั้นตอน
แล้วอยากเริ่มใหม่ ถ้าบอทตอบแค่ "ยกเลิกรายการแล้ว" เขาต้องเดาเองว่าต้องพิมพ์อะไรต่อ
ซึ่งเป็นจุดที่คนออกจากแชทไปเลยมากที่สุด · ชื่อในคำถามใช้ `incoming.display_name`
และตกกลับไปใช้ `session.line_display_name` เมื่อ event นั้นไม่ได้แนบชื่อมา ·
ไม่เติม "คุณ" ซ้ำถ้าชื่อโปรไฟล์ขึ้นต้นด้วย "คุณ" อยู่แล้ว ("คุณคุณเอ" อ่านแล้วเหมือนบอทพัง)

**บั๊กที่แก้ไปพร้อมกัน — พิมพ์ "สวัสดีครับ" แล้วบอทตอบว่า "ไม่พบสาขา"**

ข้อความแรกที่ไม่เข้า intent ถูกตีความว่าเป็น "ชื่อสาขา" เสมอ คนที่ทักทายหรือถามอะไรทั่วไป
จึงได้คำตอบที่ไม่เกี่ยวกับสิ่งที่พิมพ์เลย และเข้าใจว่าระบบพัง
ตอนนี้ข้อความ "ไม่พบสาขา" ใช้เฉพาะตอนที่ผู้ใช้กำลังถูกถามชื่อสาขาอยู่จริงๆ (`ASK_BRANCH`)
ซึ่งตรงนั้นเขาตั้งใจพิมพ์ชื่อสาขา การบอกว่าไม่พบจึงเป็นคำตอบที่ตรงประเด็น

**รายละเอียดที่ไม่ได้มาฟรี**

- **"สวัสดีครับ คอมเปิดไม่ติด" ต้องไม่ถูกตัดจบแค่ทักทาย** — `is_greeting()` จึงจำกัดความยาว
  ข้อความด้วย ไม่ได้ดูแค่ว่ามีคำทักทายอยู่ในประโยคไหม ไม่งั้นคนต้องพิมพ์เรื่องเดิมซ้ำอีกรอบ
- **"เห็นครั้งล่าสุดเมื่อไหร่" เก็บแยกจาก session** (`linebot:seen:*` อายุ 180 วัน)
  เพราะ session มีอายุ 30 นาทีและถูกล้างทุกครั้งที่แจ้งเรื่องจบ ถ้าใช้ session ตัดสิน
  ทุกคนจะกลายเป็น "คนที่หายไปนาน" ตลอดเวลา
- **คนใหม่ไม่ถูกทักซ้ำ** — คนที่ไม่เคยเห็นมาก่อนได้ข้อความต้อนรับจาก follow event อยู่แล้ว
- **ทักต้อนรับกลับแล้วยังตอบคำถามต่อ** ไม่ใช่ทักแทนคำตอบ และถ้าคำตอบยาวจนเต็มลิมิต
  5 บับเบิลของ LINE อยู่แล้ว จะไม่แทรกคำทักทายเข้าไปเบียด
- **Redis ล่มต้องไม่ทำให้ผู้ใช้ไม่ได้คำตอบ** — อ่าน/เขียนค่านี้ล้มเหลวแล้วถือว่า "ไม่ต้องทัก"

⚠️ **ห้ามเปิด "Greeting message" ใน LINE OA Manager** ควบคู่กับข้อความนี้ ไม่งั้นผู้ใช้จะได้
ข้อความต้อนรับซ้อนกัน 2 อันตอนแอด

## ผู้แจ้งกดยืนยันว่า "เรียบร้อยแล้ว"

เมื่อทีม IT กด "แก้ไขแล้ว" ในหน้าแอดมินและติ๊กแจ้ง LINE ผู้แจ้งจะได้การ์ดที่มีปุ่มสองปุ่ม:

```
┌────────────────────────────────┐
│ ✅ ดำเนินการเสร็จเรียบร้อยแล้ว   │
├────────────────────────────────┤
│ เลขที่เรื่อง                     │
│ ITRQ2026090158                 │
│ ประเภท  แจ้งซ่อม                │
│ สาขา    สำนักงานใหญ่             │
│ 📝 หมายเหตุจากทีม IT            │
│ เปลี่ยนสายจอแล้วครับ              │
├────────────────────────────────┤
│ [ ✅ เรียบร้อยแล้ว ]             │
│ [ ❌ ยังไม่หาย    ]             │
└────────────────────────────────┘
```

ปุ่มเป็น `postback` ส่ง `a=confirm&code=<เลขที่>&v=1|0` เข้ามาที่ `flow.py`

**บอทไม่ตัดสินใจอะไรเอง** — ส่งต่อไปที่ `POST /api/internal/tickets/confirm` ทั้งหมด
แล้วแปลผลลัพธ์เป็นข้อความ กฎว่าใครยืนยันได้และสถานะไหนกดได้อยู่ที่เดียวกับที่เขียนข้อมูล
(ใครที่ดัก postback data ไปยิงซ้ำเองก็ต้องเจอด่านเดียวกัน)

| ผลจากหลังบ้าน | บอทตอบ |
|---|---|
| `ok` + `v=1` | `confirm_thanks()` — ขอบคุณที่ยืนยัน + ปิดงานเลขที่... |
| `ok` + `v=0` | `confirm_reopened()` — ดึงเรื่องกลับเป็น "กำลังดำเนินการ" + แจ้งทีม IT แล้ว |
| `not_owner` (403) | `confirm_not_owner()` — ยืนยันได้เฉพาะผู้แจ้งเอง |
| `not_confirmable` (409) | `confirm_not_confirmable()` — บอกสถานะล่าสุดให้ด้วย |
| `not_found` (404) | `ticket_not_found()` |
| เชื่อมต่อไม่ได้ | `backend_error()` |

`confirm_ticket()` ใน `backend.py` **ไม่ raise** เมื่อได้ 403/404/409 ต่างจากเมธอดอื่น
เพราะสามอันนี้ไม่ใช่ระบบพัง แต่เป็นคำตอบที่มีความหมายกับผู้ใช้ ถ้าโยนเป็น error ทั้งหมด
ผู้ใช้จะเห็นแค่ "ระบบมีปัญหา" ซึ่งผิดและทำให้เขาแจ้งซ้ำโดยไม่จำเป็น

การ์ดค้างอยู่ในแชทตลอดไป ผู้ใช้เลื่อนขึ้นไปกดซ้ำได้เสมอ — กดยืนยันซ้ำที่ผลเหมือนเดิมจึงตอบ
ข้อความเดิมโดยไม่เขียนประวัติซ้ำ และเรื่องที่ยืนยันไปแล้วแต่กลับมาเสียอีกยังกด "ยังไม่หาย"
จากการ์ดเดิมได้ ไม่ต้องแจ้งเรื่องใหม่

## ชั้น AI ทำงานอย่างไร

| ชั้น | เทคโนโลยี | ใช้ทำอะไร | ค่าใช้จ่าย |
|---|---|---|---|
| 1 | PyThaiNLP (`newmm`) | ตัดคำไทย — ภาษาไทยไม่มีเว้นวรรค ถ้าไม่ตัดคำ การค้นหาจะพังหมด | ฟรี |
| 2 | TF-IDF + cosine (เขียนเอง) | จัดอันดับ FAQ ที่ตรงกับคำถาม | ฟรี |
| 3 | RapidFuzz | จับชื่อสาขา/ชื่อของ/รหัสทรัพย์สินที่พิมพ์ผิดเล็กน้อย | ฟรี |
| 4 | LLM ผ่าน API *(ปิดไว้)* | เรียบเรียงคำตอบจาก FAQ ให้เป็นภาษาคน (RAG) | ต่อครั้ง |

**ทำไมไม่ใช้ scikit-learn / sentence-transformers**

TF-IDF เขียนเองราว 40 บรรทัด ได้ผลดีพอกับ FAQ ระดับหลักสิบ–หลักพันรายการ
แต่ประหยัดขนาด deploy หลายสิบ MB และ cold start เร็วกว่ามาก
ถ้าวันหนึ่ง FAQ โตเป็นหลักหมื่นค่อยย้ายไป embedding + vector database

**ทำไมจับ intent ด้วยคีย์เวิร์ดไม่ใช่โมเดล**

เพราะแก้ได้ เวลาบอทเดาผิดแค่เพิ่มคำใน `INTENT_KEYWORDS` ใน `app/ai.py` แล้วรีสตาร์ท
ถ้าใช้โมเดลกล่องดำ พอเดาผิดจะทำอะไรไม่ได้นอกจากเทรนใหม่ ซึ่งไม่คุ้มกับงานระดับนี้

**เปิดชั้น LLM (ไม่บังคับ)**

```env
AI_PROVIDER=anthropic        # หรือ openai
AI_API_KEY=sk-...
AI_MODEL=claude-3-5-haiku-latest
```

เมื่อเปิด LLM จะถูกบังคับให้ตอบจากเนื้อหา FAQ ที่ค้นเจอเท่านั้น (RAG) ถ้าข้อมูลไม่พอให้ตอบว่าไม่ทราบ
ไม่งั้นมันจะแต่งวิธีแก้ปัญหา IT ที่ไม่มีอยู่จริงในองค์กรขึ้นมาเอง ซึ่งอันตรายกว่าการตอบว่าไม่รู้
ถ้าเรียก LLM ไม่สำเร็จ บอทจะตกกลับไปใช้คำตอบดิบจาก FAQ อัตโนมัติ ไม่พังทั้งบทสนทนา

## สิ่งที่ต้องทำก่อนขึ้นใช้งานจริง (ติเพื่อก่อ)

1. **เปลี่ยน state store เป็น Redis** — ค่าตั้งต้นเก็บในหน่วยความจำ พอรีสตาร์ทบทสนทนาที่ค้างจะหาย
   และถ้ารันหลาย worker แต่ละตัวจะเห็น state คนละชุด ผู้ใช้จะเจออาการ "บอทลืมว่าคุยถึงไหน"
   ใส่ `REDIS_URL` แล้วจบ ไม่ต้องแก้โค้ด

2. **ปิด `/api/internal/*` ไม่ให้เข้าถึงจากอินเทอร์เน็ตตรงๆ** — ตอนนี้กันด้วย API key อย่างเดียว
   ถ้าเป็นไปได้ควรอยู่หลัง firewall หรือจำกัด IP ของ bot service เพิ่มอีกชั้น

3. ~~**ยังไม่มี rate limit**~~ — ✅ **ทำแล้ว** จำกัดต่อ `userId` ผ่าน `RATE_LIMIT_PER_MINUTE`
   (ค่าตั้งต้น 20 ครั้ง/นาที, ตั้ง 0 เพื่อปิด) ใช้ Redis เป็นตัวนับเมื่อมี `REDIS_URL`
   เกินลิมิตครั้งแรกบอทตอบเตือน 1 ครั้ง ครั้งต่อไปในนาทีเดียวกันเงียบ — ไม่ให้บอทกลายเป็นตัวขยายสแปมเอง
   ถ้าตัวนับพัง (Redis ล่ม) จะปล่อยผ่าน ไม่ทำให้บอททั้งตัวใช้ไม่ได้

4. **ประมวลผลแบบ inline** — ตอนนี้ตอบ 200 กลับให้ LINE หลังทำงานเสร็จ ซึ่งพอสำหรับปริมาณปกติ
   ถ้าโหลดสูงควรเปลี่ยนเป็น ack ทันทีแล้วโยนงานเข้า queue (เช่น Redis Queue / Celery)

5. **FAQ ค้นไม่เจอบางคำ** — เช่น "เครื่องพิมพ์กระดาษติด" ยังไม่แมตช์กับ FAQ "ปริ้นเอกสารไม่ได้"
   เพราะคำว่า "เครื่องพิมพ์" ไม่ได้อยู่ในคีย์เวิร์ดของ FAQ นั้น
   แก้ที่หน้า FAQ Bot ในแอดมิน โดยเพิ่มคำพ้องเข้าไปในคีย์เวิร์ด — ไม่ต้องแก้โค้ด

6. ~~**ยังไม่รองรับรูป/สติกเกอร์/ไฟล์**~~ — ✅ **ทำแล้วบางส่วน**
   - **รูป**: รับแล้วแนบเข้า ticket อัตโนมัติ (ดูหัวข้อ "รูปที่ผู้ใช้ส่งมา" ด้านล่าง)
   - **สติกเกอร์/วิดีโอ/ไฟล์/เสียง**: ยังอ่านไม่ได้ แต่ตอนนี้ **ตอบกลับว่าอ่านไม่ได้** แทนที่จะเงียบ
     (การเงียบทำให้ผู้ใช้แยกไม่ออกว่าบอทไม่รองรับหรือบอทล่ม ซึ่งทำให้เลิกใช้เร็วกว่าเดิม)

## รูปที่ผู้ใช้ส่งมา

ภาพหน้าจอที่ error คือสิ่งแรกที่คนส่งเวลาเจอปัญหา IT บอทจึงรับรูปแล้วแนบเข้า ticket ให้เลย

**เส้นทางของไฟล์:**

```
ผู้ใช้ส่งรูป
  -> main.py ดาวน์โหลดจาก LINE Content API (api-data.line.me) แบบ stream
  -> ตัดจบทันทีถ้าเกิน MAX_IMAGE_BYTES (ไม่รอโหลดจบแล้วค่อยเช็ค)
  -> อัปโหลดต่อไปที่ POST /api/internal/attachments ของ Next.js
  -> ได้ URL กลับมา เก็บไว้ใน session
  -> ตอนสร้าง ticket ส่งไปเป็น image_urls -> เก็บใน meta -> แสดงในหน้า /tickets
```

**พฤติกรรมที่ออกแบบไว้:**

| สถานการณ์ | บอททำอะไร |
| --- | --- |
| ส่งรูปตอนยังไม่ได้เริ่มแจ้งเรื่อง | เก็บรูปไว้แล้ว**เปิด flow ให้เลย** ไม่ต้องส่งรูปซ้ำ |
| ส่งรูประหว่างแจ้งเรื่อง | แนบเพิ่ม + **ถามคำถามของ step เดิมซ้ำ** ไม่ให้ผู้ใช้ค้าง |
| เกิน `MAX_IMAGES_PER_TICKET` | บอกตรงๆ ว่าแนบได้กี่รูป |
| รูปใหญ่เกิน / โหลดไม่สำเร็จ | บอกเหตุผล แล้วให้แจ้งเรื่องต่อได้โดยพิมพ์อธิบายแทน |

ทำไมการดาวน์โหลดอยู่ใน `main.py` ไม่ใช่ `flow.py`: LINE เก็บไฟล์ให้ดาวน์โหลดได้ระยะเวลาจำกัด
ถ้ารอไปทำทีหลังจะได้ 404 — และ `flow.py` ตั้งใจออกแบบไม่ให้รู้จัก LINE API เลย เพื่อให้เทสต์บทสนทนา
ได้โดยไม่ต้องมี token (ดู `tests/test_flow.py`)

## รหัสทรัพย์สินที่ซ้ำกัน

ข้อมูลจริงมี **28 แถวที่ใช้รหัสซ้ำกับเครื่องอื่น** (เช่น `PC2306001` ถูกใช้กับ 4 เครื่องคนละสาขา —
ดู `db/imports/equipment-import-conflicts.csv`)

เดิมระบบคืนเครื่องแรกที่เจอเงียบๆ แปลว่า ticket อาจผูกกับเครื่องผิดสาขาโดยไม่มีใครรู้จนช่างไปถึงหน้างาน

ตอนนี้ `GET /api/internal/lookup?kind=equipment` คืน `matches` ครบทุกเครื่อง และบอทจะ**ให้ผู้ใช้เลือก**
พร้อมแสดงสถานที่/ผู้ถือครองกำกับ (เพราะรหัสอย่างเดียวแยกไม่ออก)

เมื่อเลือกแล้วบอทส่ง **`equipment_id`** ไปกับ ticket ด้วย ไม่ใช่แค่ `asset_code` —
ไม่งั้นการอุตส่าห์ถามว่า "เครื่องไหน" จะเสียเปล่า เพราะหลังบ้านได้รหัสที่กำกวมไปแล้วต้องเดาเองอยู่ดี

ทุกทางเข้าที่ผูกเครื่อง (พิมพ์รหัสเอง · ไล่เมนูประเภท→ยี่ห้อ→รหัส · AI จับรหัสจากประโยคแรก)
เรียกตัวผูกเครื่องตัวเดียวกันใน `flow.py` จึงถามเรื่องรหัสซ้ำเหมือนกันทั้งหมด
(เดิมทาง AI เดาจาก knowledge cache ตรงๆ รหัสที่ซ้ำ 4 เครื่องจึงถูกรับเงียบๆ เฉพาะทางนั้นทางเดียว)

⚠️ นี่เป็นการลดความเสียหาย ไม่ใช่การแก้ต้นเหตุ — **รหัสซ้ำยังควรแก้ที่ข้อมูลต้นทาง**

## กดส่งซ้ำแล้วต้องไม่ได้ ticket 2 ใบ

ตอนส่งไม่สำเร็จ บอทเก็บ session ไว้ให้กดปุ่ม "🔁 ลองส่งใหม่" ได้ ไม่ต้องกรอกใหม่ทั้งหมด
แต่ **"บอทส่งไม่สำเร็จ" ไม่ได้แปลว่าหลังบ้านไม่ได้สร้าง ticket** — timeout หลังจากเขียนข้อมูลลงไปแล้ว
เป็นเคสคลาสสิก ถ้ากดส่งซ้ำแล้วยิงเข้าไปเฉยๆ จะได้ ticket 2 ใบและตัดสต็อกซ้ำ 2 รอบ

แต่ละ session จึงมี `request_id` ของตัวเอง (สร้างตอนเปิดเรื่อง คงเดิมตลอดแม้ session ถูกเก็บลง Redis
แล้วอ่านกลับมา) ส่งไปกับทุกครั้งที่ยิงสร้าง ticket หลังบ้านเจอ `request_id` ซ้ำจะ**คืน ticket เดิม**
แทนการสร้างใหม่ ผู้ใช้จึงเห็นเลขที่เดิม ไม่ใช่เลขใหม่ที่ทำให้สับสนว่าตกลงแจ้งไปกี่เรื่อง

ปุ่มนี้ทำงานเฉพาะตอนอยู่ในสถานะ `RETRY_SUBMIT` เท่านั้น — ผู้ใช้เลื่อนขึ้นไปกดปุ่มเก่าที่ค้างบนจอ
ระหว่างกรอกเรื่องใหม่ได้ ถ้าไม่ดักจะได้ ticket ที่ไม่มีผู้แจ้ง ไม่มีรายละเอียด และตัดสต็อกโดยไม่มีรายการ

## โครงสร้างไฟล์

```
line-bot-python/
├── app/
│   ├── main.py        FastAPI + webhook endpoint (ไม่มี logic บทสนทนา)
│   ├── flow.py        state machine ของบทสนทนา ← หัวใจของระบบ
│   ├── messages.py    ข้อความไทยและปุ่มทั้งหมด ← แก้คำพูดที่นี่
│   ├── ai.py          ตัดคำไทย, TF-IDF, จับ intent/slot, ชั้น LLM
│   ├── backend.py     client ไปยัง /api/internal/* ของ Next.js
│   ├── store.py       เก็บ state (memory / Redis)
│   ├── line_api.py    ห่อ line-bot-sdk v3
│   └── config.py      อ่าน env + validate ตอน startup
└── tests/
    ├── test_flow.py   บทสนทนาทั้งเส้น
    ├── test_ai.py     ชั้น AI และการตอบจากข้อมูล
    └── e2e/           ทดสอบจริงผ่าน HTTP ทั้งระบบ
```

จุดที่ควรแก้บ่อยที่สุดคือ `messages.py` (คำพูด) และ `ai.py` (คีย์เวิร์ดจับ intent)
ส่วน `flow.py` แก้เมื่อจะเพิ่ม/ลดขั้นตอนของบทสนทนาเท่านั้น
