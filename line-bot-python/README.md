# LINE OA Bot (Python) — ระบบแจ้งปัญหา IT

บอท LINE Official Account ที่คุยกับพนักงานเป็นภาษาไทย รับแจ้งเรื่อง สร้าง ticket เข้าระบบ
และตอบคำถามจากข้อมูลจริงในฐานข้อมูลของโปรเจกต์ (สต็อก ทรัพย์สิน สถานะงาน FAQ)

---

## สถาปัตยกรรม

```
  พนักงานใน LINE
        │  webhook (HTTPS + ลายเซ็น HMAC-SHA256)
        ▼
  ┌──────────────────────────────────────┐
  │  Python service (FastAPI)            │
  │   • ตรวจลายเซ็น                       │
  │   • State machine ของบทสนทนา          │
  │   • ชั้น AI: ตัดคำไทย + TF-IDF + fuzzy │
  │   • state เก็บใน memory หรือ Redis     │
  └──────────────┬───────────────────────┘
                 │  HTTP + INTERNAL_API_KEY
                 ▼
  ┌──────────────────────────────────────┐
  │  Next.js admin (/api/internal/*)     │
  │   • สร้าง ticket / ตัดสต็อก            │
  │   • อ่านสาขา ทรัพย์สิน สต็อก FAQ        │
  └──────────────┬───────────────────────┘
                 ▼
           ฐานข้อมูลของระบบ
```

**ทำไมแยกเป็น 2 service แทนที่จะให้ Python เขียนฐานข้อมูลเอง**

ตรรกะสำคัญ (การออกเลข ticket, การตัดสต็อก, การผูกผู้แจ้ง) อยู่ในฝั่ง Next.js อยู่แล้ว
ถ้าให้ Python เขียนตรงจะต้อง maintain ตรรกะเดียวกัน 2 ภาษา และถ้ามี 2 process เขียนไฟล์
ข้อมูลเดียวกันพร้อมกันจะเกิด race condition วันที่ย้ายไป Postgres ก็แก้แค่ฝั่งเดียว บอทไม่ต้องแตะ

## ติดตั้งและรัน

```bash
cd line-bot-python
python -m venv .venv
.venv\Scripts\activate          # Windows
# source .venv/bin/activate     # macOS / Linux

pip install -r requirements.txt
copy .env.example .env          # Windows  (macOS/Linux: cp)
# แก้ค่าใน .env ให้ครบ แล้วรัน
uvicorn app.main:app --reload --port 8000
```

ตรวจว่าขึ้นแล้ว: เปิด `http://localhost:8000/health` ต้องได้ `{"ok": true, ...}`

`/health` คืน `richmenu_state` (ASCII: `ok` · `installed` · `installing` · `disabled` · `failed`)
คู่กับ `richmenu` ที่เป็นข้อความไทยสำหรับคนอ่าน — **สคริปต์ต้องอ่านจาก `richmenu_state` เท่านั้น**

ฝั่ง Next.js ต้องรันคู่กันด้วย และต้องมี `INTERNAL_API_KEY` ใน `.env` ตรงกันทั้งสองฝั่ง

## เชื่อมกับ LINE Official Account

### 1. เปิด public URL ให้ webhook

LINE ต้องยิงเข้ามาได้จากอินเทอร์เน็ตและต้องเป็น HTTPS

**ระบบนี้ใช้ Cloudflare Tunnel เป็นทางเข้าจริง** ตั้งแต่ 7 ต.ค. 2026 (container `tunnel` ใน
`docker-compose.yml`) — `https://it.thanakronpart-time.com/webhook` → `http://bot:8000/webhook`
ตั้ง token และย้าย Webhook URL ของ LINE ด้วย `use-cloudflare.bat` ที่โฟลเดอร์หลัก (ทดสอบก่อนเปลี่ยนเสมอ)

> ก่อนหน้านั้นใช้ Tailscale Funnel (`tailscale funnel --bg --set-path=/webhook 8000`) ซึ่งไม่จำค่าข้ามการรีบูต
> และเคยค้างเงียบ — ขั้นตอนเดิมอยู่ที่ `LINE_SETUP.md` §3 / §3.1 เก็บไว้เป็นทางสำรอง

ตอน dev บนเครื่องที่ไม่มี Tailscale จะใช้ `cloudflared tunnel --url http://localhost:8000` ก็ได้
แต่อย่าเอามาใช้กับเครื่องที่ใช้งานจริง

### 2. ตั้งค่าใน LINE Developers Console

ไปที่ <https://developers.line.biz/console/> เลือก channel แล้วตั้งตามนี้:

| หัวข้อ | ค่าที่ต้องตั้ง |
|---|---|
| Messaging API → Webhook URL | `https://<ชื่อเครื่อง>.<tailnet>.ts.net/webhook` |
| Messaging API → Use webhook | **เปิด** |
| Messaging API → Auto-reply messages | **ปิด** (ไม่งั้นจะตอบซ้อนกับบอท) |
| Messaging API → Greeting messages | ปิด ถ้าจะให้บอทจัดการเอง หรือดูข้อ 3 |

กด **Verify** ข้างช่อง Webhook URL — ต้องขึ้น Success (service มี endpoint `GET /webhook` รองรับไว้แล้ว)

### 3. ข้อความต้อนรับ (Greeting message)

ในรูปต้นแบบ บับเบิลแรกมาจาก Greeting message ที่ตั้งใน LINE Official Account Manager
(<https://manager.line.biz/>) → Auto-responses → Greeting messages วางข้อความนี้:

```
สวัสดีครับ 👋 ยินดีต้อนรับสู่ระบบแจ้งปัญหา IT

กดปุ่ม "แจ้งเรื่องใหม่" เพื่อเลือกบริษัทและสาขาได้เลยครับ
หรือพิมพ์ชื่อสาขามาตรงๆ ก็ได้ เช่น: ภูเก็ต, สำนักงานใหญ่, ลาดพร้าว

📋 บริการที่รองรับ:
🖊 แจ้งซ่อมอุปกรณ์
📦 เบิกอุปกรณ์
🔄 คืนอุปกรณ์
```

บับเบิลที่สอง (ที่ทักชื่อผู้ใช้ พร้อมปุ่มเมนู) บอทเป็นคนส่งจาก follow event เอง ไม่ต้องตั้งอะไร

> ถ้าไม่อยากตั้ง Greeting message ก็ข้ามได้ บอทจะทักเองอยู่แล้ว แค่จะไม่มีบับเบิลแรก

## บทสนทนาที่รองรับ

### แจ้งเรื่อง (ได้ ticket จริงเข้าระบบ)

```
เลือกบริษัท → [ถ้าสาขาเยอะ: เลือกกลุ่ม/ทีม] → เลือกสาขา → เลือกประเภท
            → ใส่รหัสทรัพย์สิน → [ถ้าเบิก: เลือกของ + จำนวน]
            → ผู้แจ้ง (ถามครั้งเดียวต่อบัญชี) → รายละเอียด → ได้เลขที่ ticket
            [ถ้าเบิก: จบทันทีหลังยืนยันผู้เบิก ไม่มีขั้นรายละเอียด]
```

**เมนูสาขาแบ่งหน้า (หน้าละ 8) + พิมพ์ชื่อเขตได้ (13 ต.ค. 2026)** — ปุ่ม "▼ ดูเพิ่ม" ของเมนูสาขาส่ง `a=bk_page&l=<ชั้น>&p=<หน้า>` (เดิมส่ง `a=pk_page` ของเมนูทรัพย์สิน กดหน้า 2 แล้วได้ "ดึงรายการทรัพย์สินไม่ได้") · การ์ดเก่าที่ยังส่ง `pk_page` ระหว่างเลือกสาขา บอทพาไปหน้าถัดไปของเมนูสาขาให้ · พิมพ์ชื่อเขต/AM ("ใบตอง", "น้องใบตอง", "ทีมปอ New") เปิดรายชื่อสาขาของเขตนั้นทันที — ตรงทั้งคำเท่านั้น และชื่อสาขาที่ตรงเป๊ะชนะชื่อเขตเสมอ (`flow._match_area`, เทสต์ `tests/test_branch_paging.py`)

**เบิกต้องระบุอุปกรณ์อย่างน้อย 1 รายการ (13 ต.ค. 2026)** — ชื่อที่พิมพ์เองต้องบอกว่าของอะไร: "อุปกรณ์" · "ของ" · ตัวเลขล้วน ·
ป้ายปุ่มเมนู ถูกถามใหม่พร้อมปุ่มของในสต็อก (`flow._clean_item_name`) · พิมพ์ "ขอเบิกเมาส์ครับ" ได้ชื่อ "เมาส์" · ชื่อที่ตรงของในสต็อกใช้หน่วยนับจริง ·
ขั้นถามเบิกเพิ่มพิมพ์ "พอแล้ว" แทนปุ่มได้ · **ทุกขั้นของการเบิกมีปุ่ม ❌ ยกเลิก**
กดเมนู rich menu แล้วป้ายปุ่ม ("แจ้งซ่อม" ฯลฯ) **ไม่นับเป็นข้อความเล่า** (`initial_message`) — แจ้งซ่อมจึงต้องพิมพ์อาการจริง

ประเภทที่รองรับ: 🖊 แจ้งซ่อม · 📦 เบิกอุปกรณ์ · 🔄 คืนอุปกรณ์ · 🛠 ขอใช้บริการ IT

**rich menu เหลือ 2 ปุ่ม (22 ต.ค. 2026)** — แจ้งซ่อม · ขอใช้บริการ IT แถวเดียว (2500×843) · เบิก/คืนยังเลือกได้ที่ขั้นเลือกประเภท
(📝 แจ้งเรื่องใหม่) และพิมพ์เองได้ · ป้ายของปุ่มที่ถอดออก (`richmenu.RETIRED_BUTTON_TEXTS`) ยังนับเป็นป้ายปุ่มใน `flow.RICH_MENU_TEXTS`
เพราะมือถือที่แคชเมนูเก่ายังส่งมา — ถอดปุ่มไหนอีกให้ย้ายป้ายไปไว้ที่นั่นด้วย

พิมพ์ `ยกเลิก` ออกจากขั้นตอนได้ทุกเมื่อ และบทสนทนาที่ค้างเกิน 30 นาทีจะหมดอายุเอง

**เลือกบริษัทก่อนสาขาเสมอ** — มี 3 บริษัท: Montipa · Motta · ส่วนกลาง
เพราะชื่อสาขาซ้ำกันข้ามบริษัทได้จริง (ขอนแก่น / ชลบุรี / หาดใหญ่ มีทั้ง 2 บริษัท) ถ้าถามแค่สาขา
ticket จะบอกไม่ได้ว่าต้องส่งช่างของบริษัทไหนไป และรวมกันแล้วมี 102 สาขาซึ่งใส่ปุ่มชุดเดียวไม่พอ
(LINE จำกัด quick reply ที่ 13 ปุ่ม) จึงมีชั้น "เลือกกลุ่ม/ทีม/หน่วยงาน" คั่นก่อน พร้อมปุ่มเลื่อนหน้า

> เงื่อนไขในโค้ดคือ `company == "central"` แบบ hardcode (`flow.py:118`) **ไม่ได้นับจำนวนสาขา**
> ตามที่เอกสารรุ่นก่อนเขียนไว้ · ส่วน Montipa/Motta ไล่ชั้นจาก `BRANCH_DIRECTORY` ตามปกติ

**ผู้แจ้งมาจากทะเบียนพนักงาน 338 คน และถามครั้งเดียว** — ครั้งแรกให้พิมพ์ชื่อจริง/นามสกุล/ชื่อเล่น/รหัสพนักงาน
พอยืนยันแล้วบอทผูกบัญชี LINE เข้ากับพนักงานคนนั้น

> **ปิดเมนู "เลือกจากรายชื่อ" ไว้ชั่วคราว (28 ก.ย. 2026)** — ขั้นนี้ให้พิมพ์ชื่อเอาเองอย่างเดียว
> ธงอยู่ที่ `REQUESTER_PICKER_ENABLED` ใน `app/messages.py` เปิดกลับ = แก้เป็น `True` บรรทัดเดียว
> (คุมทั้งปุ่มในข้อความใหม่ และปุ่มเก่าที่ค้างในห้องแชท ซึ่งกดแล้วจะถอยไปหน้าพิมพ์ชื่อแทน)
ครั้งต่อไปจึงข้ามขั้นนี้ทั้งขั้น ขั้นถามรายละเอียดจะขึ้น `👤 แจ้งในชื่อ: ...` พร้อมปุ่ม "เปลี่ยนคนแจ้ง"

**ยกเว้นการเบิก (30 ก.ย. 2026)** ซึ่งจบทันทีหลังระบุผู้เบิก (`flow._ends_at_requester`) — บัญชีที่ผูกแล้ว
จะเห็นการ์ด "ผู้เบิกคือคนนี้ใช่ไหม" ของคนที่ผูกไว้ กด **✅ ใช่ ฉันเอง** แล้วส่งเรื่องเลย หรือ
**👤 ไม่ใช่ เปลี่ยนคน** เพื่อถอดการผูก — ห้ามข้ามเงียบๆ เพราะการเบิกไม่มีขั้นรายละเอียดให้ปุ่มเปลี่ยนคนไปอยู่แล้ว

ค้นหาทำฝั่งบอทในหน่วยความจำ (ทะเบียนมาในก้อน `knowledge` ที่ cache ไว้ 5 นาที) จึงใช้ `rapidfuzz`
รับคำพิมพ์ผิดได้ และไม่ยิงถามหลังบ้านทุกตัวอักษรที่พิมพ์
คนที่ยังไม่มีชื่อในทะเบียน (พนักงานใหม่) กด "ใช้ชื่อที่พิมพ์" แจ้งต่อได้เลย ไม่ติดตาย

ชื่อเล่นซ้ำกันเยอะในพนักงานสาขา (ปอ/ฝน 6 คน · ครีม 5 คน) จึง (24 ต.ค. 2026 — `ai.find_employees` · `messages.requester_choices`):
ผลทุกคนมีบรรทัด "ฝ่าย · ตำแหน่ง" ใต้ชื่อ (ตำแหน่งพนักงานสาขามีชื่อสาขาอยู่ในตัว) · ชื่อเล่นซ้ำในผลชุดเดียวกัน
ปุ่มใช้ชื่อจริงแทน · ชื่อจริง/นามสกุลที่ตรงทั้งคำนับเป็น "ตรงเป๊ะ" (เดิมพิมพ์ "น้ำฝน" ได้แต่คนชื่อเล่นน้ำฝน
เจ้าของชื่อจริงหาตัวเองไม่เจอ) · `เเ`/`แ` และ `ํา`/`ำ` ถือเป็นตัวเดียวกันตอนค้น

**ชื่อสาขาถูกตรวจกับข้อมูลจริงในระบบ** ถ้าพิมพ์สาขาที่ไม่มีจะถูกปฏิเสธ (เหมือนต้นแบบ)
แต่ยอมให้พิมพ์ผิดเล็กน้อยได้ เช่น `สำนักงานใหย่` → จับเป็น `สำนักงานใหญ่` ให้อัตโนมัติ
ถ้าเลือกบริษัทไว้แล้ว การค้นจะจำกัดเฉพาะสาขาของบริษัทนั้น ซึ่งแม่นขึ้นด้วยเพราะชุดที่เอามาเทียบเล็กลง

พิมพ์ชื่อสาขามาตรงๆ โดยข้ามขั้นตอนเลือกบริษัทได้ ถ้าชื่อสาขานั้นไม่ซ้ำข้ามบริษัท (บอทเติมบริษัทให้เอง)
แต่ถ้าซ้ำ บอทจะถามบริษัทเสมอ ไม่เดาให้ — ticket ที่ระบุบริษัทผิดแย่กว่า ticket ที่ไม่ระบุบริษัท

#### เจ้าหน้าที่รับแชทต่อเอง — หลังบ้านสั่งให้บอทเงียบ (12 ต.ค. 2026)

LINE **ไม่ส่ง webhook ตอนเจ้าหน้าที่ตอบแชทในแอป LINE OA** บอทจึงรู้เองไม่ได้ว่ามีคนคุยอยู่ แล้วตอบแทรก
หน้าแอดมินจึงสั่งผ่าน API ภายในของบอท (ต้องมี header `x-internal-key` = `INTERNAL_API_KEY` ตัวเดียวกับที่บอทใช้เรียกหลังบ้าน):

| เส้น | body | ผล |
| --- | --- | --- |
| `POST /internal/handoff` | `{line_user_id, hours?}` | เริ่มโหมดเจ้าหน้าที่ (ไม่ส่ง hours = `HANDOFF_HOURS`) · Chat ใน OA ปิดอยู่ = 409 `chat_off` |
| `POST /internal/handoff/end` | `{line_user_id}` | คืนให้บอท (ล้าง session เหมือนผู้ใช้กด "กลับไปใช้บอท") — ไม่ได้อยู่ในโหมดนี้ = ไม่แตะอะไร |
| `POST /internal/handoff/status` | `{line_user_id}` | `{active, until, chat_mode}` ให้หน้าเว็บโชว์สถานะ |

- ใช้ POST + body ทุกเส้นโดยตั้งใจ — access log ของ uvicorn พิมพ์ query string ออกมาเต็มๆ
- ไม่เปิดสู่อินเทอร์เน็ต: Cloudflare Tunnel ส่งเข้าบอทเฉพาะ `^/webhook` (ยังตรวจ key ทุกครั้งเผื่อวันที่ย้าย proxy)
- ผู้แจ้งกด "ยังมีปัญหาอยู่" → `flow.py` เข้าโหมดนี้ให้เองหลังเปิดเรื่องกลับสำเร็จ (ถ้า Chat ใน OA เปิดอยู่)
- `/end` เปิดบอทคืนให้คนที่ทีม IT ปิดไว้จากการ์ดด้วย · `/status` ตอบ `bot_off_user` · `bot_off_all` เพิ่ม (13 ต.ค. 2026)

### ทีม IT เปิด/ปิดบอทจากแชท (13 ต.ค. 2026)

```
ทีม IT: ขอสิทธิ์แอดมิน              ← ครั้งแรก — แอดมินกดอนุมัติที่หน้าเว็บ "บอท LINE"
ทีม IT: แอดมิน
บอท  : [การ์ดควบคุมบอท]  บอททั้งระบบ: เปิดอยู่
        Somchai 🐻   🟢 บอทตอบ · ทักล่าสุด 14:05        [ปิดบอท]
        Mook         🔴 ปิดบอทอยู่ · โดย Film เมื่อ 13:00  [เปิดบอท]
        [⛔ ปิดบอททั้งระบบ]  [ถัดไป ▶]
```

- ด่านแรกของทุก event คือ `flow._admin_gate` → `_off_gate` → `_handoff_gate` · สิทธิ์ถาม `POST /api/internal/line-staff` ทุกครั้ง
  (ไม่ cache — ถอดสิทธิ์ในเว็บแล้วการ์ดเก่าใช้ไม่ได้ทันที) · หลังบ้านล่ม = ไม่ใช่ทีม IT · คนทั่วไปพิมพ์ "แอดมิน" = ขอคุยกับเจ้าหน้าที่ตามเดิม
- ปิดอยู่: แจ้ง `bot_off_notice()` วันละครั้ง (`store.once_per_day` ตามวันที่ไทย) แล้วเงียบ · ผู้ใช้เปิดเองไม่ได้ · ปุ่มดาว/เช็คสถานะ/ความเห็นหลังดาวผ่านได้
  · Chat ใน OA ปิด = ไม่มีผล (และสั่งปิดไม่ได้) · ไม่สั่ง "อ่านแล้ว" และไม่โหลดรูปของคนที่บอทเงียบใส่
- เก็บที่ `store.py` (`linebot:ctl:*` บน Redis ไม่มีวันหมดอายุ ยกเว้นตัวนับวันละครั้ง) — แยกจาก session โดยตั้งใจ

API ภายในสำหรับหน้าเว็บ "บอท LINE" (ต้องมี `x-internal-key` · POST ทุกเส้น):

| เส้น | body | ผล |
| --- | --- | --- |
| `POST /internal/bot/status` | `{}` | `{bot_off: {since, by} \| null, users_off: [{line_user_id, name, since, by}], chat_mode}` |
| `POST /internal/bot/global` | `{off, by?}` | ปิด/เปิดทั้งระบบ · ปิดตอน Chat ใน OA ปิด = 409 `chat_off` |
| `POST /internal/bot/user` | `{line_user_id, off, by?}` | ปิด/เปิดรายคน (เปิด = ล้างโหมดคุยกับเจ้าหน้าที่ที่ค้างด้วย) |

`/health` มี `bot_off` · `users_off` เพิ่ม — `deploy.bat` เตือนถ้าปิดทั้งระบบค้างอยู่

## คำทักทาย — สิ่งที่ทำงานจริง กับสิ่งที่ยังไม่ได้ทำ

> **แก้เอกสาร 2026-09-26:** หัวข้อนี้เคยบรรยายฟีเจอร์ทักทายไว้ทั้งชุด (ทักกลับเมื่อพิมพ์คำทักทาย ·
> ต้อนรับกลับหลังหายไปนาน · ข้อความ "ยังไม่เข้าใจ" · ยกเลิกแบบเรียกชื่อ) **ซึ่งไม่มีอยู่ในโค้ดเลย**
> ตรวจด้วยการรัน `flow.handle()` จริงแล้ว — พิมพ์ "สวัสดีครับ" ตอน IDLE ถูกตีความเป็น "ชื่อสาขา"
> เอกสารเดิมจึงถูกเขียนใหม่ให้ตรงกับของจริง และย้ายส่วนที่ยังไม่ได้ทำไปเป็นรายการงานค้าง

### ทำงานจริงตอนนี้

| สถานการณ์ | บอททำอะไร | โค้ด |
| --- | --- | --- |
| กดเพิ่มเพื่อน (follow event) | ทักด้วยชื่อ + การ์ดเมนูแนะนำบริการ | `flow.py` → `M.welcome()` |
| กดปุ่ม/พิมพ์ "ยกเลิก" กลางทาง | `"ยกเลิกรายการแล้วครับ 🙏"` + quick reply เมนู | `M.cancelled()` |
| ขั้นรายละเอียด แล้วไม่มีอะไรจะเพิ่ม | กดปุ่ม **"✅ ไม่มี ส่งเลย"** จบใน 1 คลิก (พิมพ์ `-` ก็ยังได้) | `a=desc_skip` → `flow._finish_description()` |
| เบิกอุปกรณ์ ระบุผู้เบิกเสร็จ | ส่งเรื่องทันที ไม่ถามรายละเอียด · บัญชีที่ผูกแล้วกดยืนยันชื่อครั้งเดียว | `flow._ends_at_requester()` · `_ready_to_submit()` |
| session ทิ้งไว้เกิน 30 นาที | บอกว่าหมดเวลาแล้ว เริ่มใหม่ได้เลย | `M.session_expired()` |

**ข้อความต้อนรับสั้น รายละเอียดอยู่ในการ์ด** — บับเบิลข้อความยาวๆ บนมือถือกินเกือบครึ่งจอ
คนจึงปัดผ่านแล้วไปกดเมนูอยู่ดี รายการบริการจึงอยู่ในการ์ด (flex) ที่แยกเป็นบรรทัดละบริการ
พร้อมไอคอนและปุ่มกดต่อได้ทันที

> ตรวจเมื่อ 2026-09-14: "Greeting message" ของ LINE OA Manager ถูกปิดอยู่ แปลว่าคำแนะนำบริการ
> ที่เคยฝากไว้ตรงนั้นไม่เคยถูกส่งถึงใครเลย จึงย้ายมาอยู่ในข้อความ follow ของบอทเอง
>
> ⚠️ **ห้ามเปิด "Greeting message" ใน OA Manager** ควบคู่กัน ไม่งั้นผู้ใช้ได้ข้อความต้อนรับซ้อน 2 อันตอนแอด

> **ปุ่ม "ไม่มี ส่งเลย" (2026-09-30):** ขั้นรายละเอียดจบได้ด้วยการกด 1 ครั้ง ขั้นตอนยังอยู่สำหรับ
> คืน · ซ่อม · ขอใช้บริการ เพราะปุ่ม "เปลี่ยนคนแจ้ง" ของประเภทเหล่านี้ติดอยู่กับข้อความของขั้นนี้
> (การเบิกย้ายปุ่มนั้นไปอยู่บนการ์ดยืนยันผู้เบิกแล้ว และไม่มีขั้นนี้อีก) · ปุ่มข้ามโผล่เฉพาะตอนที่
> `flow._can_skip_description()` เป็นจริง (เบิก/คืน เสมอ · ซ่อม/ขอใช้บริการ เฉพาะตอนมี `initial_message`)
> — เงื่อนไขนี้ต้องตรงกับที่ handler ยอมรับเสมอ มีเทสต์ผูกไว้แล้ว

### ยังไม่ได้ทำ (มีโค้ดค้างไว้บางส่วน — อย่าเชื่อว่ามันทำงาน)

| สิ่งที่ยังไม่มี | หลักฐาน |
| --- | --- |
| พิมพ์คำทักทายล้วนๆ แล้วบอททักกลับ | `ai.is_greeting()` เขียนไว้แล้วแต่ **ไม่มีใครเรียก** — ข้อความแรกที่ไม่เข้า intent ยังถูกตีความเป็น "ชื่อสาขา" |
| ทักต้อนรับกลับหลังหายไปนาน | `welcome_back_days` อยู่ใน `config.py` และถูกส่งออกที่ `/health` แต่ **ไม่มีโค้ดไหนใช้ค่านี้** |
| ข้อความ "ยังไม่เข้าใจข้อความนี้" | ไม่มีข้อความนี้ใน `messages.py` |
| ยกเลิกแล้วเรียกชื่อ + ถามว่าจะแจ้งอะไรต่อไหม | `M.cancelled()` คืนข้อความคงที่ ไม่มีชื่อ |
| เก็บ "เห็นครั้งล่าสุด" ที่ `linebot:seen:*` | key นี้ไม่มีในโค้ด (มีแค่ `linebot:session:` · `linebot:rate:` · `linebot:event:` · `linebot:event-lock:`) |

**ทำไมยังควรทำ** — คนที่พิมพ์ "สวัสดีครับ" แล้วได้คำตอบเรื่องสาขา จะเข้าใจว่าระบบพัง
และนี่คือจุดที่คนออกจากแชทไปเลยมากที่สุด เช่นเดียวกับการยกเลิกแล้วจบห้วนๆ
(คนกดยกเลิกส่วนใหญ่ไม่ได้เลิกอยากแจ้ง แต่กรอกผิดขั้นตอนแล้วอยากเริ่มใหม่)

**ข้อควรระวังตอนทำ** — `is_greeting()` ต้องจำกัดความยาวข้อความด้วย ไม่ใช่ดูแค่ว่ามีคำทักทายอยู่ไหม
ไม่งั้น "สวัสดีครับ คอมเปิดไม่ติด" จะถูกตัดจบแค่ทักทาย แล้วคนต้องพิมพ์เรื่องเดิมซ้ำอีกรอบ ·
"เห็นครั้งล่าสุด" ต้องเก็บแยกจาก session (session อายุ 30 นาทีและถูกล้างทุกครั้งที่แจ้งเรื่องจบ
ถ้าใช้ session ตัดสิน ทุกคนจะกลายเป็น "คนที่หายไปนาน" ตลอดเวลา) ·
และถ้า Redis ล่ม ต้องถือว่า "ไม่ต้องทัก" ไม่ใช่ทำให้ผู้ใช้ไม่ได้คำตอบ

| `a=confirm&code=<เลขที่>&v=0` "ยังมีปัญหาอยู่" | `POST /api/internal/tickets/confirm` (`reject`) → เรื่องกลับเป็นรอดำเนินการ + ทีม IT ได้แจ้งเตือน → บอทเข้าโหมดเจ้าหน้าที่ให้ (`still_broken_ack(handed_off=True)`) |
| `a=confirm&code=<เลขที่>&v=1` (การ์ดรุ่นเก่า) | ปิดงานเหมือนเดิม → `confirm_done_thanks()` แนบปุ่มดาว 1–5 ให้คะแนนต่อ |

**บอทไม่ตัดสินใจอะไรเอง** — เกณฑ์ "คะแนนต่ำ" (1–3) · ใครกดได้ (เจ้าของเรื่องเท่านั้น) · เปิดกลับได้ภายในกี่วัน
อยู่ที่หลังบ้านทั้งหมด บอทแค่แปลผลเป็นข้อความ:

| ผลจากหลังบ้าน | บอทตอบ |
|---|---|
| `not_owner` (403) | `confirm_not_owner()` — ปุ่มนี้กดได้เฉพาะคนที่แจ้งเรื่อง |
| `not_completed` (กดดาวหลังเปิดเรื่องกลับไปแล้ว) | `rate_not_completed()` + สถานะล่าสุด |
| `reopen_expired` (ปิดงานเกิน 14 วัน) | `reopen_expired()` — ให้แจ้งเรื่องใหม่แล้วอ้างเลขที่เดิม |
| `not_resolved` ตอนกดยังมีปัญหาซ้ำ | `reopen_not_possible()` — "ไม่ต้องกดซ้ำ" + สถานะล่าสุด |
| `not_resolved` ตอนกดเรียบร้อยแล้ว (การ์ดเก่า) | `confirm_not_resolved()` |
| เชื่อมต่อไม่ได้ | `backend_error()` (ความเห็น: `rate_comment_failed()` และยังรอความเห็นอยู่ พิมพ์ส่งใหม่ได้เลย) |

กรณีที่ตั้งใจออกแบบไว้:

- กดดาว/ปุ่มได้แม้ session หมดอายุ — การ์ดเด้งมาตอนผู้ใช้ไม่ได้เปิดแชท กว่าจะกดอาจผ่านไปหลายชั่วโมง
- กดดาวระหว่างกรอกเรื่องใหม่ค้างอยู่ → **ไม่ถามความเห็น** (ไม่ยึด session) ขอบคุณแล้วพากลับคำถามเดิม
- กดดาวระหว่างคุยกับเจ้าหน้าที่ → ได้คำตอบแต่ยังคุยกับเจ้าหน้าที่ต่อ (`rate`/`rate_skip` อยู่ใน `_HANDOFF_PASSTHROUGH`)
- ขั้น `RATE_COMMENT`: กดปุ่ม rich menu = เปลี่ยนเรื่อง ไม่ใช่ความเห็น · ส่งรูป = เริ่มแจ้งเรื่องใหม่
- ความเห็นตัดที่ 500 ตัวแบบนับ UTF-16 (`_clip_utf16`) ให้ตรงกับหลังบ้าน — อีโมจิ 1 ตัวนับ 2

## ชั้น AI ทำงานอย่างไร

| ชั้น | เทคโนโลยี | ใช้ทำอะไร | ค่าใช้จ่าย |
|---|---|---|---|
| 1 | PyThaiNLP (`newmm`) | ตัดคำไทย — ภาษาไทยไม่มีเว้นวรรค ถ้าไม่ตัดคำ การค้นหาจะพังหมด | ฟรี |

| 4 | LLM ผ่าน API *(ปิดไว้)* | เรียบเรียงคำตอบจาก FAQ ให้เป็นภาษาคน (RAG) | ต่อครั้ง |

**ทำไมไม่ใช้ scikit-learn / sentence-transformers**

TF-IDF เขียนเองราว 40 บรรทัด ได้ผลดีพอกับ FAQ ระดับหลักสิบ–หลักพันรายการ
แต่ประหยัดขนาด deploy หลายสิบ MB และ cold start เร็วกว่ามาก
ถ้าวันหนึ่ง FAQ โตเป็นหลักหมื่นค่อยย้ายไป embedding + vector database

**ทำไมจับ intent ด้วยคีย์เวิร์ดไม่ใช่โมเดล**

เพราะแก้ได้ เวลาบอทเดาผิดแค่เพิ่มคำใน `INTENT_KEYWORDS` ใน `app/ai.py` แล้วรีสตาร์ท
ถ้าใช้โมเดลกล่องดำ พอเดาผิดจะทำอะไรไม่ได้นอกจากเทรนใหม่ ซึ่งไม่คุ้มกับงานระดับนี้

**เปิดชั้น LLM (ไม่บังคับ)**

```env
AI_PROVIDER=anthropic        # หรือ openai
AI_API_KEY=sk-...
AI_MODEL=claude-3-5-haiku-latest
```

เมื่อเปิด LLM จะถูกบังคับให้ตอบจากเนื้อหา FAQ ที่ค้นเจอเท่านั้น (RAG) ถ้าข้อมูลไม่พอให้ตอบว่าไม่ทราบ
ไม่งั้นมันจะแต่งวิธีแก้ปัญหา IT ที่ไม่มีอยู่จริงในองค์กรขึ้นมาเอง ซึ่งอันตรายกว่าการตอบว่าไม่รู้
ถ้าเรียก LLM ไม่สำเร็จ บอทจะตกกลับไปใช้คำตอบดิบจาก FAQ อัตโนมัติ ไม่พังทั้งบทสนทนา

## สิ่งที่ต้องทำก่อนขึ้นใช้งานจริง (ติเพื่อก่อ)

1. **เปลี่ยน state store เป็น Redis** — ค่าตั้งต้นเก็บในหน่วยความจำ พอรีสตาร์ทบทสนทนาที่ค้างจะหาย
   และถ้ารันหลาย worker แต่ละตัวจะเห็น state คนละชุด ผู้ใช้จะเจออาการ "บอทลืมว่าคุยถึงไหน"
   ใส่ `REDIS_URL` แล้วจบ ไม่ต้องแก้โค้ด

2. **ปิด `/api/internal/*` ไม่ให้เข้าถึงจากอินเทอร์เน็ตตรงๆ** — ตอนนี้กันด้วย API key อย่างเดียว
   ถ้าเป็นไปได้ควรอยู่หลัง firewall หรือจำกัด IP ของ bot service เพิ่มอีกชั้น

3. ~~**ยังไม่มี rate limit**~~ — ✅ **ทำแล้ว** จำกัดต่อ `userId` ผ่าน `RATE_LIMIT_PER_MINUTE`
   (ค่าตั้งต้น 20 ครั้ง/นาที, ตั้ง 0 เพื่อปิด) ใช้ Redis เป็นตัวนับเมื่อมี `REDIS_URL`
   เกินลิมิตครั้งแรกบอทตอบเตือน 1 ครั้ง ครั้งต่อไปในนาทีเดียวกันเงียบ — ไม่ให้บอทกลายเป็นตัวขยายสแปมเอง
   ถ้าตัวนับพัง (Redis ล่ม) จะปล่อยผ่าน ไม่ทำให้บอททั้งตัวใช้ไม่ได้

4. **ประมวลผลแบบ inline** — ตอนนี้ตอบ 200 กลับให้ LINE หลังทำงานเสร็จ ซึ่งพอสำหรับปริมาณปกติ
   ถ้าโหลดสูงควรเปลี่ยนเป็น ack ทันทีแล้วโยนงานเข้า queue (เช่น Redis Queue / Celery)

5. **FAQ ค้นไม่เจอบางคำ** — เช่น "เครื่องพิมพ์กระดาษติด" ยังไม่แมตช์กับ FAQ "ปริ้นเอกสารไม่ได้"
   เพราะคำว่า "เครื่องพิมพ์" ไม่ได้อยู่ในคีย์เวิร์ดของ FAQ นั้น
   แก้ที่หน้า FAQ Bot ในแอดมิน โดยเพิ่มคำพ้องเข้าไปในคีย์เวิร์ด — ไม่ต้องแก้โค้ด

6. ~~**ยังไม่รองรับรูป/สติกเกอร์/ไฟล์**~~ — ✅ **ทำแล้วบางส่วน**
   - **รูป**: รับแล้วแนบเข้า ticket อัตโนมัติ (ดูหัวข้อ "รูปที่ผู้ใช้ส่งมา" ด้านล่าง)
   - **สติกเกอร์/วิดีโอ/ไฟล์/เสียง**: ยังอ่านไม่ได้ แต่ตอนนี้ **ตอบกลับว่าอ่านไม่ได้** แทนที่จะเงียบ
     (การเงียบทำให้ผู้ใช้แยกไม่ออกว่าบอทไม่รองรับหรือบอทล่ม ซึ่งทำให้เลิกใช้เร็วกว่าเดิม)

## รูปที่ผู้ใช้ส่งมา

ภาพหน้าจอที่ error คือสิ่งแรกที่คนส่งเวลาเจอปัญหา IT บอทจึงรับรูปแล้วแนบเข้า ticket ให้เลย

**เส้นทางของไฟล์:**

```
ผู้ใช้ส่งรูป
  -> main.py ดาวน์โหลดจาก LINE Content API (api-data.line.me) แบบ stream
  -> ตัดจบทันทีถ้าเกิน MAX_IMAGE_BYTES (ไม่รอโหลดจบแล้วค่อยเช็ค)
  -> อัปโหลดต่อไปที่ POST /api/internal/attachments ของ Next.js
  -> ได้ URL กลับมา เก็บไว้ใน session
  -> ตอนสร้าง ticket ส่งไปเป็น image_urls -> เก็บใน meta -> แสดงในหน้า /tickets
```

**พฤติกรรมที่ออกแบบไว้:**

| สถานการณ์ | บอททำอะไร |
| --- | --- |
| ส่งรูปตอนยังไม่ได้เริ่มแจ้งเรื่อง | เก็บรูปไว้แล้ว**เปิด flow ให้เลย** ไม่ต้องส่งรูปซ้ำ |
| ส่งรูประหว่างแจ้งเรื่อง | แนบเพิ่ม + **ถามคำถามของ step เดิมซ้ำ** ไม่ให้ผู้ใช้ค้าง |
| เกิน `MAX_IMAGES_PER_TICKET` | บอกตรงๆ ว่าแนบได้กี่รูป |
| รูปใหญ่เกิน / โหลดไม่สำเร็จ | บอกเหตุผล แล้วให้แจ้งเรื่องต่อได้โดยพิมพ์อธิบายแทน |

ทำไมการดาวน์โหลดอยู่ใน `main.py` ไม่ใช่ `flow.py`: LINE เก็บไฟล์ให้ดาวน์โหลดได้ระยะเวลาจำกัด
ถ้ารอไปทำทีหลังจะได้ 404 — และ `flow.py` ตั้งใจออกแบบไม่ให้รู้จัก LINE API เลย เพื่อให้เทสต์บทสนทนา
ได้โดยไม่ต้องมี token (ดู `tests/test_flow.py`)

## รหัสทรัพย์สินที่ซ้ำกัน

ข้อมูลจริงมี **28 แถวที่ใช้รหัสซ้ำกับเครื่องอื่น** (เช่น `PC2306001` ถูกใช้กับ 4 เครื่องคนละสาขา —
ดู `db/imports/equipment-import-conflicts.csv`)

เดิมระบบคืนเครื่องแรกที่เจอเงียบๆ แปลว่า ticket อาจผูกกับเครื่องผิดสาขาโดยไม่มีใครรู้จนช่างไปถึงหน้างาน

ตอนนี้ `GET /api/internal/lookup?kind=equipment` คืน `matches` ครบทุกเครื่อง และบอทจะ**ให้ผู้ใช้เลือก**
พร้อมแสดงสถานที่/ผู้ถือครองกำกับ (เพราะรหัสอย่างเดียวแยกไม่ออก)

เมื่อเลือกแล้วบอทส่ง **`equipment_id`** ไปกับ ticket ด้วย ไม่ใช่แค่ `asset_code` —
ไม่งั้นการอุตส่าห์ถามว่า "เครื่องไหน" จะเสียเปล่า เพราะหลังบ้านได้รหัสที่กำกวมไปแล้วต้องเดาเองอยู่ดี

ทุกทางเข้าที่ผูกเครื่อง (พิมพ์รหัสเอง · ไล่เมนูประเภท→ยี่ห้อ→รหัส · AI จับรหัสจากประโยคแรก)
เรียกตัวผูกเครื่องตัวเดียวกันใน `flow.py` จึงถามเรื่องรหัสซ้ำเหมือนกันทั้งหมด
(เดิมทาง AI เดาจาก knowledge cache ตรงๆ รหัสที่ซ้ำ 4 เครื่องจึงถูกรับเงียบๆ เฉพาะทางนั้นทางเดียว)

⚠️ นี่เป็นการลดความเสียหาย ไม่ใช่การแก้ต้นเหตุ — **รหัสซ้ำยังควรแก้ที่ข้อมูลต้นทาง**

## กดส่งซ้ำแล้วต้องไม่ได้ ticket 2 ใบ

ตอนส่งไม่สำเร็จ บอทเก็บ session ไว้ให้กดปุ่ม "🔁 ลองส่งใหม่" ได้ ไม่ต้องกรอกใหม่ทั้งหมด
แต่ **"บอทส่งไม่สำเร็จ" ไม่ได้แปลว่าหลังบ้านไม่ได้สร้าง ticket** — timeout หลังจากเขียนข้อมูลลงไปแล้ว
เป็นเคสคลาสสิก ถ้ากดส่งซ้ำแล้วยิงเข้าไปเฉยๆ จะได้ ticket 2 ใบและตัดสต็อกซ้ำ 2 รอบ

แต่ละ session จึงมี `request_id` ของตัวเอง (สร้างตอนเปิดเรื่อง คงเดิมตลอดแม้ session ถูกเก็บลง Redis
แล้วอ่านกลับมา) ส่งไปกับทุกครั้งที่ยิงสร้าง ticket หลังบ้านเจอ `request_id` ซ้ำจะ**คืน ticket เดิม**
แทนการสร้างใหม่ ผู้ใช้จึงเห็นเลขที่เดิม ไม่ใช่เลขใหม่ที่ทำให้สับสนว่าตกลงแจ้งไปกี่เรื่อง

ปุ่มนี้ทำงานเฉพาะตอนอยู่ในสถานะ `RETRY_SUBMIT` เท่านั้น — ผู้ใช้เลื่อนขึ้นไปกดปุ่มเก่าที่ค้างบนจอ
ระหว่างกรอกเรื่องใหม่ได้ ถ้าไม่ดักจะได้ ticket ที่ไม่มีผู้แจ้ง ไม่มีรายละเอียด และตัดสต็อกโดยไม่มีรายการ

### 3 ฟิลด์ที่ติดไปกับทุก ticket (ทำเสร็จ 26 ก.ย. 2026)

| ฟิลด์ | มาจากไหน | ถ้าไม่มีจะเป็นยังไง |
| --- | --- | --- |
| `request_id` | เกิดพร้อม `Session` คงเดิมตลอดแม้ผ่าน Redis | กด "ลองส่งใหม่" ได้ ticket ใบที่ 2 + ตัดสต็อกซ้ำ |
| `initial_message` | ข้อความแรกที่ผู้ใช้พิมพ์มาเอง | ข้อมูลที่ดีที่สุดที่เคยมีหายตั้งแต่บับเบิลแรก เหลือแค่ค่าที่ AI แกะได้ |
| `equipment_id` | เครื่องที่ผูกแล้วจริง ไม่ใช่รหัสที่พิมพ์ | รหัสซ้ำกัน 28 แถว หลังบ้านต้องเดา → ticket ผูกผิดเครื่อง/ผิดสาขา |

จุดที่เคยพลาดและแก้แล้ว: ทางที่ **AI จับรหัสจากประโยคแรก** เคยตั้ง `asset_code`/`asset_label` เอง
จาก cache แล้วเดินต่อเลย ซึ่งข้ามการถาม "เครื่องไหน" ตอนรหัสซ้ำไปเงียบๆ
ตอนนี้ทุกทางเข้า (พิมพ์รหัสเอง / ไล่เมนู / AI) ผ่าน `_resolve_asset_code` ตัวเดียวกันหมด

ผลพลอยได้: มี `initial_message` แล้วบอท**ไม่บังคับให้พิมพ์รายละเอียดซ้ำ** — คนที่พิมพ์
"NB2501001 เปิดไม่ติด" มาตั้งแต่แรกแล้วตอบ "ไม่มี" ตอนถามรายละเอียด ผ่านได้เลย
(เดิมถูกถามวนอยู่ตรงนั้นทั้งที่บอกไปครบแล้ว) ส่วนคนที่เปิดเรื่องจากการกดปุ่มโดยไม่เคยเล่าอะไร
ยังถูกบังคับเหมือนเดิม

## โครงสร้างไฟล์

```
line-bot-python/
├── app/
│   ├── main.py        FastAPI + webhook endpoint + /health (ไม่มี logic บทสนทนา)
│   ├── flow.py        state machine ของบทสนทนา ← หัวใจของระบบ
│   ├── messages.py    ข้อความไทยและปุ่มทั้งหมด ← แก้คำพูดที่นี่
│   ├── flex.py        การ์ด Flex + picker() ที่เมนูไล่ชั้นทุกตัวใช้ร่วมกัน
│   ├── ai.py          ตัดคำไทย, TF-IDF, จับ intent/slot, ชั้น LLM
│   ├── thai_text.py   ตัดคำ/normalize ภาษาไทย
│   ├── backend.py     client ไปยัง /api/internal/* ของ Next.js
│   ├── store.py       เก็บ state (memory / Redis)
│   ├── events.py      กัน event ซ้ำ + ล็อกต่อผู้ใช้ (⚠️ main.py ยังไม่ import)
│   ├── richmenu.py    ติดตั้ง rich menu ตอนสตาร์ท แบบ idempotent
│   ├── line_api.py    ห่อ line-bot-sdk v3
│   └── config.py      อ่าน env + validate ตอน startup
└── tests/             453 เคส
    ├── test_flow.py       บทสนทนาทั้งเส้น
    ├── test_ai.py         ชั้น AI และการตอบจากข้อมูล
    ├── test_requester.py  ขั้นตอนระบุผู้แจ้ง
    ├── test_intake.py     idempotency + ข้อมูลที่ต้องติดไปกับ ticket
    ├── test_richmenu.py   ติดตั้ง rich menu กับเซิร์ฟเวอร์จำลอง LINE API
    ├── test_flex.py       การ์ด Flex
    ├── test_main.py       webhook + /health
    ├── test_handoff.py    คุยกับเจ้าหน้าที่ (บอทเงียบ/กลับมา) + สั่งอ่านแล้ว
    ├── test_takeover.py   หลังบ้านสั่งบอทเงียบ (POST /internal/handoff)
    ├── test_bot_control.py  ทีม IT เปิด/ปิดบอทจากแชท ("แอดมิน") + API /internal/bot/*
    ├── test_withdraw_items.py  เบิกต้องระบุอุปกรณ์ + ปุ่มยกเลิกทุกขั้น
    ├── test_branch_paging.py  เมนูสาขาแบ่งหน้า (ปุ่มดูเพิ่ม bk_page) + พิมพ์ชื่อเขต/AM
    ├── test_rating.py     ให้คะแนนหลังปิดงาน + ยังมีปัญหาอยู่
    ├── conftest.py        แชร์ fixture "bot" (แอปตัวจริง) จาก test_handoff ให้ไฟล์อื่นใช้
    ├── test_thai_text.py  ตัดคำไทย
    └── e2e/               ทดสอบจริงผ่าน HTTP ทั้งระบบ (48 จุดตรวจ)
```

จุดที่ควรแก้บ่อยที่สุดคือ `messages.py` (คำพูด) และ `ai.py` (คีย์เวิร์ดจับ intent)
ส่วน `flow.py` แก้เมื่อจะเพิ่ม/ลดขั้นตอนของบทสนทนาเท่านั้น
