## 1. ระบบนี้คืออะไร

ระบบจองคิว **สวัสดิการนวดผ่อนคลายสำหรับพนักงาน** ของ 2 บริษัทในเครือ คือบริษัท แอ็ท เฟเวอริท จำกัด (ATF · แบรนด์ Motta)
และบริษัท มนทิพาดีไซน์ จำกัด (MTP · แบรนด์ Montipa) ทำตามประกาศฝ่ายทรัพยากรบุคคล ลงวันที่ 14 ก.ย. 2569
เริ่มให้บริการ **30 ก.ย. 2569**

| หัวข้อ | ค่า |
|--------|-----|
| ผู้ใช้ | พนักงาน 326 คน (ATF 229 · MTP 89 · ไม่ระบุบริษัท 8) · HR ที่ใช้หลังบ้าน |
| บริการ | นวดผ่อนคลาย 15 นาที ฟรี (รหัส `RELAX15`) |
| ผู้ให้บริการ | 1 คน เป็นผู้พิการทางสายตา (รหัส `M01`) |
| วัน/เวลา | ทุกวันพุธ 09:00–12:00 และ 13:00–17:00 |
| ความจุ | 21 คน/วัน (เช้า 9 · บ่าย 12) |
| ทางเข้าหลัก | **LINE Login** + ผูกรหัสพนักงานกับรายชื่อ HR (อีเมลบริษัทเป็นทางสำรองช่วงเปลี่ยนผ่าน) |
| แจ้งเตือน | **LINE OA** (push) · อีเมลเฉพาะบัญชีที่ยังไม่ผูก LINE |
| ขึ้นระบบที่ | Windows Server ในบริษัท · Docker Compose · เปิดออกอินเทอร์เน็ตด้วย ngrok (static domain) |

**ที่มา:** โปรเจ็คเริ่มจากระบบจองคิวร้านนวดเชิงพาณิชย์ (5 บริการ 3 หมอนวด เปิดทุกวัน) แล้วเปลี่ยนทิศทาง 3 รอบ
จนเป็นระบบสวัสดิการพนักงาน ชื่อตาราง `customers` จึงยังหมายถึง "พนักงาน" (ตั้งใจไม่เปลี่ยนชื่อ เพราะถูกอ้างถึงทุกที่)

## 4. สถาปัตยกรรม

### 4.1 ภาพรวมการทำงาน

```
พนักงาน (มือถือ) ──https──► ngrok ──► api (FastAPI + เสิร์ฟหน้าเว็บ React) ──► PostgreSQL
                                          ▲        │ เขียนแถวลง outbox (notifications)
LINE Platform ◄── push / Login ───────────┤        ▼
LINE Platform ── webhook (ลายเซ็น) ───────┘      worker (ทุก 60 วินาที)
                                                   ├─ ส่งแจ้งเตือน LINE / อีเมล (retry key)
HR (หลังบ้าน /admin) ── คุกกี้ SameSite=Strict ──►  ├─ ตัดสิทธิ์ผู้ไม่มาตามนัด
                                                   ├─ เตือน HR ให้โพสต์รายชื่อในห้อง LINE
                                                   └─ ลบโทเคน/เซสชันที่หมดอายุ
                                                 backup (pg_dump รายวัน 20:00 เก็บ 14 วัน)
```

### 4.2 หัวใจของระบบ: ให้ฐานข้อมูลเป็นคนตัดสิน

ปัญหาหลักของระบบจองคิวคือ **race condition**: สองคนเห็นรอบว่างพร้อมกันแล้วกดจองพร้อมกัน
ช่องว่างระหว่าง `SELECT` กับ `INSERT` ปิดด้วยโค้ดแอปไม่ได้ ระบบนี้จึงใช้ด่านระดับฐานข้อมูล 2 ด่าน:

```sql
-- ด่าน 1: 2 คนห้ามได้รอบเดียวกัน
ALTER TABLE bookings ADD CONSTRAINT bookings_no_overlap
  EXCLUDE USING gist (therapist_id WITH =, slot WITH &&)
  WHERE (status IN ('pending','confirmed'));

-- ด่าน 2: 1 คนห้ามใช้สิทธิ์เกิน 1 ครั้ง/เดือน
CREATE UNIQUE INDEX uq_bookings_monthly_quota
  ON bookings (customer_id, quota_month)
  WHERE status IN ('pending','confirmed','completed','no_show');
```

- ทั้งคู่เป็น **partial index** → ยกเลิกคิว (`cancelled`) แล้วคืนรอบและสิทธิ์ให้อัตโนมัติ
- `quota_month` เป็น generated column นับ **เดือนตามเวลาไทย** ด้วย `timezone(INTERVAL '+07:00', starts_at)`
  (ต้องเป็นฟังก์ชัน IMMUTABLE — ใช้ชื่อโซน `'Asia/Bangkok'` ไม่ได้)
- กันได้จริงแม้มี API หลาย worker/หลายเครื่อง · พิสูจน์ด้วยเทสต์ยิงพร้อมกัน 10 คำขอ ได้คิวเดียว
- Postgres ตรวจ EXCLUDE ก่อน unique index → การ retry ด้วย idempotency key ต้องถามกลับทุกจุดที่จะตอบว่าจองไม่ได้
  (2 จุดใน `booking.py` · ตัวแปร `_RETRYABLE_CONFLICTS`)

### 4.3 การคำนวณรอบว่าง

```
ช่วงว่าง = (เวลาให้บริการ ∩ กะผู้ให้บริการ) − วันงด − วันลา − คิวที่จองแล้ว
           ตัดทั้งวันถ้าก่อน service_start_date หรือ service_days.is_cancelled
```

รอบ 21 รอบเกิดเองจาก `slot_interval=20` + `duration=15` + เวลาให้บริการ 2 ช่วง
HR ขยายเวลาเมื่อไร ระบบคำนวณรอบใหม่ให้เอง · หน้าเว็บอ่านความจุจาก `/settings → daily_capacity` ไม่ hardcode 21
กฎที่ทำให้ "ทั้งวันจองไม่ได้" ต้องอยู่ใน `AvailabilityService._work_windows()` เท่านั้น (ตัวเดียวที่หน้าจอกับการตรวจก่อนบันทึกใช้ร่วมกัน)

### 4.4 การแจ้งเตือนแบบ outbox

- การจอง/ยกเลิก/เลื่อนเขียนแถวลง `notifications` ใน transaction เดียวกับคิว — **ไม่ส่งข้อความใน transaction**
- worker เลือกช่องทางตอนเข้าคิว (`notify_target()`: LINE ถ้าผูกแล้ว ไม่งั้นอีเมล) · 1 แถวต่อ (คิว, ชนิด)
- LINE push ใช้ `X-Line-Retry-Key` คงที่ต่อแถว → worker ล่มหลังส่งแล้วส่งซ้ำ LINE ก็ไม่ส่งซ้ำ (409 = ส่งแล้ว)
- ลองใหม่ 1-2-4-8-16 นาที สูงสุด 6 ครั้ง · ไม่ส่งหลังเลยเวลานัด
- ชนิดข้อความ: ยืนยันจอง · เตือน 24 ชม./2 ชม. · ยกเลิก · เลื่อนรอบ · สถานที่เปลี่ยน
- ข้อยกเว้นเดียว: อีเมลลิงก์เข้าระบบส่งตรง (พนักงานรอหน้าจออยู่)

## 8. LINE: เข้าสู่ระบบ แจ้งเตือน และห้องประกาศ

| ส่วน | สถานะ |
|------|-------|
| LINE OA + Messaging API | ✅ ต่อกับ Server จริงแล้ว (Verify webhook ผ่าน) |
| LINE Login channel | ✅ ตั้งค่าแล้ว · ⬜ **ยังไม่ Publish** (ตอนนี้เข้าได้เฉพาะ Admin/Tester) |
| ผูกรหัสพนักงาน | ✅ รหัสอย่างเดียว (ผู้ใช้เลือก 25 ก.ย. หลังรับทราบความเสี่ยง) |
| ห้องประกาศ OpenChat | ระบบร่างข้อความ · HR คัดลอกไปโพสต์เอง (LINE ไม่มี API ส่งเข้า OpenChat) |

**ด่านผูกรหัส (ห้ามคลาย):** นับทุกครั้งที่ค้น (5 ครั้ง/โทเคน · 10 ครั้ง/ชม./บัญชี LINE) · ตอบเฉพาะชื่อย่อ ·
ผูกได้เฉพาะรหัสที่เพิ่งค้นเจอ · 1 รหัส = 1 LINE · รหัสที่ถูกปิดสิทธิ์เข้าไม่ได้และเซสชันเดิมหลุด

**ข้อความประกาศในห้อง:** มีได้แค่ "ชื่อย่อ + รอบเวลา" ผ่าน `short_name()` ("คุณสมชาย จ.") ·
ห้ามใส่หมายเหตุ (อาจเป็นข้อมูลสุขภาพ) อีเมล เบอร์ แผนก หรือรหัสจอง · ห้ามโพสต์ผู้ไม่มาตามนัด/ผู้ถูกงดสิทธิ์

**ปุ่ม "โพสต์แล้ว":** บันทึกตามชุดที่ HR เห็นตอนคัดลอก ไม่ใช่สถานะปัจจุบัน (กันคิวที่เข้ามาระหว่างนั้นถูกนับว่าประกาศแล้ว)

## 9. รายชื่อพนักงาน แผนก และผังองค์กร

- **ไฟล์ HR:** อ่านในหน่วยความจำแล้วทิ้ง · จำกัดขนาด 5 MB · ตรวจ zip bomb · หัวคอลัมน์อยู่ใน 10 แถวแรก ·
  ต้องมี "รหัสพนักงาน" + "ชื่อ-นามสกุล" · "คำนำหน้าชื่อ" "ชื่อเล่น" "แผนก / ฝ่าย" "ตำแหน่ง" มีหรือไม่มีก็ได้
- **นำเข้าซ้ำได้:** นับใหม่/แก้/เท่าเดิม · ปิดสิทธิ์คนที่ไม่อยู่ในไฟล์ได้ (มีด่านกันปิดเกิน 30%)
  · ชื่อ/บริษัท/ฝ่ายของคนที่ผูก LINE แล้วซิงก์ตามไฟล์
- **ผังองค์กร H2-2026 (โยงเมื่อ 25 ก.ย.):** อยู่ในผัง 133 คน · ไม่อยู่ในผัง 193 คน (ส่วนใหญ่พนักงานหน้าร้าน) ·
  ชื่อในผังที่ไม่อยู่ในรายชื่อ HR 5 คน · สะกดต่างกัน 11 คน (ระบบใช้ชื่อตามไฟล์ HR)
- **เงื่อนไขฝ่าย (012):**
  - คนในผัง → ฝ่ายในโปรไฟล์ตั้งให้อัตโนมัติ และ**ล็อก** (ย้ายได้โดย HR เท่านั้น)
  - นอกผัง / บัญชียุคอีเมล → ตั้งต้นเป็น **"อื่นๆ (Others)"** · เลือกเองได้ · ถ้าเลือกจากรายการแล้วระบบไม่ทับ
  - ไฟล์ที่ไม่มีคอลัมน์ฝ่ายไม่ล้างฝ่ายที่บันทึกไว้ · ชื่อฝ่ายที่ไม่รู้จักเตือนตอนตรวจไฟล์และคงค่าเดิม
- ไฟล์สรุปและไฟล์พร้อมนำเข้า (มีรายชื่อจริง) อยู่ใน `Claude outputs/` ซึ่ง git ไม่เก็บ

## 10. ความปลอดภัยและข้อมูลส่วนบุคคล

| เรื่อง | มาตรการ |
|--------|---------|
| เซสชัน | คุกกี้ HttpOnly · Secure บน production · เก็บเฉพาะ sha256 ของโทเคนในฐานข้อมูล |

| LINE Login | state ใช้ครั้งเดียว (ผูกกับคุกกี้) · PKCE · nonce · ตรวจ aud ของ ID token · `next` รับเฉพาะ path ภายใน |
| Webhook | ตรวจลายเซ็นเสมอบน production · ข้อความ LINE ไม่มีลิงก์ที่มีโทเคน |
| ลิงก์ห้อง LINE | ส่งให้เฉพาะคนที่ล็อกอินแล้ว · รับเฉพาะ https + โดเมน LINE · QR สร้างในเบราว์เซอร์ |
| ไฟล์ Excel | ไม่บันทึกลงดิสก์ · กัน zip bomb / XML bomb · log ไม่พิมพ์ชื่อพนักงาน |
| ข้อมูลจริง | ห้าม commit รายชื่อจริง · เทสต์ใช้ชื่อสมมติเท่านั้น |
| production | ปิด `/docs` `/redoc` `/openapi.json` · ความลับอยู่ใน `.env` เท่านั้น |

- ตัวนับเดารหัสหลังบ้านอยู่ในหน่วยความจำ (รีสตาร์ต = ล้าง · หลาย worker นับแยก)
- ผูก LINE ด้วยรหัสอย่างเดียว: ใครรู้รหัสผูกแทนได้ถ้าผูกก่อนเจ้าตัว → ให้ทุกคนผูกภายในวันที่กำหนด
- แจ้งเตือน LINE ถึงเฉพาะคนที่เป็นเพื่อน OA · push นับโควตาแพ็กเกจ (1 คิว ≈ 3 ข้อความ)
- โพสต์ลง OpenChat อัตโนมัติไม่ได้
- ลิงก์เข้าระบบทางอีเมลถูกใช้ทันทีที่มีคน GET → ตัวสแกนลิงก์ (Safe Links) อาจใช้โทเคนก่อนพนักงาน

## 17. ข้อสังเกตจากการรีวิว

จุดแข็ง:

- **ความถูกต้องของกติกาอยู่ที่ฐานข้อมูล** ไม่ใช่แค่โค้ด — กันจองซ้ำและกันใช้สิทธิ์เกินได้จริงภายใต้การยิงพร้อมกัน
- เทสต์กับ Postgres จริง และมีเทสต์สำหรับบั๊กที่เคยเกิดจริงทุกตัว
- เอกสาร "สิ่งที่ห้ามทำ" พร้อมเหตุผลและเหตุการณ์ที่เคยพลาด ช่วยกันการแก้ผิดซ้ำได้ดี
- ออกแบบเรื่องข้อมูลส่วนบุคคลตั้งแต่ต้น (ชื่อย่อ · ไม่เก็บไฟล์ HR · ลิงก์ห้องเฉพาะคนล็อกอิน)

ความเสี่ยงที่ควรจับตา:

- **Single point of failure:** ทั้งระบบอยู่บน Windows Server เครื่องเดียว + ngrok ฟรี และไฟล์สำรองอยู่ดิสก์เดียวกัน
  → ดิสก์เสีย = ข้อมูลหายทั้งหมด ควรคัดลอกไฟล์สำรองออกนอกเครื่องเป็นอันดับแรก
- **ด่านผูก LINE อ่อนโดยเจตนา** (รหัสพนักงานไม่ใช่ความลับ) — ยอมรับได้ถ้าทุกคนผูกเร็ว แต่ควรกำหนดวันปิดรับให้ชัด
- **worker เป็นส่วนที่พังเงียบ** — ถ้าหยุด คนไม่มาจะไม่ถูกตัดสิทธิ์และไม่มีแจ้งเตือน ควรมี health check/แจ้งเตือนเมื่อ worker ไม่ทำงาน
- **types ฝั่งหน้าเว็บเขียนมือ** — เพิ่มฟิลด์ backend แล้วลืมแก้หน้าเว็บจะไม่มีอะไรเตือน
- `react-router-dom` มีช่องโหว่ระดับ moderate ค้างอยู่
