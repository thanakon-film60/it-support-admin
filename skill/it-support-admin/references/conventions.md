# ธรรมเนียมการเขียนโค้ด เทสต์ และเอกสาร

## ภาษา

**ทุกอย่างเป็นภาษาไทย** — คอมเมนต์ · ชื่อฟังก์ชันเทสต์ (Python ใช้ชื่อไทยได้ตรงๆ) ·
ข้อความ error · ข้อความในแชท · หัวตาราง · เอกสาร ยกเว้นชื่อตัวแปร/ฟังก์ชันในโค้ดที่ใช้อังกฤษตามปกติ

## คอมเมนต์เขียน "ทำไม" ไม่ใช่ "ทำอะไร"

โค้ดบอกอยู่แล้วว่าทำอะไร คอมเมนต์ที่มีค่าคือเหตุผลและผลเสียถ้าทำอีกแบบ ตัวอย่างจากโปรเจกต์จริง:

```python
# รหัสเดียวตรงหลายเครื่อง -> ถามก่อน ห้ามเดา
#
# ข้อมูลจริงมีรหัสซ้ำอยู่ 28 แถว เช่น PC2306001 ถูกใช้กับ 4 เครื่องที่ถลางภูเก็ต / อยุธยา /
# บางกะปิ / สำนักงานใหญ่ ถ้าเดาเอาเครื่องแรก ช่างจะได้ ticket ที่ชี้ไปผิดสาขา
# และไม่มีใครรู้ตัวจนกว่าจะไปถึงหน้างาน
```

รูปแบบที่ใช้ทั้งโปรเจกต์: **บอกอาการที่จะเกิด → บอกตัวเลข/เคสจริงที่วัดมา → บอกทางที่เลือกและทำไม**

คอมเมนต์ที่ยาวได้ถ้าคุ้ม — หัวไฟล์ของ `flow.py` · `store.ts` · `employees.ts` · `richmenu.py`
เป็นย่อหน้าอธิบายการตัดสินใจทั้งหมดของไฟล์นั้น ให้เขียนต่อในสไตล์เดียวกัน

## สถานะให้เครื่องอ่าน ต้องแยกจากข้อความให้คนอ่าน

ค่าที่สคริปต์เอาไป `if` ต้องเป็น ASCII สั้นๆ คงที่ และอยู่คนละฟิลด์กับข้อความที่เขียนให้คนเข้าใจ

```json
{ "richmenu_state": "installing", "richmenu": "กำลังติดตั้ง..." }
```

**เคสจริง 2026-09-26:** `deploy.ps1` เทียบสถานะ rich menu จากข้อความไทยตรงๆ
แต่ Windows PowerShell 5.1 ถอดรหัส body ของ `Invoke-WebRequest` เป็น ISO-8859-1
เมื่อ `Content-Type` ไม่มี charset ข้อความจึงเพี้ยนก่อนถึงบรรทัดที่เทียบ — การเทียบพลาดทุกกรณี
ลูปที่รอให้ติดตั้งเสร็จหลุดทันที แล้วรายงานว่า "ติดตั้งไม่สำเร็จ" ทั้งที่กำลังติดตั้งอยู่
**ไม่มี error ที่ไหนเลย** เพราะในสายตาโค้ดคือการเทียบที่ให้ผลเท็จตามปกติ

ค่าเดียวที่ทำสองหน้าที่จะพังเงียบๆ ในวันที่ข้อความเปลี่ยน — แปลภาษา แก้คำ หรือโดน encoding เล่นงาน

ข้อควรรู้เพิ่ม: Starlette เติม `; charset=utf-8` ให้เฉพาะ media type ที่ขึ้นต้นด้วย `text/`
`application/json` จึงออกไปแบบไม่มี charset ถ้า response มีภาษาไทยให้ระบุเอง

## เทสต์

ฝั่ง JS ใช้ `node:test` ล้วน ไม่มี framework · ฝั่ง Python ใช้ `pytest` + `pytest-asyncio`
(`asyncio_mode = auto` ใน `pytest.ini` จึงไม่ต้องใส่ decorator ทุกตัว)

**ชื่อเทสต์ต้องบอกว่า "ทำไมเคสนี้สำคัญ" ไม่ใช่แค่ชื่อฟังก์ชันที่เรียก:**

```python
def test_ชื่อซ้ํากันหลายคนต้องให้เลือกห้ามเดา():
    """"สมชาย" มี 2 คนในทะเบียน — เดาให้คนแรกคือการผูกผิดคนแบบถาวร"""
```

```js
test('1 บัญชี LINE ผูกได้กับพนักงานคนเดียว — ผูกคนใหม่ต้องถอดคนเก่าออก', () => {
  // ถ้าปล่อยให้ค้าง 2 แถว การค้นย้อนกลับจะคืน "แถวไหนก็ได้ที่เจอก่อน" แปลว่าคนคนเดียว
  // กลายเป็นผู้แจ้งคนละคนได้ในแต่ละครั้ง โดยไม่มีอะไรฟ้อง
```

### เทคนิคที่ใช้ซ้ำได้

**รัน route/โมดูลจริงบน store ชั่วคราว** (`tests/line-intake.test.cjs`, `tests/employees.test.cjs`):
override `Module._load` ให้ mock `next/cache` + map `@/` → `src/`, ลงทะเบียน `require.extensions['.ts']`
ด้วย `ts.transpileModule`, แล้ว `process.chdir(tmpdir)` เพื่อให้ `store.ts` เขียนลงที่ชั่วคราว

**เรนเดอร์ component จริง** (`tests/employees-board.test.cjs`): เพิ่ม `jsx: ts.JsxEmit.ReactJSX`
แล้ว mock `next/navigation` กับโมดูล server action → `renderToStaticMarkup()` → ตรวจข้อความที่ต้องเห็น

**จำลอง LINE API ทั้งเซิร์ฟเวอร์** (`test_richmenu.py`): ใช้ `http.server` จริงแทน mock ทีละฟังก์ชัน
เพราะ **ลำดับการเรียกสำคัญ** (alias ต้องตั้งหลังสร้างเมนู · รูปต้องอัปโหลดก่อนตั้ง default)
ถ้า mock ทีละฟังก์ชันจะไม่จับลำดับที่ผิดเลย

**ตรวจ UI ด้วยตาจริง**: `react-dom/server` → คอมไพล์ Tailwind กับ `globals.css` ตัวจริง →
Playwright วัด `scrollWidth` vs `clientWidth` + ถ่ายภาพที่ 390 / 768 / 1440

## UI

Tailwind CSS v4 แบบ CSS-first (`@theme inline` ใน `src/app/globals.css`)
โทเคนสี: `page` · `surface` · `surface-2` · `line` · `ink` · `muted` · `accent` · `accent-bg`
คลาสช่วย: `glass` · `edge-glow` · `font-num` (ตัวเลขความกว้างเท่ากัน ใช้ในตาราง)

- ธีมมืดอย่างเดียว ไม่มีโหมดสว่าง
- ปุ่มในแถวตารางสูงอย่างน้อย `2.25rem` — เล็กกว่านี้กดพลาดบนมือถือเมื่อมีปุ่มติดกัน 3–4 ปุ่ม
- ช่องกรอกในโมดัลใช้ `MODAL_INPUT` (`text-base` บนมือถือเพื่อไม่ให้ iOS ซูมเข้าอัตโนมัติ)
- ตารางบนจอใหญ่: กำหนด `min-w` ต่อคอลัมน์ อย่าใช้ `whitespace-nowrap` พร่ำเพรื่อ
  (เคยทำแล้วปัญหาย้ายไปบีบคอลัมน์อื่นแทน) และต้องวัดความกว้างจริงว่าไม่ล้น
