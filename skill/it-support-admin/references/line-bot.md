# LINE Bot — บทสนทนาและการออกแบบ

## ผังสถานะ

```
IDLE ─▶ ASK_BRANCH   บริษัท → [กลุ่ม/หน่วยงาน เฉพาะ central] → สาขา
     ─▶ ASK_TYPE     แจ้งซ่อม / เบิกอุปกรณ์ / คืนอุปกรณ์ / ขอใช้บริการ IT
     ─▶ ASK_ASSET    เมนู ประเภท → ยี่ห้อ/รุ่น → รหัส · หรือพิมพ์รหัสเอง · หรือกดข้าม
        └─ รหัสซ้ำ ─▶ ASK_PICK_ASSET
     ─▶ [ถ้าเบิก] ASK_ITEM ─▶ ASK_QTY ─▶ ASK_MORE_ITEMS
     ─▶ ASK_REQUESTER   ← ข้ามทั้งขั้นถ้าบัญชี LINE นี้เคยระบุตัวไปแล้ว (ยกเว้นเบิก — ดูข้างล่าง)
        └─ [ถ้าเบิก] ยืนยันผู้เบิกแล้ว ─▶ สร้าง ticket ─▶ IDLE   ← จบตรงนี้ ไม่มีขั้นรายละเอียด
     ─▶ ASK_DESC ─▶ สร้าง ticket ─▶ IDLE   ← ปุ่ม "เปลี่ยนคนแจ้ง" ของประเภทอื่นอยู่ที่ขั้นนี้
                                             และปุ่ม "ไม่มี ส่งเลย" (a=desc_skip) จบใน 1 คลิก

สถานะพิเศษ: RETRY_SUBMIT (ส่งไม่สำเร็จ รอกดส่งซ้ำ) · FIND_ASSET (โหมดค้นหาอย่างเดียว)
```

ทุกสถานะรับ "ยกเลิก" · session หมดอายุ 30 นาที · `Session.from_json` ทิ้งคีย์ที่ไม่รู้จัก
(เพื่อให้ deploy/rollback ระหว่างที่มีคนคุยค้างอยู่ไม่ทำให้บอทเงียบ)

## คุยกับเจ้าหน้าที่ — `flow._handoff_gate` (8 ต.ค. 2026)

ลูกค้ากด `a=human` หรือพิมพ์ขอคุยกับคน (`wants_human()` — ต้องขึ้นต้นด้วยคำขอและไม่ยาว ประโยคที่แค่มีคำว่า
"เจ้าหน้าที่" ปนอยู่ไม่นับ) → `Session.handoff_until = now + HANDOFF_HOURS` แล้วบอท **เงียบ** (คืน `[]`)
กับทุกข้อความ/รูป/สติกเกอร์ของคนนั้น ให้ทีม IT ตอบในแอป LINE Official Account

| เหตุการณ์ระหว่างคุยกับเจ้าหน้าที่ | ผล |
| --- | --- |
| ข้อความ / รูป / สติกเกอร์ | เงียบ + ต่อเวลา (นับจากข้อความล่าสุด) |
| `a=bot_resume` · พิมพ์ "เมนู" "ยกเลิก" "บอท" | ล้าง session + ตอบ `handoff_ended()` |
| ข้อความจาก rich menu (`RICH_MENU_TEXTS` สร้างจาก `richmenu.MAIN_BUTTONS`) · postback อื่นของบอท | ล้าง session แล้วทำงานต่อตามปกติ |
| `ticket` · `confirm*` · `still_broken` · `my_assets` · `rate` · `rate_skip` (ดูข้อมูล/ตอบผลงาน) | ตอบตามปกติ ไม่ตัดการคุย |
| Chat ใน OA ปิด (`handoff_available=False`) | ไม่ส่งต่อ — ตอบ `handoff_unavailable()` และล้าง handoff ที่ค้าง |

- ด่านนี้อยู่ **ก่อน** image/unsupported เพราะระหว่างคุยทุกอย่างเป็นของเจ้าหน้าที่ · `main.py` ไม่โหลดรูปเข้าระบบด้วย
- store ยืดอายุ session ให้ถึง `handoff_until` (ปกติ 30 นาที) — ไม่งั้นบอทลืมว่าต้องเงียบ
- `main._mark_read` สั่งอ่านแล้วด้วย `markAsReadToken` เฉพาะเมื่อบอทจัดการจบเอง: ไม่สั่งตอนเงียบ · ตอน `Reply.keep_unread`
  (ขอคุยกับคน / ตีความไม่ออก) · ตอนก่อน/หลังข้อความนั้นอยู่ในช่วงคุย — **LINE นับอ่านแล้วย้อนหลังทั้งห้อง**
- ข้อความแรกที่ตีความไม่ออก (IDLE) ตอบ `not_understood()` + การ์ดเลือกสาขาที่เติม `HUMAN_BUTTON` แทน "ไม่พบสาขา"
- เทสต์: `tests/test_handoff.py` (flow + TTL ของ store + webhook จริงผ่าน TestClient)

### เจ้าหน้าที่รับแชทต่อเอง — หลังบ้านสั่ง (12 ต.ค. 2026)

LINE ไม่ส่ง webhook ตอนเจ้าหน้าที่ตอบในแอป LINE OA → บอทรู้เองไม่ได้ หน้าแอดมินจึงสั่งผ่าน `main.py`:

— การเปลี่ยนสถานะไม่สั่งบอทเอง `tests/chat-takeover.test.cjs` ตรวจ)
· หลังบ้านส่งสถานะมาแค่ `pending` / `resolved` — ป้ายของสถานะเดิมใน `messages.TICKET_STATUS_LABEL` / `flex.py` เหลือไว้เฉยๆ ไม่ต้องลบ

## ทีม IT เปิด/ปิดบอทจากแชท — `flow._admin_gate` · `_off_gate` (13 ต.ค. 2026)

ลำดับด่านของทุก event: `_admin_gate` → `_off_gate` → `_handoff_gate` (follow ผ่านแค่ `_off_gate`)
- พิมพ์ "แอดมิน" (`ADMIN_WORDS`) → `backend.line_staff(check)` → approved = การ์ด `M.admin_panel` · pending = บอกให้รออนุมัติ ·
  none/หลังบ้านล่ม = คืน None ให้ `_handoff_gate` ตีความเป็นขอคุยกับคน (ความหมายเดิม) · "ขอสิทธิ์แอดมิน" = `line_staff(request)`
- ปุ่ม `a=adm` (`p=` หน้า) · `a=adm_all&v=off|on` (off ต้องมี `ok=1` = ยืนยัน) · `a=adm_u&v=off|on&u=<uid>` — **ถามสิทธิ์ใหม่ทุกครั้งที่กด** ·
  `u` ต้องตรง `^U\w{1,63}$` · Chat ใน OA ปิด = ปิดไม่ได้ (`admin_chat_off`)
- `_off_gate`: `store.get_bot_off()` / `get_user_off(uid)` → passthrough `_HANDOFF_PASSTHROUGH` + ข้อความใน `RATE_COMMENT` ·
  ที่เหลือ `once_per_day("off_notice:<uid>")` ได้ `bot_off_notice()` (keep_unread) ไม่งั้น `[]` · ผู้ใช้เปิดเองไม่ได้
- `pause_bot_for` / `resume_bot_for` (ล้าง handoff ด้วย) ใช้ร่วมกับ `main.py` `/internal/bot/*` และ `/internal/handoff/end`
- store แยกจาก session: `linebot:ctl:bot_off` · `user_off` (hash) · `recent` (zset 200) + `names` · `once:*` (SET NX EX 2 วัน)
- เทสต์ `tests/test_bot_control.py` (มี FakeRedis ของตัวเอง ไม่ต้องติดตั้ง fakeredis)

## ให้คะแนนหลังปิดงาน (12 ต.ค. 2026)

การ์ดปิดงานสร้างฝั่ง Next.js (`lib/line/rating-card.ts`): ดาว `a=rate&code=&s=1..5` + "ยังมีปัญหาอยู่" `a=confirm&code=&v=0`
- `a=rate` → `backend.rate_ticket(score)` → หลังบ้านตอบ `ask_comment` (1–3 ดาว) → ขั้น `RATE_COMMENT` (`Session.rate_code`)
  ข้อความถัดไป = ความเห็น (`comment` อย่างเดียว · ตัด 500 แบบ UTF-16) · "ข้าม"/`a=rate_skip` = เลิกรอ
- ไม่ถามความเห็นถ้ากำลังกรอกเรื่องอื่นค้าง (ไม่ยึด session — ขอบคุณแล้ว `_prompt_for_step`) หรือกำลังคุยกับเจ้าหน้าที่
- `RATE_COMMENT` + ข้อความจาก rich menu = เปลี่ยนเรื่อง (ล้างแล้วทำงานตามปุ่ม) · + รูป = เริ่มแจ้งเรื่องใหม่
- reject สำเร็จ → `still_broken_ack(handed_off=True)` + เข้าโหมดเจ้าหน้าที่ · `reopen_expired` (เกิน 14 วัน) → ให้แจ้งใหม่
- การ์ดยืนยันรุ่นเก่า `v=1` ยังกดได้ → `confirm_done_thanks()` แนบปุ่มดาว (quick reply) ให้คะแนนต่อ

## เมนูไล่ชั้น — ทำไมต้องมี

LINE ให้ quick reply 13 ปุ่ม / carousel 12 ใบ แต่ข้อมูลจริงมีสาขา 102 แห่ง ทรัพย์สิน 200+ ชิ้น
พนักงาน 326 คน การกรองทีละชั้นจึงเป็นทางเดียวที่พาคนไปถึงของที่ต้องการในไม่กี่ปุ่ม

**ปุ่มส่งกลับมาแค่ "ลำดับที่" (`i=`) ไม่ใช่ค่าจริง** เพราะ postback data จำกัด 300 ไบต์
และภาษาไทย encode แล้วกินตัวละ 9 ไบต์ — ค่าจริงเก็บไว้ใน session (`pick_values` / `rq_values`)

ผลข้างเคียงที่ต้องจัดการ: ผู้ใช้กดปุ่มจากการ์ดเก่าที่ค้างบนจอได้ ถ้า index ไม่ตรงกับ session แล้ว
**ต้องพากลับไปเริ่มเลือกใหม่ ห้ามเดาให้** (มีเทสต์ครอบทุกเมนู)

## ชั้น AI — `ai.py`

`Knowledge` = ข้อมูลทั้งระบบที่ดึงจาก `?kind=knowledge` แล้ว cache 5 นาที
(สาขา · `branch_items` · `companies` · **`employees` 326 คน** · `departments` · สต็อก · ทรัพย์สิน · FAQ)

`analyze(text, kb)` คืน intent + slot ที่จับได้ (สาขา · รหัสทรัพย์สิน · ชื่อของ · จำนวน)
ทำให้พิมพ์ประโยคเดียวแล้วข้ามคำถามที่ตอบไปแล้วได้

`_fuzzy_best()` ใช้วิธี **เลื่อนหน้าต่าง 1–5 คำ** แล้วเทียบทีละ candidate ไม่ใช่ `partial_ratio`
ทั้งประโยค — วัดจริงกับ "ขอเบิกคีย์บอด" เทียบ "คีย์บอร์ด": partial_ratio ได้ 77.8 (หลุด threshold)
วิธีเลื่อนหน้าต่างได้ 87.5 (ผ่าน) ขณะที่เคสที่ไม่ควรแมตช์ยังอยู่แถว 22–38 เท่าเดิม

## ขั้นตอนระบุผู้แจ้ง

ครั้งแรกของแต่ละบัญชี LINE:

```
"ผู้แจ้งคือใครครับ?"
  ├─ พิมพ์ชื่อจริง/ชื่อเล่น/รหัสพนักงาน ─┬─ เจอคนเดียว ─▶ ให้กดยืนยัน ─▶ ผูกบัญชี
  │                                      ├─ เจอหลายคน  ─▶ ให้เลือก    ─▶ ผูกบัญชี
  │                                      └─ ไม่เจอ      ─▶ "ใช้ชื่อที่พิมพ์" แจ้งต่อได้เลย
  └─ กด "เลือกจากรายชื่อ" ─▶ เลือกฝ่าย ─▶ เลือกชื่อ ─▶ ผูกบัญชี
```

ครั้งที่ 2 เป็นต้นไป **ข้ามทั้งขั้น** — ขั้นถามรายละเอียดขึ้น `👤 แจ้งในชื่อ: ...` + ปุ่ม "เปลี่ยนคนแจ้ง"

**ยกเว้นการเบิก** (`flow._ends_at_requester`) ซึ่งจบทันทีหลังระบุผู้เบิก — ไม่มีขั้นรายละเอียดให้ปุ่ม
"เปลี่ยนคนแจ้ง" ไปอยู่ บัญชีที่ผูกแล้วจึงเห็นการ์ด "ผู้เบิกคือคนนี้ใช่ไหม" ของคนที่ผูกไว้แทน
(**✅ ใช่ ฉันเอง** = ส่งเรื่อง · **👤 ไม่ใช่ เปลี่ยนคน** = `a=rq_change` ถอดการผูก) **ห้ามส่งเงียบๆ**
ไม่งั้นบัญชีที่ผูกผิดคนจะเบิกของในชื่อคนอื่นไปเรื่อยๆ โดยไม่มีทางแก้เองในแชท

ทุกทางที่ระบุผู้แจ้งเสร็จตัดสินด้วย `_ready_to_submit()` ตัวเดียว ส่วนข้อความ "กด 'ใช่ ฉันเอง'
เพื่อส่งเรื่อง…ทันที" บนการ์ดโผล่ตาม `_submits_after_requester()` — สองตัวนี้ต้องตรงกันเสมอ

| การตัดสินใจ | เหตุผล |
| --- | --- |
| ทางหลักคือพิมพ์ ไม่ใช่กดเมนู | 326 คน ถ้าเริ่มที่เมนูต้องเลื่อนหาตัวเองในฝ่ายที่มีเป็นสิบคน |
| เจอคนเดียวยังต้องกดยืนยัน | การผูกติดถาวร ผูกผิดครั้งเดียว ticket ทุกใบหลังจากนั้นขึ้นชื่อคนอื่น |
| เบิกของบัญชีที่ผูกแล้วยังต้องกดยืนยัน | การเบิกไม่มีขั้นรายละเอียดที่เคยมีปุ่ม "เปลี่ยนคนแจ้ง" — การ์ดนี้คือทางแก้เดียวในแชท |
| เลือกจากเมนูไม่ต้องยืนยันซ้ำ | กดชื่อตัวเองจากฝ่ายตัวเองชัดเจนพอแล้ว |
| ไม่เจอในทะเบียน = แจ้งต่อได้ | พนักงานใหม่ที่ HR ยังไม่เพิ่มคือกลุ่มที่ต้องพึ่ง IT มากที่สุด |
| หลังบ้านล่ม = ถามตามปกติ | ถามเกิน 1 ครั้งเสียเวลาไม่กี่วินาที แต่ค้างคือแจ้งเรื่องไม่ได้เลย |
| ทะเบียนว่าง = ถอยไปพิมพ์ "ชื่อ - แผนก" | เว็บรุ่นเก่ายังไม่ส่ง `employees` มา ห้ามตอบ "ไม่พบ" ทั้งที่ไม่มีทะเบียนให้ค้น |

## 3 ฟิลด์ที่ติดไปกับทุก ticket

| ฟิลด์ | มาจากไหน | ถ้าไม่มีจะเป็นยังไง |
| --- | --- | --- |
| `request_id` | เกิดพร้อม `Session` คงเดิมตลอดแม้ผ่าน Redis | กด "ลองส่งใหม่" ได้ ticket ใบที่ 2 + ตัดสต็อกซ้ำ |
| `initial_message` | ข้อความแรกที่ผู้ใช้พิมพ์เอง | ข้อมูลที่ดีที่สุดหายตั้งแต่บับเบิลแรก |
| `equipment_id` | เครื่องที่ผูกแล้วจริง | รหัสซ้ำ 28 แถว หลังบ้านต้องเดา → ticket ผูกผิดเครื่อง |

มี `initial_message` แล้วบอท **ไม่บังคับให้พิมพ์รายละเอียดซ้ำ** ตอนถึงขั้น `ASK_DESC`
(คนที่เล่าอาการมาตั้งแต่แรกแล้วตอบ "ไม่มี" ผ่านได้) แต่คนที่เปิดเรื่องจากการกดปุ่มโดยไม่เคยเล่าอะไร
ยังบังคับเหมือนเดิม — ticket แจ้งซ่อมที่ไม่มีข้อความเลยช่างเอาไปทำต่อไม่ได้

> **ทุกทางเข้าที่รับรหัสทรัพย์สิน (พิมพ์เอง / ไล่เมนู / AI จับจากประโยคแรก) ต้องผ่าน
> `_resolve_asset_code()` ตัวเดียวกัน** — เคยมีบั๊กที่ทาง AI ตั้งค่าเองจาก cache แล้วเดินต่อเลย

## Rich menu — `richmenu.py` + `line-oa/`

4 ปุ่มจัดเป็น **2×2** (แจ้งซ่อม · เบิกอุปกรณ์ / คืนอุปกรณ์ · ขอใช้บริการ IT) รูป **2500×1686** ปุ่มละ 1250×843
LINE รับแค่ 2 ขนาด: 2500×1686 (2 แถว) กับ 2500×843 (แถวเดียว) และไฟล์ต้องไม่เกิน 1 MB

**ปุ่มอยู่ 3 ที่ ต้องขยับพร้อมกันเสมอ** ไม่งั้นได้อาการ "กดปุ่มนี้แล้วได้อีกเรื่อง":

| ไฟล์ | ตัวแปร |
| --- | --- |
| `line-oa/make_assets.py` | `MENU_MAIN` + `COLS/ROWS` + `W/H` (รูปที่ผู้ใช้เห็น) |
| `line-bot-python/app/richmenu.py` | `MAIN_BUTTONS` + `COLS/ROWS` + `W/H` (พื้นที่กดจริง) |
| `line-oa/setup_richmenu.py` | `BUTTONS` + `COLS` + `W/H` (ทางสำรอง รันมือ) |

`ensure_rich_menu()` เทียบ **"ลายเซ็นปุ่ม + ขนาดรูป"** ของเมนูที่ติดตั้งอยู่กับโค้ด ไม่ตรงเมื่อไหร่
ติดตั้งใหม่ให้เอง (เดิมเช็คแค่ชื่อเมนู ทำให้ตอนลดจาก 6 ปุ่มเหลือ 4 ปุ่ม deploy ไปแล้วเมนูไม่เปลี่ยน)
และตามลบเมนูชั้น 2 + alias `itsupport-data` ที่เลิกใช้ เพราะ LINE ไม่ลบให้เอง

`RICHMENU_FORCE_REINSTALL=true` ใช้เฉพาะตอน "เปลี่ยนรูปแต่ปุ่มเหมือนเดิม"

`ensure_rich_menu()` คืน `RichMenuResult(state, message)` — `state` เป็น ASCII
(`ok` · `installed`) ไว้ให้เครื่องตัดสิน ส่วน `message` เป็นไทยไว้ใส่ log
`/health` ส่งออกเป็น `richmenu_state` คู่กับ `richmenu` (รวม `installing` · `disabled` · `failed`
ที่ `main.py` ตั้งเอง) — **สคริปต์ต้องอ่านจาก `richmenu_state` เท่านั้น** ดูเหตุผลที่ `conventions.md`
