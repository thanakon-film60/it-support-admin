# IT Admin — ระบบจัดการ IT Support Ticket / ทรัพย์สิน / สต็อก

โปรเจกต์นี้ clone มาจากการวิเคราะห์ UX/UI และโครงสร้างข้อมูลของ `it-support-admin.vercel.app`
(รายละเอียดการวิเคราะห์ทั้งหมดอยู่ใน Project doc `it-support-admin-analysis.md`) โดยขยายขอบเขตเพิ่มจากต้นแบบ 2 จุดตามที่ตกลงกันไว้:

1. **เพิ่มระบบ Login/Auth จริง** (ต้นแบบไม่มีระบบยืนยันตัวตนเลย — เป็นช่องโหว่ด้านความปลอดภัยที่เปิดให้ใครก็เข้าถึงข้อมูลได้)
2. **สร้าง LINE OA Bot + LIFF mini-app แบบเต็มรูปแบบ** สำหรับให้พนักงานแจ้งปัญหา/สร้าง ticket จากภายนอกระบบแอดมิน (ต้นแบบไม่มีปุ่ม "สร้าง Ticket" ในหน้าแอดมินเลย แสดงว่า ticket ทั้งหมดถูกสร้างจากช่องทางอื่น)

สถานะปัจจุบัน: **ใช้งานจริงอยู่** บนเครื่อง Windows ในออฟฟิศ (Docker Desktop) ข้อมูลเก็บเป็นไฟล์ JSON
ใน docker volume `app_data` — **ยังไม่ได้ย้ายไป Postgres** ทั้งที่ service เตรียมไว้แล้ว
ดูหัวข้อ ["ย้ายจากไฟล์ JSON ไป Postgres"](#ย้ายจากไฟล์-json-ไป-postgres) ด้านล่าง

> **เพิ่งเข้ามาดูโปรเจกต์นี้ครั้งแรก?** อ่าน [`PROJECT.md`](./PROJECT.md) ก่อน —
> สรุปทั้งระบบไว้ในไฟล์เดียว (โครงสร้าง · ชั้นข้อมูล · บทสนทนาของบอท · กฎเหล็ก · กับดักที่เคยเจอ ·
> งานที่ค้างอยู่) ส่วนไฟล์นี้เป็นคู่มือรายหัวข้อสำหรับตอนลงมือทำจริง
>
> ถ้าเป็น AI agent: มี skill พร้อมใช้ที่ [`it-support-admin.skill`](./it-support-admin.skill)
> (ต้นฉบับแก้ได้ที่ `skill/` แล้ว `python skill/build.py` เพื่อแพ็กใหม่)

## Tech Stack

| ส่วน | เทคโนโลยี |
| --- | --- |
| Framework | Next.js 16 (App Router, React 19, Server Actions) |
| ภาษา | TypeScript |
| Styling | Tailwind CSS v4 (CSS-first config, ไม่มี `tailwind.config.js`) |
| Auth | Session cookie + JWT (`jose`) เซ็นเอง, hash รหัสผ่านด้วย `bcryptjs` |
| Data (ปัจจุบัน) | ไฟล์ JSON ใน docker volume `app_data` ผ่าน adapter เดียว (`src/lib/db/store.ts`) |
| Data (เป้าหมาย) | **Postgres 16** ที่รันเองใน `docker-compose.yml` — schema อยู่ที่ `db/init/001_schema.sql` · pool อยู่ที่ `src/lib/db/pg.ts` (ยังไม่มีโค้ดไหนเรียกใช้) |
| ทางเข้าจากเน็ต | **Cloudflare Tunnel** (container `tunnel`) → `https://it.thanakronpart-time.com` (เว็บ → `app:3000`) · `/webhook` (บอท → `bot:8000`) — ก่อน 7 ต.ค. 2026 ใช้ Tailscale Funnel |
| LINE Integration | LINE Messaging API (webhook) + LIFF (`@line/liff`) |
| Excel Import | `xlsx` (SheetJS) — ⚠️ ดูหมายเหตุความปลอดภัยด้านล่าง |

> ⚠️ Next.js 16 มี breaking changes จากเวอร์ชันเก่าพอสมควร (เช่น `middleware.ts` → `proxy.ts`) ถ้าจะแก้โค้ด
> เกี่ยวกับ routing/caching/auth ให้อ่าน `node_modules/next/dist/docs/` ก่อนเสมอ (มีคำเตือนไว้ใน `AGENTS.md` แล้ว)


เปิด [http://localhost:3000](http://localhost:3000) — ระบบจะพาไปหน้า `/login` อัตโนมัติเพราะยังไม่มี session

> ⚠️ `npm run build` ต้องมีอินเทอร์เน็ตเข้าถึง `fonts.googleapis.com` ได้ (โหลดฟอนต์ Sarabun/Space Mono ผ่าน
> `next/font/google`) ถ้า build ในเครื่อง/CI ที่ปิด network ไว้จะ error ตรงจุดนี้ — แก้ได้โดยเปิด network หรือเปลี่ยนไปโหลด
> ฟอนต์ผ่าน `next/font/local` แทน (ดาวน์โหลดไฟล์ฟอนต์มาเก็บในโปรเจกต์เอง) ที่ `src/app/layout.tsx`

**บัญชีทดสอบ:**

| Username | Password |
| --- | --- |
| `admin` | `ITadmin@2026` |

รหัสผ่านนี้ hash ไว้ในข้อมูล seed ที่ `src/lib/db/staff.ts` — **ต้องเปลี่ยนก่อนใช้งานจริงเสมอ**
ด้วย `staff-admin.bat` → เลือกบัญชี → "ตั้งรหัสผ่านใหม่" (โปรแกรมขึ้นเตือนเองถ้ายังมีบัญชีใช้รหัสนี้อยู่)

ครั้งแรกที่รัน ระบบจะสร้างโฟลเดอร์ `data/` และ seed ข้อมูลตัวอย่างให้อัตโนมัติ (ดูใน `.gitignore` — โฟลเดอร์นี้ไม่ถูก commit)

## ระบบ Auth ทำงานอย่างไร

- Login ผ่าน Server Action (`src/app/actions/auth.ts`) → เช็ค username/password กับ `staff_accounts` (bcrypt แบบไม่บล็อก
  event loop · ไม่พบชื่อก็เทียบกับ hash หลอกให้ใช้เวลาเท่ากัน กันการเดาว่าชื่อไหนมีบัญชี) → เซ็น JWT ใส่ cookie
  `itadmin_session` (httpOnly, secure ใน production, sameSite=lax, อายุ 7 วัน)
- **cookie เก็บแค่ "เป็นใคร" กับ "รุ่นของ session"** (`staffId` + `sv`) — ทุก request เปิดไฟล์บัญชีดูของจริงเสมอ
  (`src/lib/session-token.ts`) ผลคือ: ปิดใช้งาน/ลบบัญชี = หลุดทันที · เปลี่ยนรหัสผ่าน/กด "บังคับออกจากระบบ" =
  `session_version` เพิ่ม cookie ทุกใบที่ออกก่อนหน้าใช้ไม่ได้ · เปลี่ยนชื่อ/สิทธิ์ = มีผลทันทีโดยไม่ต้องล็อกอินใหม่
  (เดิมเชื่อข้อมูลใน cookie อย่างเดียว บัญชีที่ลบไปแล้วยังใช้งานต่อได้ถึง 7 วัน)
- **สิทธิ์รายหน้า:** `admin` เข้าได้ทุกหน้า (รวมหน้าที่จะเพิ่มในอนาคต) · `it_staff` เข้าได้เฉพาะหน้าที่ติ๊กไว้
  ทุก `page.tsx` และ**ทุก Server Action** เรียก `requireSession("<หน้า>")` — ไม่มีสิทธิ์ = ไป `/no-access`
  (ซ่อนเมนูอย่างเดียวไม่พอ: Server Action ถูกเรียกตรงได้โดยไม่ผ่านหน้าเว็บ) · action ที่หลายหน้าใช้ร่วมกัน
  ส่งเป็นรายการ (เช่นสต็อกกับ Tickets) · route handler ของคลังไฟล์ตรวจสิทธิ์หน้า `files` เอง
  · สิทธิ์หน้า "แก้ไขปัญหาแล้ว"/"ประวัติซ่อม" ที่ค้างในบัญชีเก่าถูกตัดทิ้งเงียบๆ (หน้าเหล่านั้นรวมเข้า Tickets แล้ว)
- **ชื่อผู้แก้ไข = บัญชีที่ล็อกอินอยู่** (13 ต.ค. 2026): หน้าต่างอัปเดตสถานะโชว์ "ชื่อที่แสดง" ของบัญชี (ตัวเดียวกับมุมขวาบน)
  แบบแก้ไม่ได้ ไม่ต้องพิมพ์เอง · Server Action ใช้ชื่อจาก session เท่านั้น ชื่อที่หน้าเว็บส่งมาไม่มีผล (กันบันทึกในนามคนอื่น)
  ใช้ทั้งประวัติสถานะและไทม์ไลน์ "รับแชทต่อเอง" (`accountEditorName()` ใน `src/lib/editor-name.ts`) · อยากให้ชื่อในประวัติเปลี่ยน
  = แก้ชื่อที่แสดงของบัญชีใน `staff-admin.bat` · ปิดล็อกอิน (`AUTH_DISABLED=true`) ไม่มีตัวตนให้ใช้ จึงกลับไปให้พิมพ์ชื่อเองแบบเดิม
- **`src/proxy.ts`** (ต้องอยู่ใน `src/` เพราะโปรเจกต์ใช้ `src/app` — เดิมวางไว้ที่ราก repo ซึ่ง Next ข้ามไปเงียบๆ
  ด่านนี้จึงไม่เคยทำงานเลยจนถึง 13 ต.ค. 2026):
  - `/uploads/*` (รูปแนบ ticket / FAQ) — ตรวจ session จริง + สิทธิ์หน้าที่ใช้รูปนั้น เพราะไฟล์ที่มีอยู่ตอนเซิร์ฟเวอร์เริ่ม
    Next เสิร์ฟจาก `public/` ตรงๆ โดยไม่ผ่าน route handler (ก่อนแก้: เปิดได้โดยไม่ต้องล็อกอิน)
  - หน้าอื่น — ดูแค่ว่ามี cookie ไหม (optimistic) แล้วพาไป `/login?from=<หน้าเดิม+query>` · ตรวจจริงอยู่ที่ `requireSession`
  - `/api/*` ไม่ผ่าน proxy เลย (ดู matcher) — ทุก route ตรวจเอง และ proxy ตัด body เกิน 10 MB ทิ้งเงียบๆ
- ปลายทางหลังล็อกอิน (`?from=`) รับเฉพาะ path ในระบบนี้ (`safeRedirectPath`) — กัน open redirect ไปหน้าหลอก
  ไม่ได้ขอหน้าไหน = พาไปหน้าแรกที่มีสิทธิ์ (เจ้าหน้าที่ที่ไม่มีสิทธิ์หน้าภาพรวมจะไม่เจอ "ไม่มีสิทธิ์" ทุกครั้งที่ล็อกอิน)
- หน้า public (ไม่ต้อง login): `/login`, `/liff/*` และ `/api/line/webhook` · `/api/internal/*` (ใช้ `x-internal-key`) · `/api/health`

## จัดการผู้ใช้และสิทธิ์รายหน้า (`staff-admin.bat`)

ดับเบิลคลิก `staff-admin.bat` ที่โฟลเดอร์โปรเจกต์บนเครื่องเซิร์ฟเวอร์ (Docker Desktop ต้องเปิด + container `app` รันอยู่)
ครั้งแรกจะติดตั้งไลบรารี `bcrypt` ของ Python ให้เอง แล้วเปิดหน้าต่าง `tools/staff_admin.py`

| ปุ่ม | ทำอะไร |
| --- | --- |
| เพิ่มผู้ใช้ใหม่ (Ctrl+N) | ชื่อผู้ใช้ · ชื่อที่แสดง · ประเภท (ผู้ดูแลระบบ = ทุกหน้า / เจ้าหน้าที่ = ติ๊กเลือกหน้า) · รหัสผ่านเริ่มต้น — "สุ่มรหัสผ่าน" สร้าง 16 ตัวแล้วคัดลอกให้เลย |
| แก้ไข / สิทธิ์หน้า (ดับเบิลคลิกแถว) | เปลี่ยนชื่อ ประเภท หน้าที่เข้าได้ และสถานะ — มีผลกับเว็บทันที ไม่ต้องให้คนนั้นล็อกอินใหม่ |
| ตั้งรหัสผ่านใหม่ | ทุกเครื่องที่ล็อกอินบัญชีนี้ค้างไว้จะหลุดทันที (กันกรณีรหัสเดิมรั่ว) |
| ปิด / เปิดใช้งาน | ปิด = ล็อกอินไม่ได้ + หลุดทุกเครื่องทันที · ข้อมูลและประวัติงานยังอยู่ · **ใช้แทนการลบสำหรับคนที่ลาออก** |
| บังคับออกจากระบบ | ใช้ตอนทำเครื่องหาย/สงสัยว่ามีคนอื่นใช้บัญชี — เจ้าของล็อกอินใหม่ด้วยรหัสเดิมได้ |
| ลบบัญชี | สำหรับบัญชีที่สร้างผิดเท่านั้น (ถามยืนยัน ปุ่มตั้งต้นคือ "ไม่") |
| ประวัติการแก้ไข | ใคร (บัญชี Windows) ทำอะไรกับบัญชีไหนเมื่อไหร่ — `data/staff_admin_log.json` ล่าสุด 2,000 รายการ · ไม่เก็บรหัสผ่าน |

กติกาที่โปรแกรมบังคับให้:

- รหัสผ่าน ≥ 12 ตัว · ไม่เกิน 72 ไบต์ (ข้อจำกัดของ bcrypt — ตัวไทย 1 ตัว = 3 ไบต์) · ห้ามมีชื่อผู้ใช้อยู่ข้างใน · ห้ามใช้รหัสตั้งต้น
- ชื่อผู้ใช้ห้ามซ้ำแบบไม่สนตัวพิมพ์ (หน้า login ไม่สนตัวพิมพ์) · ถ้าไฟล์มีชื่อซ้ำอยู่แล้ว เว็บจะไม่ให้บัญชีที่ซ้ำล็อกอิน
- **ไม่ยอมให้เหลือผู้ดูแลระบบที่ใช้งานได้ 0 คน** (ลบ/ปิด/ลดสิทธิ์คนสุดท้ายไม่ได้)
- บันทึกแบบ compare-and-swap: ถ้าไฟล์ถูกแก้จากที่อื่นหลังเปิดโปรแกรม (เช่นเปิดค้างไว้ 2 เครื่อง) จะไม่เขียนทับ

## หน้ารหัสผ่าน (`/passwords`)

4. ให้สิทธิ์หน้า "รหัสผ่าน" กับคนที่ต้องใช้ใน `staff-admin.bat` (ผู้ดูแลระบบได้อัตโนมัติ · เจ้าหน้าที่ต้องติ๊กให้)

6. ตรวจว่าครบแล้ว **ลบไฟล์ CSV ต้นฉบับ** (ไฟล์นั้นไม่ได้เข้ารหัส — `.gitignore` / `.dockerignore` กันไว้ไม่ให้หลุดขึ้น git/image แล้ว แต่ไม่ควรเก็บต่อ)

**การใช้งาน:**

- เปิดหน้า = ล็อกอยู่เสมอ ต้องใส่**รหัสผ่านที่ใช้ล็อกอิน**ซ้ำ แล้วเปิดได้ 15 นาที (ล็อกเองอัตโนมัติ · กด "ล็อกตอนนี้" ได้)
  ใส่ผิดเกิน 5 ครั้ง ต้องรอ 15 นาที · ตอนล็อกอยู่หน้าเว็บไม่ได้รับข้อมูลอะไรเลย นอกจากจำนวนต่อหมวด
- รหัสในตารางเป็น `••••••••` — กด "ดู" โชว์ 30 วินาทีแล้วซ่อนเอง · "คัดลอก" ลงคลิปบอร์ดโดยไม่ขึ้นจอ · **ทุกครั้งถูกบันทึก**

  ใช้ตอบคำถามว่า "พนักงานที่ลาออกเคยเปิดดูรหัสอะไรบ้าง" → เปลี่ยนเฉพาะรหัสพวกนั้น

  ไม่ผูกตำแหน่งคอลัมน์) · "-" = ไม่มีค่า · แถวที่มีแต่เลขลำดับถูกข้าม · แถวที่มีรหัสแต่ไม่มีชื่อ = นำเข้าด้วยชื่อชั่วคราวแล้วแจ้ง

## การตั้งค่า LINE OA Bot

ต้องมี LINE Business Account + LINE Developers Console (ฟรี) ทำตามนี้:

1. ไปที่ [LINE Developers Console](https://developers.line.biz/console/) → สร้าง Provider (ถ้ายังไม่มี) → สร้าง **Messaging API Channel**
2. ในหน้า channel ที่สร้าง: แท็บ "Basic settings" จะมี **Channel secret** และแท็บ "Messaging API" จะมีปุ่มออก **Channel access token (long-lived)** — copy ทั้งสองค่าไปใส่ใน `.env.local` (`LINE_CHANNEL_SECRET`, `LINE_CHANNEL_ACCESS_TOKEN`)
3. ทำให้ระบบมี URL จริงที่ LINE ยิงเข้ามาได้ **ระบบนี้รันบนเครื่อง Windows ในออฟฟิศ และเปิดทางเข้าด้วย Cloudflare Tunnel** (ไม่ได้ขึ้นคลาวด์ ไม่ต้องเปิด port ที่เราเตอร์) ได้โดเมน `https://it.thanakronpart-time.com` — ดับเบิลคลิก `use-cloudflare.bat` แล้ววาง token ของ tunnel สคริปต์จะต่อ tunnel ตรวจจากข้างนอก แล้วตั้ง Webhook URL ของ LINE เป็น `https://it.thanakronpart-time.com/webhook` ให้เอง (ให้ LINE ยิงทดสอบก่อนเปลี่ยนเสมอ) จากนั้นตรวจว่า **Use webhook** เปิดอยู่
4. ปิด "Auto-reply messages" และ "Greeting messages" ของ LINE Official Account เริ่มต้น (ในหน้า [OA Manager](https://manager.line.biz/)) ไม่งั้นจะชนกับข้อความที่บอทของเราตอบเอง · ส่วน **Chat** เปิดคู่กับ Webhooks ได้ ถ้าจะให้ทีม IT ตอบแชทลูกค้าเองในแอป LINE Official Account (ปุ่ม "คุยกับเจ้าหน้าที่" — ดู [`LINE_SETUP.md`](./LINE_SETUP.md) §8)
5. สร้าง **LIFF app** ในแท็บ "LIFF" ของ channel เดียวกัน: Size = `Full`, Endpoint URL = `https://<โดเมน>/liff/new-ticket` → copy **LIFF ID** ไปใส่ `NEXT_PUBLIC_LIFF_ID` ใน `.env.local` (ต้อง rebuild หลังแก้ค่านี้ เพราะเป็น build-time env)

### ⚠️ เลือกได้แค่ทางเดียว: บอท TypeScript หรือบอท Python

**LINE ตั้ง Webhook URL ได้แค่ 1 อันต่อ channel** ตอนนี้ในโปรเจกต์มีบอท 2 ตัวให้เลือก:

| | บอท TypeScript (เดิม) | **บอท Python (แนะนำ)** |
| --- | --- | --- |
| Webhook URL | `https://<โดเมน>/api/line/webhook` | `https://<โดเมนบอท>/webhook` |
| ความสามารถ | ตอบ FAQ + ส่งลิงก์ไปหน้า LIFF | คุยเก็บข้อมูลครบทุกขั้นตอนแล้วสร้าง ticket ในแชทเลย |
| สร้าง ticket | ต้องเปิดหน้า LIFF กรอกฟอร์ม | จบในแชท ไม่ต้องออกจาก LINE |
| ตอบคำถามข้อมูล | ไม่ได้ | ได้ (สต็อกคงเหลือ, ทรัพย์สินอยู่กับใคร, สถานะ ticket) |
| เข้าใจภาษาไทย | จับ keyword แบบ substring | ตัดคำไทย + TF-IDF + fuzzy (ทนคำพิมพ์ผิด) |

บอท Python อยู่ในโฟลเดอร์ [`line-bot-python/`](./line-bot-python/README.md) — **มีเอกสารการติดตั้งและตั้งค่าครบอยู่ในนั้น**
ถ้าเลือกใช้ตัวนี้ ให้ตั้ง Webhook URL ไปที่ service ของ Python แทน `/api/line/webhook` (route เดิมยังอยู่ ไม่ได้ลบ
เผื่ออยากกลับไปใช้ หรือใช้เป็นตัวอย่างเปรียบเทียบ)

**พฤติกรรมของบอท TypeScript** (`src/lib/line/faq-bot.ts`): เมื่อพนักงานพิมพ์อาการปัญหาเข้ามา บอทจะจับคู่ keyword กับ FAQ
ในระบบก่อนเสมอ (`matchFaqByKeyword`) ถ้าเจอจะตอบวิธีแก้เบื้องต้น พร้อมปุ่มลิงก์ไปหน้า LIFF ให้แจ้งปัญหาต่อถ้ายังไม่หาย
ถ้าไม่เจอ FAQ ที่ตรงกันเลยก็จะส่งปุ่มลิงก์ไปหน้าเดียวกันทันที — การสร้าง ticket จริงเกิดที่หน้า LIFF เท่านั้น

### Internal API สำหรับบอท Python

`/api/internal/*` เป็น endpoint ที่เปิดให้ service ภายนอก (บอท Python) เรียกเข้ามาได้ โดยไม่ต้องมี session ของแอดมิน
ป้องกันด้วย header `x-internal-key` เทียบกับ `INTERNAL_API_KEY` แบบ constant-time (ดู `src/lib/internal-auth.ts`)

| Endpoint | ทำอะไร |
| --- | --- |
| `POST /api/internal/tickets` | สร้าง ticket + ตัดสต็อกให้อัตโนมัติถ้าเป็นการเบิก |
| `GET /api/internal/lookup?kind=stock` | รายการสต็อกพร้อมยอดคงเหลือ |
| `GET /api/internal/lookup?kind=branches` | รายชื่อสาขาที่มีจริง (ใช้ตรวจว่าผู้ใช้พิมพ์สาขาถูกไหม) |
| `GET /api/internal/lookup?kind=equipment&code=` | ค้นทรัพย์สินจากรหัส (ยอมรับรูปแบบ `NB-001` ได้) |
| `GET /api/internal/lookup?kind=ticket&code=` | สถานะของ ticket ตามเลขที่ |
| `GET /api/internal/lookup?kind=my_tickets&line_user_id=` | ticket ทั้งหมดของผู้ใช้ LINE คนนั้น |
| `GET /api/internal/lookup?kind=faq&q=` | จับคู่ FAQ ด้วย keyword |
| `GET /api/internal/lookup?kind=knowledge` | ชุดข้อมูลรวมสำหรับให้ชั้น AI ของบอทสร้างดัชนีค้นหา |

ตรรกะสำคัญทั้งหมด (ออกเลข ticket / ตัดสต็อก / ผูกผู้แจ้ง) อยู่ฝั่งนี้ที่เดียว บอทไม่แตะฐานข้อมูลเอง
เพื่อไม่ให้ต้อง maintain ตรรกะเดียวกัน 2 ภาษา และไม่ให้มี 2 process เขียนข้อมูลชนกัน

ถ้ายังไม่ได้ตั้งค่า `NEXT_PUBLIC_LIFF_ID` หน้า `/liff/new-ticket` จะ**ไม่ล่ม** — ระบบ fallback เป็นฟอร์มให้กรอกชื่อผู้แจ้งเอง
แทนการดึงชื่อจาก LINE Profile อัตโนมัติ ทำให้ทดสอบฟอร์มได้แม้ยังไม่มี LINE channel จริง (เปิด URL ตรงๆ ในเบราว์เซอร์ปกติได้เลย)

## ย้ายจากไฟล์ JSON ไป Postgres

> เอกสารรุ่นก่อนเขียนไว้ว่าจะย้ายไป Supabase — **เปลี่ยนแผนแล้ว** ของจริงคือ Postgres ที่รันเอง
> ใน `docker-compose.yml` เพราะทั้งระบบอยู่บนเครื่องในออฟฟิศ ไม่ได้อยู่บนคลาวด์

**สถานะตอนนี้:** service `db` (postgres:16) รัน healthy อยู่ · schema อยู่ที่ `db/init/001_schema.sql` ·
`src/lib/db/pg.ts` มี connection pool พร้อมใช้ — **แต่ยังไม่มีโมดูลไหน import มันเลย**
ข้อมูลจริงทั้งหมดยังเป็นไฟล์ JSON ใน docker volume `app_data`

**ทำไมควรย้าย:** ตอนนี้ทุก request อ่าน/เขียน**ทั้งไฟล์** และถ้ามี 2 process เขียนพร้อมกันข้อมูลพังได้จริง

**ย้ายยังไง:** ทุกไฟล์ใน `src/lib/db/*.ts` (ยกเว้น `store.ts`) เรียกผ่านฟังก์ชันของ `store.ts` เท่านั้น
ไม่แตะ `fs` ตรงๆ จึงแค่เขียน adapter ใหม่ที่ implement 4 signature เดิม
(`readCollection` · `writeCollection` · `upsertOne` · `patchOne`) ให้คุยกับ Postgres แทนไฟล์ แล้วสลับ import
— **ไม่ต้องแก้โค้ดฝั่ง UI / Server Action / บอท เลยแม้แต่บรรทัดเดียว**

ก่อนขึ้นใช้จริงให้ตั้งสิทธิ์ระดับตารางผูกกับ role ทีม IT ด้วย (ต้นแบบไม่มีชั้นนี้เลย)

ไฟล์รูปที่อัปโหลดจากฟอร์ม FAQ เซฟลง `public/uploads/faq/` ตรงๆ (ไม่ใช่ base64 ในไฟล์ JSON)
ตอนย้ายฐานข้อมูลไม่ต้องแตะส่วนนี้ — ถ้าจะย้ายที่เก็บไฟล์ด้วย ปรับที่ `saveImages()` ใน
`src/app/actions/faq.ts` จุดเดียว

## แจ้งเตือนสถานะ ticket ทาง LINE

เมื่อแอดมินเปลี่ยนสถานะ ticket ระบบจะ push ข้อความกลับไปหาผู้แจ้งทาง LINE ให้อัตโนมัติ
(`src/lib/line/notify.ts` เรียกจาก `changeTicketStatusAction`)

หาตัวผู้รับจาก `meta.line_user_id` ของ ticket ก่อน ถ้าไม่มีจะดูที่ `users.line_user_id` ของผู้แจ้ง
ถ้าไม่เจอทั้งสองทาง (เช่นแอดมินคีย์ ticket เอง) ก็แค่ไม่ส่ง ไม่ถือเป็น error

> ⚠️ **แพ็กเกจฟรีของ LINE OA ส่ง push ได้ 300 ข้อความ/เดือน** (ข้อความ reply ไม่นับ)
> ค่าตั้งต้น `LINE_NOTIFY_STATUSES=resolved,cancelled` จึงส่งเฉพาะตอนจบเรื่อง ("แก้ไขแล้ว" = การ์ดให้คะแนน · "ยกเลิก" = ข้อความธรรมดา)
> = ประมาณ 1 ข้อความต่อ 1 ticket รองรับได้ ~300 ticket/เดือน
> ถ้าอยากให้แจ้งทุกครั้งที่เปลี่ยนสถานะ ตั้ง `pending,resolved,cancelled` · ค่าของระบบเดิม (completed ฯลฯ) ถูกข้ามไปเฉยๆ
> ตั้งเป็นค่าว่างเพื่อปิดการแจ้งเตือนทั้งหมด
> (หน้าต่างอัปเดตสถานะในหน้าแอดมินส่งตามสวิตช์ "แจ้งกลับผ่าน LINE OA" ที่แอดมินเลือก — ค่านี้ใช้กับการแจ้งอัตโนมัติอื่นๆ)

ฟังก์ชันนี้กลืน error ทุกชนิดไว้ข้างในโดยตั้งใจ — LINE ล่มหรือโควตาหมด แอดมินต้องกดเปลี่ยนสถานะได้ตามปกติอยู่ดี

## รูปที่ผู้ใช้ส่งมาในแชท

บอทรับรูปแล้วแนบเข้า ticket ให้อัตโนมัติ (ภาพหน้าจอที่ error คือสิ่งแรกที่คนส่งเวลาเจอปัญหา)
ถ้าส่งรูปมาตอนยังไม่ได้เริ่มแจ้งเรื่อง บอทจะเก็บรูปไว้แล้วเปิด flow ให้เลย ไม่ต้องส่งซ้ำ

เส้นทางของไฟล์: LINE Content API → บอท Python → `POST /api/internal/attachments` → `public/uploads/tickets/`
→ เก็บ URL ไว้ใน `meta.image_urls` → แสดงในแผงรายละเอียดของหน้า `/tickets`

> **ทำไมต้องมี `src/app/uploads/[...path]/route.ts`:** Next.js อ่านรายชื่อไฟล์ในโฟลเดอร์ `public/`
> **แค่ตอนเซิร์ฟเวอร์เริ่มทำงาน** ไฟล์ที่เขียนเพิ่มทีหลังจะได้ 404 จนกว่าจะ restart
> (ยืนยันจริงบน Next.js 16.3.5 standalone แล้ว) — route นี้จึงครอบทั้ง `/uploads/faq/*` และ
> `/uploads/tickets/*` และแก้บั๊กที่รูปแนบ FAQ ไม่ขึ้นมาตลอดไปพร้อมกัน

## วงจรปิดเรื่อง: 3 สถานะ — รอดำเนินการ → แก้ไขแล้ว (ผู้แจ้งให้คะแนน 1–5 ดาว) / ยกเลิก

### 3 สถานะ (21 ต.ค. 2026)

ผู้ใช้ขอให้เรื่องที่แจ้งเข้ามามีแค่ **"รอดำเนินการ"** (`pending`) กับ **"แก้ไขแล้ว"** (`resolved`)
แล้วขอเพิ่ม **"ยกเลิก"** (`cancelled`) กลับมาในวันเดียวกัน — เดิมมี 8 สถานะ (กำลังดำเนินการ · รอข้อมูล ·
รอส่งมอบ · ดำเนินการเสร็จสิ้น · ปิดแล้ว ฯลฯ) ซึ่งทีมไม่ได้แยกใช้จริง และทำให้เรื่องกระจายอยู่หลายแท็บ/หลายหน้า

- **ทีม IT ปิดงานเองได้ทันที** — เลือก **"แก้ไขแล้ว"** ไม่ต้องรอใคร (สวิตช์ "แจ้งกลับผ่าน LINE OA" ติ๊กไว้ให้ก่อน)
- **ผู้แจ้งได้การ์ด "✅ แก้ไขเรียบร้อยแล้ว"** ทาง LINE (1 ข้อความ = 1 push) มีรายละเอียดเรื่อง + หมายเหตุจากทีม IT
  + **ดาว 1–5 ให้คะแนน** + ปุ่ม **"🔁 ยังมีปัญหาอยู่"**
- **ให้ 1–3 ดาว** บอทถามต่อว่าควรปรับปรุงตรงไหน (พิมพ์ตอบ หรือกด "ข้าม") — 4–5 ดาวขอบคุณแล้วจบ
- **"ยังมีปัญหาอยู่"** (กดได้ภายใน 14 วันหลังปิดงาน) → เรื่องกลับเป็น **รอดำเนินการ** + แจ้งทีม IT ทาง LINE
  (`LINE_ADMIN_USER_IDS`) + บอท **เงียบให้เจ้าหน้าที่คุยต่อ** ในแอป LINE OA (ดูหัวข้อถัดไป)
  เกิน 14 วันบอทบอกให้แจ้งเรื่องใหม่ — กันการ์ดเก่าในห้องแชทดึงเรื่องที่ปิดไปนานแล้วกลับมาเปิด
- **"ยกเลิก"** = ปิดเรื่องโดยไม่ได้แก้ (แจ้งซ้ำ / แจ้งผิด / ผู้แจ้งขอยกเลิก) — ใส่เหตุผลในหมายเหตุ ·
  ผู้แจ้งได้**ข้อความธรรมดา** "❌ เรื่องนี้ถูกยกเลิก" + หมายเหตุ (ไม่มีดาว — ไม่มีงานให้ประเมิน · ติ๊กส่งไว้ให้ก่อน เอาออกได้) ·
  **ไม่มีวันปิดงาน/ระยะเวลา ไม่นับในสรุปคะแนน** · คะแนนของรอบที่เคยปิดถูกถอด · ผู้แจ้งกด "ยังมีปัญหาอยู่" กับเรื่องที่ยกเลิกไม่ได้
  (บอทบอกสถานะแล้วให้แจ้งเรื่องใหม่) · ทีม IT เปลี่ยนกลับเป็นรอดำเนินการเองได้ถ้ายกเลิกผิด
- **การ์ดยืนยันรุ่นเก่า** (ก่อน ต.ค. 2026) ที่ยังค้างในห้องแชทยังกดได้: "ยังไม่หาย" = เปิดเรื่องกลับ · "เรียบร้อยแล้ว" = ไม่เกิดอะไร (ปิดอยู่แล้ว)

**ข้อมูลเดิมแปลงให้อัตโนมัติ** ตอนอ่านครั้งแรกหลังอัปเดต (`migrateLegacyStatuses()` ใน `src/lib/db/tickets.ts`
— ทำตอนอ่าน ไม่ใช่สคริปต์ครั้งเดียว เพราะไฟล์ที่กู้จาก `backups/` ก็ยังเป็นสถานะเดิม):

| สถานะเดิม | → |
| --- | --- |
| รอดำเนินการ · กำลังดำเนินการ · รอข้อมูล · รอส่งมอบ | **รอดำเนินการ** |
| แก้ไขแล้ว · ดำเนินการเสร็จสิ้น · ปิดแล้ว | **แก้ไขแล้ว** |
| ยกเลิก | **ยกเลิก** (คงเดิม) |

ทุกเรื่องที่แปลงได้บรรทัดในประวัติ + ไทม์ไลน์ว่าเดิมเป็นสถานะอะไร (ผู้ทำ = "ระบบ") · คะแนน/วิธีแก้เดิมอยู่ครบ
· ไม่มีสถานะ "รอข้อมูล" ที่สั่งบอทเงียบอัตโนมัติแล้ว — จะคุยกับผู้แจ้งเองให้กด "รับแชทต่อเอง"

> **ประวัติของ 3 เรื่องที่เคยยกเลิก:** ช่วงที่ระบบมี 2 สถานะ (เช้า 21 ต.ค. 2026) ถูกแปลงเป็น "แก้ไขแล้ว" ตามที่ผู้ใช้เลือกตอนนั้น
> พอเพิ่ม "ยกเลิก" กลับ จึงคืนเป็นยกเลิกด้วยสคริปต์ครั้งเดียวบนเครื่องจริง — ประวัติของเรื่องพวกนี้จึงมี 2 บรรทัดของระบบ
> (ยกเลิก → แก้ไขแล้ว → ยกเลิก) ซึ่งตั้งใจ ไม่ใช่บั๊ก

### หน้า Tickets = ที่เดียวของงานแจ้งเรื่อง (รวม "แก้ไขปัญหาแล้ว" + "ประวัติซ่อม" เข้ามา 21 ต.ค. 2026)

แท็บ **ทั้งหมด / รอดำเนินการ / แก้ไขแล้ว / ยกเลิก** · ลิงก์เก่า `/resolved` → `/tickets?status=resolved` ·
`/repair-history` → `/tickets?type=repair` · `/completed` → `/tickets?status=resolved`

- **ประวัติซ่อม** = เลือกประเภท "แจ้งซ่อม" — มีคอลัมน์ทรัพย์สิน ค่าซ่อม และยอดค่าซ่อมรวมบนหัวหน้า
- **สรุปคะแนน** (แท็บทั้งหมด/แก้ไขแล้ว) คะแนนเฉลี่ย · % พึงพอใจ (4–5 ดาว) · ตอบแบบประเมินกี่เรื่อง ·
  จำนวนเรื่องที่ได้ 1–3 ดาว (กดเพื่อดูเฉพาะเรื่องเหล่านั้น) — คิดจากตัวกรองอื่นที่เลือกอยู่
- **คอลัมน์คะแนน** ★★★★☆ + 💬 · ตัวกรอง "ทุกคะแนน / 1–3 / 4–5 / ยังไม่ให้คะแนน" · คอลัมน์ "วันที่แจ้ง / ปิดงาน" + ระยะเวลาที่ใช้
- **กรองช่วงวันที่ได้ 2 แบบ** ตามวันที่แจ้ง ("เดือนนี้มีคนแจ้งกี่เรื่อง") หรือตามวันที่ปิดงาน ("เดือนนี้ปิดไปกี่เรื่อง")
- **แผงรายละเอียด** สรุปเวลา/ค่าใช้จ่าย · อาการ · วิธีแก้ · ความพึงพอใจ + ความเห็น · อะไหล่ที่เบิก · รูป · การเปิดดู · ไทม์ไลน์ทุกขั้น · รับแชทต่อ
- **Export Excel (.xlsx)** แทน CSV — ทุกแถวที่ผ่านตัวกรอง เรียงเหมือนบนจอ (ไม่ใช่แค่หน้าที่เปิดอยู่) · ชีต "Tickets"
  (22 คอลัมน์ · วันที่เป็นวันที่จริงของ Excel ตามเวลาไทย · ค่าซ่อม/คะแนน/ชั่วโมงเป็นตัวเลขจริง · มีปุ่มกรองบนหัวตาราง)
  + ชีต "สรุป" (ตัวกรองที่ใช้ · จำนวนแต่ละสถานะ · ค่าซ่อมรวม · คะแนนเฉลี่ย · อัตราการตอบ) — `src/lib/ticket-export.ts`

> ค่าเฉลี่ยคิดจากเรื่องที่ให้คะแนนแล้วเท่านั้น — ไม่นับ "ยังไม่ให้คะแนน" เป็น 0 ดาว (คนที่ไม่กดไม่ได้แปลว่าไม่พอใจ)
> จึงต้องดูคู่กับอัตราการตอบเสมอ: เฉลี่ย 5.0 จาก 2 คนในร้อยเรื่องไม่ได้แปลว่าบริการดี

### รายละเอียดที่ไม่ได้มาฟรี

- **ตาราง `ticket_events` แยกจาก ticket** — ไทม์ไลน์คือของที่เพิ่มเรื่อยๆ ส่วน ticket คือสถานะล่าสุด
  การให้คะแนนทุกครั้งบันทึกเป็น event `rated` (กดดาวเดิมซ้ำไม่บันทึกซ้ำ)
- **เปลี่ยนสถานะกับบันทึก log อยู่ในฟังก์ชันเดียว** (`changeTicketStatus`) ไม่แยก
  และประวัติสถานะเก็บ `role` (admin/requester/system) ไว้ด้วย — ไม่งั้นแยกไม่ออกว่าชื่อคนปิดงานเป็นช่าง
  ลูกค้า (กดเปิดกลับ / การ์ดเก่า) หรือระบบ (แปลงสถานะเดิม) · ประวัติของเรื่องเก่ายังมีสถานะเดิมปนอยู่ แสดงผลด้วย
  `statusLabel()` (`src/lib/ticket-status.ts`) ซึ่งรู้จักชื่อสถานะเดิมทั้งหมด
- **ให้คะแนน/เปิดเรื่องกลับได้เฉพาะผู้แจ้งคนนั้น** เช็คจาก LINE user id ไม่ใช่แค่รู้เลขที่ตั๋ว
  (`ticketOwnerLineId()` ที่เดียว ใช้ทั้งตอนส่งแจ้งเตือนและตอนตรวจสิทธิ์กดปุ่ม)
- **เกณฑ์ "คะแนนต่ำ" อยู่ฝั่ง Next.js ที่เดียว** (`src/lib/ticket-feedback.ts`) — API ตอบ `ask_comment` ให้บอททำตาม
- **เปิดเรื่องกลับแล้วคะแนนรอบเดิมถูกถอดออกจากเรื่อง** (ยังอยู่ในไทม์ไลน์) — ไม่งั้นพอปิดรอบใหม่
  หน้า log จะโชว์คะแนนของงานที่ยังไม่หายเหมือนเป็นคะแนนของงานที่แก้เสร็จแล้ว
- **แจ้งทีม IT ตอนเปิดเรื่องกลับใช้ `after()`** ของ Next.js — ตอบบอทก่อนแล้วค่อย push
  ถ้ารอ LINE ใน request บอทอาจ timeout แล้วบอกผู้แจ้งว่าระบบขัดข้อง ทั้งที่เปิดเรื่องสำเร็จแล้ว
- **กดได้แม้ session หมดอายุ** การ์ดเด้งมาตอนผู้ใช้ไม่ได้เปิดแชท กว่าจะมากดอาจผ่านไปหลายชั่วโมง
- **`resolved_at` = ทีม IT ทำเสร็จเมื่อไหร่** · `meta.completed_at` = ปิดงานรอบล่าสุดเมื่อไหร่ (ใช้คิดเพดาน 14 วัน
  — ชื่อฟิลด์มาจากระบบเดิม) · เพิ่มหมายเหตุให้เรื่องที่ปิดแล้วไม่ทับวันเดิม (ระยะเวลาในรายงานจะไม่ยาวขึ้นเอง)
- **ไฟล์ Excel กันสูตร** — ความเห็น/อาการมาจากข้อความที่ใครก็พิมพ์ในแชทได้ ทุกช่องข้อความเก็บเป็นชนิด "ข้อความ"
  ค่าที่ขึ้นต้นด้วย `= + - @` จึงไม่ถูกรันเป็นสูตรตอนแอดมินเปิดไฟล์ (`tests/tickets-board.test.cjs` ตรวจ)
- **วันที่ในไฟล์ Excel คำนวณเป็นเวลาไทยเอง** ไม่ส่ง Date ให้ไลบรารี — ไม่งั้นเครื่องที่ตั้งเวลา UTC ได้ไฟล์ที่เร็วไป 7 ชม.

## เจ้าหน้าที่รับแชทต่อเอง (บอทหยุดตอบผู้แจ้งคนนั้น)

**LINE ไม่ส่ง webhook ตอนเจ้าหน้าที่ตอบแชทในแอป LINE Official Account** — บอทเห็นแค่ข้อความฝั่งผู้ใช้
จึงรู้เองไม่ได้ว่ามีคนกำลังคุยอยู่ แล้วโผล่มาตอบแทรก (เช่นตีความคำตอบของผู้ใช้เป็นเรื่องใหม่แล้วถามสาขา)
ระบบจึงให้สลับเป็น "โหมดเจ้าหน้าที่" จากทางที่เราเห็นแทน:

| ทาง | เกิดอะไรขึ้น |
| --- | --- |
| ปุ่ม **"👤 รับแชทต่อเอง"** ในแผงรายละเอียดของ ticket (หน้า Tickets) | บอทเงียบกับผู้แจ้งคนนั้น `HANDOFF_HOURS` ชม. (24) — กด **"🤖 คืนให้บอทตอบ"** เพื่อยกเลิก |
| ผู้แจ้งกด **"ยังมีปัญหาอยู่"** | บอทเงียบเอง และบอกผู้แจ้งว่าเจ้าหน้าที่จะคุยต่อในแชทนี้ |
| ผู้แจ้งกด **"คุยกับเจ้าหน้าที่"** (มีอยู่เดิม) | เหมือนเดิม |

ระหว่างนั้นทุกข้อความของผู้แจ้งค้าง **ยังไม่อ่าน** ในแอป LINE OA ให้เจ้าหน้าที่เห็น และเวลาต่อออกไปเองทุกครั้งที่ผู้แจ้งพิมพ์
บอทกลับมาเองเมื่อผู้แจ้งกดเมนู/"กลับไปใช้บอท" หรือเงียบครบเวลา · ทุกครั้งที่กดรับ/คืนถูกบันทึกในไทม์ไลน์ของ ticket

ทางเดินคำสั่ง: หน้าแอดมิน → `src/lib/line/bot-handoff.ts` → `POST {LINE_BOT_INTERNAL_URL}/internal/handoff`
(`/end` · `/status`) ที่บอท Python — ใน compose ตั้ง `LINE_BOT_INTERNAL_URL=http://bot:8000` ให้แล้ว
เส้นนี้ไม่เปิดสู่อินเทอร์เน็ต (Cloudflare Tunnel ส่งเข้าบอทเฉพาะ `^/webhook`) และตรวจ `x-internal-key` ทุกครั้ง
Chat ใน OA Manager ปิดอยู่ = บอทปฏิเสธ (409 `chat_off`) เพราะไม่มีใครเห็นแชท

## เปิด/ปิดบอทจากแชท LINE (ทีม IT พิมพ์ "แอดมิน") — 13 ต.ค. 2026

ทีม IT ที่แอดมินอนุมัติแล้ว (หน้า **💬 บอท LINE**) พิมพ์ **`แอดมิน`** หาบอทจาก LINE ของตัวเอง ได้การ์ดที่
**ปิด/เปิดบอทรายคน** (เลือกจากชื่อ LINE ของคนที่ทักมาล่าสุด) หรือ **ปิดทั้งระบบ** — ขอสิทธิ์ด้วยการพิมพ์ **`ขอสิทธิ์แอดมิน`**

| | คุยกับเจ้าหน้าที่ / รับแชทต่อเอง | ปิดบอท (การ์ดแอดมิน) |
| --- | --- | --- |
| ใครสั่ง | ผู้ใช้กดเอง · ปุ่มบน ticket | ทีม IT ที่ได้รับสิทธิ์ (หรือหน้า "บอท LINE") |
| หมดเมื่อไหร่ | 24 ชม. หลังข้อความล่าสุด · ผู้ใช้กดเมนู | **จนกว่าทีม IT จะกดเปิด** (ผู้ใช้เปิดเองไม่ได้) |
| ผู้ใช้เห็นอะไร | ข้อความส่งต่อ 1 ครั้ง | "เจ้าหน้าที่ IT ตอบแชทนี้เอง" **วันละ 1 ครั้ง** แล้วเงียบ |

คนที่ไม่ได้รับสิทธิ์พิมพ์ "แอดมิน" = ขอคุยกับเจ้าหน้าที่ตามเดิม · ปุ่ม "🤖 คืนให้บอทตอบ" บน ticket เปิดบอทคืนให้ด้วย ·
รายละเอียดและวิธีตั้งค่าอยู่ที่ [`LINE_SETUP.md`](./LINE_SETUP.md) §9

### ทำไมต้อง "ซิงก์" ไม่ใช่แค่ seed

`readCollection()` ใน `db/store.ts` รัน seed เฉพาะตอน **ยังไม่มีไฟล์** แต่เครื่องที่ใช้งานอยู่จริง
มี `data/users.json` อยู่แล้วเสมอ (และอยู่บน docker volume `app_data` ที่ไม่ถูกลบตอน deploy)
การแก้ `seed()` เฉยๆ จึงไม่มีผลกับใครเลยสักคน — อาการคือ "อัปเดตโค้ดแล้วแต่รายชื่อยังเป็นชุดเดิม"
ซึ่งหาสาเหตุยากมากเพราะโค้ดดูถูกทุกบรรทัด

`ensureEmployeeRegistry()` จึงรวมทะเบียนเข้ากับของเดิมให้ ครั้งเดียวต่อ 1 ค่า `EMPLOYEE_REGISTRY_VERSION`
(เก็บ marker ไว้ที่ `data/registry_meta.json`) ราคาของการเรียกซ้ำคืออ่านไฟล์เล็ก 1 ไฟล์ + เทียบสตริง
จึงเรียกได้ทุก request

**กติกาการเขียนทับ**

| ช่อง | ใครชนะ |
| --- | --- |
| ทะเบียนมีค่า (ชื่อ/ฝ่าย/ตำแหน่ง/ระดับ/บริษัท) | ทะเบียน — HR เป็นเจ้าของข้อมูลนี้ |
| ทะเบียนเป็น `null` | ของเดิมในระบบ — ไม่งั้นฝ่ายที่แอดมินเติมให้ 193 คนนั้นจะถูกล้างทุกครั้งที่ซิงก์ |
| `line_user_id` / `email` / `id` / `created_at` | ระบบ — ทะเบียนไม่แตะเด็ดขาด |

> **แก้ทะเบียนแล้วต้องขยับ `EMPLOYEE_REGISTRY_VERSION` ด้วยเสมอ** ไม่งั้นเครื่องที่ซิงก์ไปแล้วจะข้ามรอบใหม่ไปเงียบๆ

ครั้งแรกของแต่ละบัญชี LINE บอทถาม "ผู้แจ้งคือใครครับ?" แล้วรับได้ทั้ง **ชื่อจริง / ชื่อเล่น / รหัสพนักงาน**
(ค้นในหน่วยความจำฝั่งบอทจากก้อน `knowledge` ที่ cache ไว้ 5 นาที + `rapidfuzz` รับคำพิมพ์ผิด)
เจอคนเดียว → ให้กดยืนยัน · เจอหลายคน → ให้เลือก · ไม่เจอ → กด "ใช้ชื่อที่พิมพ์" แจ้งต่อได้เลย

> **28 ก.ย. 2026 — ปิดเมนู "เลือกจากรายชื่อ" ไว้ชั่วคราว** ขั้นระบุผู้แจ้งให้พิมพ์ชื่อเอาเองอย่างเดียว
> โค้ดเมนูยังอยู่ครบหลังธง `REQUESTER_PICKER_ENABLED` ใน `line-bot-python/app/messages.py`
> เปิดกลับ = แก้เป็น `True` บรรทัดเดียว · ปุ่มเก่าที่ค้างในห้องแชทกดแล้วถอยไปหน้าพิมพ์ชื่อให้เอง


**ครั้งที่ 2 เป็นต้นไปข้ามขั้นนี้ทั้งขั้น** — ขั้นถามรายละเอียดจะขึ้นบรรทัด `👤 แจ้งในชื่อ: ...`
พร้อมปุ่ม "เปลี่ยนคนแจ้ง" รายละเอียดการออกแบบและเหตุผลรายข้ออยู่ใน [`LINE_INTAKE.md`](./LINE_INTAKE.md)

**การเบิกจบทันทีหลังยืนยันผู้เบิก** (30 ก.ย. 2026) — ไม่มีขั้น "มีรายละเอียดเพิ่มเติมไหม" แล้ว
บัญชีที่ผูกไว้จะเห็นการ์ด "ผู้เบิกคือคนนี้ใช่ไหม" ให้กดยืนยันครั้งเดียว พร้อมปุ่ม "ไม่ใช่ เปลี่ยนคน"

ticket ที่สร้างจะส่ง `requester_user_id` มาด้วย จึงผูกกับ **แถวเดิม** ของคนนั้นเสมอ
ไม่ใช่ "หาจากชื่อ ถ้าไม่เจอสร้างใหม่" แบบเดิมที่ทำให้ชื่อสะกดต่างกันนิดเดียวกลายเป็นคนละคน

### กันสร้าง ticket ซ้ำตอนกด "ลองส่งใหม่"

บอทส่ง `request_id` (เกิดพร้อม session คงเดิมตลอดแม้ผ่าน Redis) `initial_message`
และ `equipment_id` ไปกับทุก ticket หลังบ้านเจอคู่ `(request_id, line_user_id)` ซ้ำจะคืน
ticket เดิมแทนการสร้างใหม่ จึงไม่ได้ 2 ใบและไม่ตัดสต็อกซ้ำเมื่อ timeout หลังเขียนข้อมูลไปแล้ว

`equipment_id` สำคัญเพราะรหัสทรัพย์สินในข้อมูลจริงซ้ำกันอยู่ 28 แถว — ทุกทางเข้า
(พิมพ์รหัสเอง / ไล่เมนู / AI จับรหัสจากประโยคแรก) ผ่าน `_resolve_asset_code` ตัวเดียวกัน
จึงถามว่า "เครื่องไหน" เหมือนกันหมด และได้ `equipment_id` ติดไปกับ ticket เสมอ

## เลือกทรัพย์สินในแชท LINE แบบไล่กรองทีละชั้น

ตอนบอทถามรหัสทรัพย์สิน ผู้ใช้ไม่ต้องจำรหัสเองแล้ว — กดเลือกไล่ลงไปทีละชั้น:

**ประเภท → ยี่ห้อ/รุ่น → รหัสทรัพย์สิน**

แต่ละชั้นแสดงจำนวนของที่เหลือหลังกรอง และชั้นสุดท้ายแสดง ยี่ห้อ · ที่ติดตั้ง · ผู้ครอบครอง
ใต้รหัสแต่ละอัน — **จำเป็นมากกับข้อมูลชุดนี้เพราะรหัสทรัพย์สินซ้ำกันอยู่ 28 แถว**
ถ้าโชว์แต่รหัส ผู้ใช้จะเลือกเครื่องผิดสาขาโดยไม่มีทางรู้เลย

### ทำไมต้องไล่ทีละชั้น แทนที่จะทำ dropdown จริง

**แชท LINE ไม่มี `<select>` ให้ใช้** ตัวเลือกที่มีจริงมีแค่:

| วิธี | เพดาน | ใช้ได้ไหมกับของ 200+ ชิ้น |
| --- | --- | --- |
| Quick reply | 13 ปุ่ม | ไม่ได้ |
| Flex carousel | 12 ใบ | ไม่ได้ |
| Rich menu | ตายตัว เปลี่ยนตามข้อมูลไม่ได้ | ไม่ได้ |
| LIFF (หน้าเว็บใน LINE) | ได้ dropdown จริง | ได้ แต่ต้องตั้ง LIFF ก่อน (ดูข้อ 5 ใน LINE_SETUP.md) |

การไล่กรองทีละชั้นจึงเป็นวิธีเดียวที่พาคนไปถึงเครื่องที่ต้องการได้ในไม่กี่ปุ่ม
โดยไม่ต้องตั้ง LIFF ก่อน — 14 ประเภท → ไม่กี่ยี่ห้อ → ไม่กี่รหัส

### รายละเอียดที่ไม่ได้มาฟรี

- **ปุ่มส่งกลับมาแค่ "ลำดับที่" ไม่ใช่ค่าจริง** เพราะ postback data ของ LINE จำกัด **300 ไบต์**
  ชื่อรุ่นภาษาไทย encode แล้วกินตัวละ 9 ไบต์ ยาวหน่อยก็ทะลุ แล้วปุ่มจะพังเงียบๆ ไม่มี error ให้เห็น
  ค่าจริงเก็บไว้ใน session (`pick_values`) — มีเทสต์คุมไว้ว่าทุกปุ่มต้องไม่เกิน 300 ไบต์
- **แถวในเมนูใช้ `box` ที่มี action ไม่ใช่ `button`** เพราะ label ของปุ่มจำกัด 20 ตัวอักษร
  ซึ่งสั้นเกินไปสำหรับภาษาไทย ("คอมพิวเตอร์ตั้งโต๊ะ" อย่างเดียวก็ 19 ตัวแล้ว)
- **หน้าละ 8 แถว** — การ์ดที่ยาวเกินจอทำให้ปุ่มท้ายการ์ดถูกดันตกขอบ แล้วคนจะไม่เลื่อนลงไปกด
- **ทางออกอยู่ใน quick reply ด้วย ไม่ใช่มีแค่ในการ์ด** (`⌨️ พิมพ์รหัสเอง` / `ไม่มี/ไม่ทราบ`)
  quick reply ปักอยู่เหนือแป้นพิมพ์เสมอ กดได้ทันทีไม่ว่าจะเลื่อนการ์ดไปถึงไหน
- **คนที่รู้รหัสอยู่แล้วพิมพ์ได้เลย** ไม่ต้องไล่กด 3 ชั้น — ทั้งสองทางใช้โค้ดตัวเดียวกัน
  (`_resolve_asset_code`) จะได้ไม่มีทางที่สองทางนี้ทำงานไม่เหมือนกัน
- **กดจากการ์ดเก่าที่ลำดับไม่ตรงกับ session แล้ว → เริ่มเลือกใหม่ ไม่เดาต่อ**
  (ผู้ใช้เลื่อนขึ้นไปกดการ์ดเก่าเป็นเรื่องปกติมาก ถ้าเดาจะได้ทรัพย์สินผิดเครื่อง)
- **ปุ่มย้อนกลับล้างตัวกรองชั้นที่ลึกกว่าเสมอ** ไม่งั้นเปลี่ยนประเภทแล้วยังโดนกรองด้วยยี่ห้อเดิมอยู่เงียบๆ
- **หลังบ้านล่ม → ตกกลับไปให้พิมพ์รหัสเอง** ไม่ใช่ตันอยู่ตรงนั้น
- **จงใจไม่กรองตามสาขาที่เลือกไว้ตอนต้น** เพราะ `install_location` ในข้อมูลจริงปนกันทั้งชื่อสาขา
  ("สาขาเซ็นทรัล") และชื่อแผนก/ห้อง ("แผนกบัญชี", "คลัง IT") กรองแล้วจะซ่อนของที่ควรเห็น
  โดยผู้ใช้ไม่รู้ตัว — แสดงที่ติดตั้งไว้ในบรรทัดรองแทน

API: `GET /api/internal/lookup?kind=asset_options&level=category|brand|code[&category=..&brand=..]`

## ปุ่ม "เช็คสถานะเรื่องนี้" และ log การเปิดดู

### บั๊กที่แก้: ปุ่มนี้ไม่เคยทำงานเลย

`flex.py` สร้างปุ่ม `a=ticket&code=...` ไว้บนการ์ด "รับเรื่องแล้ว" ตั้งแต่แรก แต่ `flow.py`
**ไม่มี handler ของ action นี้** กดแล้วจึงตกไปท้ายบล็อก postback ได้เมนูเปล่าๆ
หรือถ้า session หมดอายุ (ซึ่งเป็นกรณีปกติ เพราะคนกดจากการ์ดเก่าหลายวันให้หลัง) ได้ข้อความ
"หมดเวลา" — จากมุมผู้ใช้คือปุ่มที่เด่นที่สุดบนการ์ดนั้นเสีย

ตอนนี้กดแล้วได้การ์ดสถานะจริง และใช้ได้แม้ session หมดอายุไปแล้ว

### ⚠️ เรื่อง IP ที่ต้องเข้าใจก่อนใช้ข้อมูลนี้

**LINE ไม่ส่ง IP ของมือถือพนักงานมาให้ และไม่มีทางทำให้ส่งได้**

ตอนพนักงานกดปุ่มในแชท มือถือของเขาคุยกับเซิร์ฟเวอร์ LINE เท่านั้น **ไม่เคยต่อมาที่เครื่องเราเลย**
LINE รับการกดไว้แล้วยิง webhook มาจากเซิร์ฟเวอร์ของตัวเอง ค่า `ip` ที่บันทึกได้จึงเป็น
IP ของ LINE (หรือของ Cloudflare/Caddy ที่คั่นอยู่หน้าบ้าน) — มีประโยชน์สำหรับตรวจว่า
request มาจาก LINE จริงไหม แต่**ห้ามเอาไปอ้างว่าเป็นเครื่องของพนักงาน**

ระบบจึงเก็บฟิลด์ `ip_note` ติดไปกับทุกแถว เขียนกำกับตรงๆ ว่า IP นั้นเป็นของใคร
และหน้าแอดมินแสดงคำกำกับนี้ต่อท้ายเลข IP เสมอ

ตัวที่ระบุ "ใครกด" ได้จริงคือ `line_user_id` → แมปกลับเป็นชื่อพนักงาน ซึ่งแม่นกว่า IP มาก
ถ้าต้องการ IP ของเครื่องจริงๆ ต้องเปลี่ยนปุ่มไปเปิดหน้าเว็บ (LIFF) แทน postback —
`source: "liff"` เตรียมไว้ในโครงสร้างข้อมูลแล้ว

### สิ่งที่เกิดขึ้นเมื่อมีคนกด

1. บอทตอบการ์ดสถานะจริงกลับไป
2. บันทึกลง `data/ticket_views.json` — ใครกด · เมื่อไหร่ · เรื่องไหน · จากทางไหน · IP + คำกำกับ
3. ถ้าคนกดคือผู้แจ้งเอง บันทึก `meta.acknowledged_at` ลง ticket = **"ผู้แจ้งรับทราบแล้ว"**
   (จงใจ**ไม่**เปลี่ยน `status` เพราะ status เป็นของทีม IT ว่า "งานถึงไหนแล้ว"
   ส่วนการที่ผู้แจ้งเปิดดูเป็นคนละเรื่อง — ถ้ารวมกัน ticket ที่ยังซ่อมไม่เสร็จจะเปลี่ยนสถานะเอง
   เพียงเพราะมีคนกดดู ซึ่งผิด)
4. หน้า `/tickets` ขึ้นคอลัมน์ "ผู้แจ้งดู" (👁 N ครั้ง / ยังไม่ได้ดู) เรียงลำดับได้
   และแผงรายละเอียดแสดง log 10 ครั้งล่าสุด
5. push แจ้งทีม IT ทาง LINE ถ้าตั้ง `LINE_ADMIN_USER_IDS` ไว้

### ทำไมถึงแจ้งเฉพาะครั้งแรก

push แจ้งทีม IT ส่ง**เฉพาะครั้งแรกที่แต่ละคนเปิดดูแต่ละเรื่อง** ครั้งต่อๆ ไปยังบันทึกลง log ครบ
แต่ไม่ push — เพราะโควตาแพ็กเกจฟรีคือ 300 ข้อความ/เดือน (ก้อนเดียวกับการแจ้งสถานะ ticket)
และการกดซ้ำๆ ระหว่างรอคือพฤติกรรมปกติของคนที่รีบ ถ้า push ทุกครั้งโควตาจะหมดภายในไม่กี่วัน

ข้อความที่บอทตอบกลับจึงเขียนให้ตรงกับที่เกิดขึ้นจริง: ครั้งแรกบอก "แจ้งทีม IT แล้ว"
ครั้งต่อไปบอก "บันทึกแล้วว่าคุณเปิดดู" — ไม่หลอกว่ามีคนได้รับแจ้งทุกครั้ง

### ข้อจำกัดอื่นที่รู้ตัว

- ตาราง log เก็บสูงสุด **5,000 แถวล่าสุด** แล้วตัดของเก่าทิ้ง เพราะ `store.ts` อ่านทั้งไฟล์
  เข้าหน่วยความจำทุก request — ปล่อยให้โตไม่จำกัดแล้ววันหนึ่งหน้า `/tickets` จะช้าลงเรื่อยๆ
  โดยไม่มีใครรู้สาเหตุ
- ถ้าบันทึก log ล้มเหลว ผู้ใช้**ยังได้คำตอบสถานะตามปกติ** (log เป็นเรื่องของทีม IT
  ส่วนคำตอบเป็นเรื่องของคนที่กด ความสำคัญคนละระดับ)

ตั้งค่า: `LINE_ADMIN_USER_IDS` ใน `.env` (เว้นว่าง = ไม่ push แค่ขึ้นในหน้าแอดมิน)
ตรวจว่าทำงาน: `curl.exe http://127.0.0.1:3000/api/health` → `features.ticket_view_log`
และ `features.viewed_push_recipients`

## เรียงลำดับและกรองข้อมูลในตาราง

ทุกตารางในระบบ (Tickets · ทรัพย์สิน · ผู้ครอบครอง · สต็อก · ประวัติ Transaction)
ใช้ชุดเดียวกัน: [`src/lib/sorting.ts`](./src/lib/sorting.ts) ·
[`src/components/ui/SortControl.tsx`](./src/components/ui/SortControl.tsx) ·
[`src/components/ui/Filters.tsx`](./src/components/ui/Filters.tsx)

### บั๊กที่แก้ไปพร้อมกัน — เรื่องใหม่เคยไปอยู่ล่างสุด

`listTickets()` และ `listEquipment()` เคยคืนข้อมูล **ตามลำดับในไฟล์ JSON ตรงๆ**
แต่ `store.ts` เขียนของใหม่ด้วย `all.push(item)` คือต่อท้ายไฟล์เสมอ
ผลคือ ticket ที่พนักงานเพิ่งแจ้งผ่าน LINE ไปโผล่ **แถวล่างสุดของหน้าสุดท้าย**

อาการนี้ซ่อนตัวอยู่นานเพราะข้อมูลชุดตั้งต้น (seed) บังเอิญเรียงมาแล้ว หน้าเว็บจึง "ดูถูก"
มาตลอดจนกว่าจะมีเรื่องแจ้งเข้ามาจริง ตอนนี้เรียงใหม่→เก่าตั้งแต่ชั้น db แล้ว

### 2 ทางให้ผู้ใช้เลือก (ตั้งใจให้มีทั้งคู่)

| วิธี | ใช้ตอนไหน |
| --- | --- |
| **คลิกหัวคอลัมน์** มีลูกศร ▲▼ บอกทิศ คลิกซ้ำเพื่อสลับ | เร็วสำหรับคนที่ชินกับ Excel |
| **ปุ่ม "เรียงตาม …" + ปุ่มสลับทิศ** ข้างช่องค้นหา | จำเป็นบนมือถือ เพราะตารางต้องเลื่อนแนวนอน หัวคอลัมน์ที่อยากเรียงมักอยู่นอกจอ |

ค่าที่เลือกถูกจำไว้แยกตามหน้าใน `localStorage` (`itadmin:sort:<หน้า>`)
อ่านค่าด้วย `useSyncExternalStore` ไม่ใช่ `useEffect + setState` เพื่อไม่ให้ HTML ฝั่งเซิร์ฟเวอร์
กับฝั่งเบราว์เซอร์ไม่ตรงกัน (hydration mismatch)

### ค่าตั้งต้นของแต่ละหน้า

| หน้า | เรียงตาม | ทำไม |
| --- | --- | --- |
| Tickets · ประวัติ Transaction | วันที่ **ล่าสุด → เก่าสุด** | คนเปิดมาเพื่อดูเรื่องใหม่ |
| ทรัพย์สิน | วันที่เพิ่มเข้าระบบ ล่าสุดก่อน | ดูของที่เพิ่งลงทะเบียน/เพิ่ง import |
| ผู้ครอบครอง | วันที่เริ่มถือครอง ล่าสุดก่อน | ตอบคำถาม "ใครเพิ่งรับเครื่องไป" |
| สต็อก | **ชื่อรายการ ก → ฮ** | ตารางนี้ไม่มีคอลัมน์วันที่ และคนใช้เพื่อ "หาของที่รู้ชื่ออยู่แล้ว" (เลือก "ความเร่งด่วน" ในปุ่มเรียงเพื่อดันของใกล้หมดขึ้นบนได้) |

### รายละเอียดที่ไม่ได้มาฟรี

- **ค่าว่างไปท้ายเสมอ** ไม่ว่าเรียงขึ้นหรือลง — สำคัญมากเพราะค่าซ่อม/ราคาซื้อเป็น `null` ได้เยอะ
  ถ้านับ `null` เป็น 0 เวลาเรียง "ค่าซ่อมมากไปน้อย" จะได้แถวว่างกองกลางตาราง ดูเหมือนข้อมูลพัง
- **เรียงตามความหมาย ไม่ใช่ตามตัวอักษร** — สถานะ ticket เรียงตามลำดับขั้นการทำงาน
  (ไม่งั้น "ยกเลิก" จะลอยขึ้นต้นเพราะขึ้นด้วย ย) · "ถือครองมาแล้ว" เรียงตามวันที่จริง
  ไม่ใช่ข้อความที่แสดง (ไม่งั้น "10 เดือน" จะมาก่อน "2 ปี")
- **ภาษาไทยใช้ `localeCompare(…, "th")`** ไม่ใช่เทียบรหัส Unicode ซึ่งลำดับไม่ตรงกับที่คนไทยคาด
- **ลำดับการทำงานคือ กรอง → เรียง → ตัดหน้า** สลับไม่ได้ ถ้าตัดหน้าก่อนเรียงจะกลายเป็น
  "เรียงเฉพาะแถวในหน้านี้" ซึ่งดูเหมือนทำงานแต่ผิดสนิท
- **เปลี่ยนการเรียงแล้วเด้งกลับหน้า 1** (`usePaginated({ resetOn })`) ไม่งั้นคนที่กด
  "ค่าซ่อมมากไปน้อย" ตอนอยู่หน้า 5 จะไม่เห็นรายการที่แพงที่สุดเลย
- **Export (CSV / Excel ของหน้า Tickets) ใช้ลำดับที่เห็นบนจอ** ไม่ใช่ลำดับดิบ
- **ตัวเลือกใน dropdown สร้างจากข้อมูลจริง** เพิ่มสาขาใหม่แล้วสาขานั้นโผล่เองรอบหน้า
  และตัวกรองที่มีตัวเลือกเดียวจะซ่อนตัวเอง เพราะไม่ได้ช่วยอะไรแถมกินที่
- **ตัวกรองไม่ถูกจำข้ามรอบ** (ต่างจากการเรียง) เปิดหน้ามาต้องเห็นข้อมูลครบเสมอ —
  ตัวกรองที่ค้างไว้เคยทำให้คนเข้าใจว่าข้อมูลหาย

## กันการเปิด Inspect บนหน้าแอดมิน

หน้าในกลุ่ม `(dashboard)` มี `src/components/security/BlockDevTools.tsx` คอยสกัด

(`X-Frame-Options`, `nosniff`, `Referrer-Policy`, `Permissions-Policy`, `X-Robots-Tag: noindex`)
พร้อมปิด `x-powered-by` และยืนยันว่า production source map ปิดอยู่

> ### ⚠️ สิ่งนี้กันอะไรได้จริง และกันอะไรไม่ได้
>
> **กันได้:** คนในองค์กรที่คลิกขวาเล่นหรือกด F12 ด้วยความอยากรู้ — ซึ่งเป็นกรณีส่วนใหญ่
>
> **กันไม่ได้เลย:** คนที่ตั้งใจจะดูข้อมูล เพราะ HTML/JS ถูกส่งถึงเครื่องผู้ใช้เรียบร้อยแล้ว
> ก่อนโค้ดนี้จะได้ทำงาน ทางที่ยังเปิดอยู่เสมอและปิดไม่ได้จากฝั่งเว็บ:
> เปิด DevTools ค้างไว้ก่อนเปิดหน้าเว็บ · เมนูเบราว์เซอร์ → เครื่องมือสำหรับนักพัฒนา ·
> ปิด JavaScript แล้วโหลดใหม่ · `curl`/Postman ซึ่งไม่ผ่านเบราว์เซอร์จึงไม่เจอโค้ดนี้
>
> **เปลี่ยนรหัสผ่านแอดมินทันที** — `.\scripts\set-admin-password.ps1`
> รหัสตั้งต้นอยู่ใน `src/lib/db/staff.ts` ใครอ่าน repo ได้ก็รู้ และหน้า login ยังไม่มีตัวจำกัด
> จำนวนครั้งที่กรอกผิด สคริปต์รับรหัสแบบไม่แสดงบนจอ แฮชด้วย bcryptjs ตัวเดียวกับที่ระบบใช้ตรวจ
> แล้วเขียนลง `data/staff_accounts.json` ในคอนเทนเนอร์ (ไฟล์ที่ `lib/db/staff.ts` อ่านจริง) — ล็อกอินใหม่ได้ทันทีโดยไม่ต้อง deploy ซ้ำ
>
> **ชั้นป้องกันจริงมีชั้นเดียวคือ `AUTH_DISABLED=false`** — ✅ เปิดใช้แล้วตั้งแต่ 2 ต.ค. 2026
> ก่อนหน้านั้นใครมี URL ก็ดึงข้อมูลได้ด้วย `curl` บรรทัดเดียวโดยไม่ต้องแตะเบราว์เซอร์เลย
> (ทดสอบจากเน็ตภายนอกแล้วว่าดึงทะเบียนพนักงานออกมาได้ครบจริง — ไม่ใช่ความเสี่ยงบนกระดาษ)

เขียนหน้า/คอมโพเนนต์ใหม่ให้ตามธีมได้: ใช้โทเคน (`bg-surface` `text-ink` `border-line` `bg-accent` `text-on-accent` …)
แทนสีตรงๆ · สีหลักใช้ `border-accent/40` `ring-accent/30` ไม่ใช่ `cyan-400` · พื้นโปร่งแสงใช้ `bg-ink/[0.04]` ไม่ใช่ `bg-white/[0.04]`
— `tests/theme.test.cjs` ตรวจให้ · ใช้สีตัวหนังสือโทนอ่อนเฉดใหม่ (เช่น `text-sky-300`) ต้องเพิ่มใน**ทั้ง**บล็อกธีมสว่างและบล็อกพิมพ์ใน `globals.css`

## คลังไฟล์ (`/files`)

ที่เก็บไฟล์กลางของทีม IT แบบ Google Drive — อัปโหลดโปรแกรม/ไดรเวอร์/เอกสารไว้ที่เดียว แล้วเปิดดาวน์โหลดจากเครื่องไหนก็ได้
(ต้องล็อกอิน) · เมนู **🗂️ คลังไฟล์** ในแถบบน

| เรื่อง | รายละเอียด |
| --- | --- |
| ขนาด | ไฟล์ละไม่เกิน **500 MB** · ทั้งคลังไม่เกิน `DRIVE_QUOTA_GB` (ค่าตั้งต้น 20 GB) · ดิสก์ต้องเหลือว่าง ≥ 2 GB หลังรับไฟล์ |
| อัปโหลด | ปุ่ม ⬆ หรือลากไฟล์มาวางที่ไหนก็ได้บนหน้า · หลายไฟล์ต่อคิวกัน · เห็นความคืบหน้าทีละไฟล์ · ยกเลิกกลางทางได้ |
| เน็ตหลุดกลางทาง | ส่งเป็นท่อนละ 8 MB — ท่อนที่ล้มจะส่งซ้ำเอง 4 ครั้ง ถ้ายังไม่ได้ กด **ลองใหม่** แล้วส่งต่อจากท่อนที่ค้าง |
| จัดระเบียบ | โฟลเดอร์ซ้อนกันได้ · เปลี่ยนชื่อ · ย้ายไฟล์ · ข้อความกำกับไฟล์ · ค้นหาทุกโฟลเดอร์จากชื่อและข้อความกำกับ |
| ลบ | ลบโฟลเดอร์ได้เฉพาะโฟลเดอร์ว่าง (กันกดพลาดแล้วไฟล์หายทั้งโฟลเดอร์) · ลบไฟล์แล้วกู้คืนไม่ได้ |
| ดาวน์โหลด | ได้ชื่อไฟล์ภาษาไทยเดิม · เทียบ SHA-256 ในหน้าแก้ไขไฟล์ได้ว่าตรงต้นฉบับ · ดาวน์โหลดต่อจากที่ค้างได้ (Range) |

**ความปลอดภัย:** ทุก API เช็กล็อกอินเอง (ไม่พึ่ง `proxy.ts`) · คำขอที่แก้ข้อมูลต้องมี header `x-drive-client`
(กันเว็บอื่นยิงคำสั่งแทนผู้ใช้) · ดาวน์โหลดเป็น `attachment` + `application/octet-stream` เสมอ ไม่เปิดในหน้าเว็บ
— ไฟล์ HTML/SVG ที่อัปโหลดขึ้นมาจึงรันสคริปต์ในโดเมนแอดมินไม่ได้

**⚠️ สำรองข้อมูล:** ตัวไฟล์อยู่บน docker volume `drive` แยกจาก `app_data` — **`backup.bat` ไม่ได้สำรองให้**
(ตั้งใจ: backup ลงโฟลเดอร์ `backups/` ในโปรเจกต์ ไฟล์หลายร้อย MB ไม่ควรไปอยู่ตรงนั้น)
ไฟล์ไม่หายตอน deploy หรือรีสตาร์ตเครื่อง แต่หายถ้าลบ volume (`docker compose down -v` / รีเซ็ต Docker Desktop)
สำรองเองได้ด้วยคำสั่งนี้ในโฟลเดอร์โปรเจกต์ (ปลายทางควรเป็นดิสก์อีกลูก ไม่ใช่ในโปรเจกต์):

```powershell
docker compose cp app:/app/drive D:\backup\drive-2026-10-07
```

ความเร็วอัปโหลด/ดาวน์โหลดผ่าน Cloudflare ขึ้นกับเน็ตของออฟฟิศ — ไฟล์ใหญ่ใช้เวลาหลายนาทีได้
ระหว่างอัปโหลดห้ามปิดแท็บ (หน้าเว็บเตือนให้ก่อนปิด) ไม่งั้นต้องเริ่มไฟล์นั้นใหม่

`deploy.bat` ตรวจให้ด้วยว่าคลังไฟล์เขียนได้จริง (ขึ้น ✓ "คลังไฟล์ (/files) เขียนได้") — ดูเองได้ที่
`curl.exe http://127.0.0.1:3000/api/health` → `storage.drive_writable` ต้องเป็น `true`

## สิ่งที่ควรทำต่อก่อนขึ้น production (ติเพื่อก่อ)

รายการนี้คือช่องว่างที่รู้ตัวและตั้งใจปล่อยไว้ ไม่ใช่ของที่ลืมทำ — **ระบบใช้งานจริงอยู่แล้ว** ไม่ใช่ POC แล้ว จึงควรไล่เก็บตามลำดับความเสี่ยง:

1. **ยังไม่ได้ย้ายไป Postgres** — ข้อมูลทั้งหมดอยู่ในไฟล์ JSON บน docker volume `app_data` ซึ่ง**ไม่หายตอน deploy** (mount ถาวรไว้แล้ว) แต่ทุก request อ่าน/เขียนทั้งไฟล์ และถ้ามี 2 process เขียนพร้อมกันข้อมูลพังได้จริง · ห้ามย้ายระบบนี้ไป serverless (เช่น Vercel) ตราบใดที่ยังเป็นไฟล์ เพราะ filesystem ไม่ persist ข้าม request/instance
2. **`xlsx` (SheetJS) มีช่องโหว่ระดับ High ที่ยังไม่มี patch บน npm** (Prototype Pollution + ReDoS — `npm audit` เห็นได้) ความเสี่ยงจำกัดเพราะเป็นฟีเจอร์ Import Excel ที่ใช้ได้เฉพาะแอดมินที่ login แล้ว แต่ถ้าจะขึ้น production จริงควรพิจารณาย้ายไป `exceljs` หรือ sanitize ไฟล์ก่อน parse
3. **`stock_items.category` ยังเป็น free text** (ไม่ใช่ enum เหมือน `equipment.category`) ตามที่สังเกตจากต้นแบบ — ปล่อยให้เหมือนต้นแบบไว้ก่อนตามที่ตกลง scope "เหมือนทุกรูปแบบ" แต่ถ้าจะแก้ในอนาคตควร normalize เป็น enum/lookup table
4. **ผู้แจ้งที่มาจาก LIFF / คีย์เองในหน้าแอดมิน ยังเป็นการพิมพ์ชื่ออิสระ** (`findOrCreateUserByName`) — เสี่ยงสร้าง user ซ้ำถ้าพิมพ์ชื่อไม่ตรงกันทุกตัวอักษร **ฝั่งบอท LINE แก้แล้ว** (ส่ง `requester_user_id` จากทะเบียนพนักงานมาตรงๆ) เหลือ 2 ช่องทางนี้ที่ควรทำ autocomplete จากทะเบียน 326 คน
5. **รหัสผ่านบัญชีทดสอบยังเป็นค่า default ที่ hardcode ไว้ในโค้ด** (`SEED_PASSWORD` ใน `src/lib/db/staff.ts`) — ค่านี้อยู่ใน git history แล้ว **ต้องเปลี่ยนก่อนเปิดให้คนอื่นใช้** ด้วย `staff-admin.bat` (มีหลายบัญชี + สิทธิ์รายหน้าแล้วตั้งแต่ 13 ต.ค. 2026) · **ยังไม่มีตัวจำกัดจำนวนครั้งที่ล็อกอินผิด** — ควรทำก่อนแจกบัญชีให้หลายคน เพราะทุกบัญชีคือประตูที่เดารหัสได้จากอินเทอร์เน็ต
6. **webhook ฝั่ง Next.js (`/api/line/webhook`) ยังไม่มี rate limiting / retry queue** — ประมวลผล sync ทั้งหมด (บอท Python ซึ่งเป็นตัวที่ใช้จริงมีกันสแปม `RATE_LIMIT_PER_MINUTE` อยู่แล้ว ค่าตั้งต้น 20 ครั้ง/นาที/คน) route เดิมยังอยู่แต่ไม่ได้เป็น webhook ที่ LINE ยิงเข้าแล้ว

## คำสั่งที่ใช้บ่อย

```bash
npm run dev      # dev server (Turbopack)
npm run build    # production build — ควรรันก่อน deploy ทุกครั้งเพื่อจับ type error/route error
npm run start    # รัน production build ที่ build ไว้แล้ว
npm run lint     # ESLint
npx tsc --noEmit # ตรวจ type อย่างเดียว เร็วกว่า build มาก ใช้ระหว่างแก้

# เทสต์ — ต้องเขียวทั้งคู่ก่อนบอกว่าเสร็จ
node --test tests/*.test.cjs                  # ฝั่งเว็บ 211 เคส
cd line-bot-python && python -m pytest -q     # ฝั่งบอท 356 เคส
py -m pytest tools/tests -q                   # โปรแกรมจัดการผู้ใช้ 44 เคส (ส่วนหน้าจอข้ามเองถ้าไม่มีจอ)
```

ฝั่งปฏิบัติการ (Windows + Docker Desktop เปิดอยู่ — ดับเบิลคลิกได้เลย):

```powershell
deploy.bat              # build + docker compose up + ตรวจผลปลายทางจริงกว่า 20 ข้อ
backup.bat              # สำรอง data/ + .env (ไม่รวมตัวไฟล์ในคลังไฟล์ — ดูหัวข้อ "คลังไฟล์")
install-autostart.bat   # รันเป็น admin ครั้งเดียวตอนตั้งเครื่องใหม่ (backup อัตโนมัติ + เอาตัวเปิด Funnel เดิมออก)
use-cloudflare.bat      # ทางเข้าจากเน็ต: ใส่ token ของ Cloudflare Tunnel + ย้าย LINE webhook + ปิด Funnel (รันซ้ำได้)
enable-funnel.bat       # ทางสำรองเดิม: เปิดออกเน็ตผ่าน Tailscale Funnel (ต้องย้าย LINE webhook กลับเองด้วย)
check-public.bat        # ตรวจว่าคนนอกเข้า https://<DOMAIN>/ (DuckDNS + port forward) ได้จริงไหม และพังตรงไหน
staff-admin.bat         # จัดการผู้ใช้ รหัสผ่าน และหน้าที่แต่ละคนเข้าได้ (ต้องเปิด Docker Desktop)
```
